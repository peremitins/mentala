Техническое задание: Обновление структуры шаблонов уведомлений под формат items[]

1. Контекст и проблема

В системе уведомлений внедряется семантическая привязка изображений к текстам через поле imageTag.

AI-генерация уже работает (или будет работать) в формате массива объектов, а не массива строк:
• было: string[]
• стало: { text: string; imageTag: ImageTag | null; subtype: NotificationSubtype | null }[]

Шаблонные уведомления (и кастомные шаблоны пользователя) сейчас хранятся или обрабатываются как строки, из-за чего:
• нельзя назначить картинку осознанно (нет imageTag);
• невозможно единообразно поддерживать mixed и правила harm\_\*;
• усложняется ротация и учет использования;
• сервисы превращаются в “если AI, то так, если шаблон, то иначе”.

Цель задачи: унифицировать формат шаблонов под новую структуру.

⸻

2. Цель

Сделать так, чтобы шаблонные уведомления и AI-уведомления имели одинаковый внутренний формат и проходили через один и тот же пайплайн:
• выбор текста,
• выбор изображения,
• правила совместимости,
• ротация,
• учет использования.

⸻

3. Термины и сущности

3.1 Формат элемента уведомления

Единый формат для всех источников (AI, templates):

type NotificationItem = {
text: string;
imageTag: ImageTag | null;
subtype: NotificationSubtype | null; // null, кроме subtype=mixed в контексте generation
};

3.2 Список ImageTag (фиксированный)
• harm_organs
• harm_appearance
• harm_mental
• activity
• nature
• meditation
• daily_life
• neutral_abstract

⸻

4. Что именно нужно изменить

4.1 Каталог шаблонов (статические шаблоны приложения)

Если шаблоны сейчас выглядят как:

const templates = [
"Текст 1",
"Текст 2",
];

нужно перейти на:

const templates: NotificationItem[] = [
{ text: "Текст 1", imageTag: null, subtype: null },
{ text: "Текст 2", imageTag: null, subtype: null },
];

Требования:
• subtype для шаблонов всегда null.
• imageTag может быть null. Если null — картинка не прикрепляется.
• harm\_\* в шаблонах допускается только если шаблон относится к quit + informational + hard по текущим правилам.
• если imageTag = null, harm\_\* не допускаются (нельзя “подтянуть” вредный визуал без явного тега).

⸻

4.2 Пользовательские шаблоны (если есть редактирование текста)

Если у пользователя есть возможность редактировать шаблонные тексты, то структура хранения в базе данных должна поддерживать imageTag.

Было (текущее в проекте):
• таблицы `notification_texts` и `notification_text_presets` содержат `text`, но не `imageTag`.

Стало (целевой вариант для проекта):
• таблицы `notification_texts` и `notification_text_presets` получают поле `image_tag` (string, null).
• default значение для legacy/без явной привязки: `null`.

Важно:
• **НЕ** использовать JSONB массивы в БД для шаблонов — в проекте уже есть табличная модель (строка = один текст).
• user templates = записи в `notification_texts` с `user_id != null`.

⸻

5. Обратная совместимость и миграция legacy

5.1 Legacy шаблоны, если остались строки

Если где-то в коде или базе остаются string[], используется автоматическая нормализация:
• text = строка
• imageTag = null
• subtype = null

Это временная мера до полной миграции.

5.2 Скрипт миграции

Нужен скрипт миграции для данных в базе:
• вход: записи `notification_texts`/`notification_text_presets` без `image_tag`.
• выход: те же записи с заполненным `image_tag`.

Правило:
• всем шаблонам выставить `image_tag = null`, если нет явной информации.

Примечание:
• В проекте уже есть скрипт `scripts/migrate-templates-to-db.ts`, он должен начать проставлять `image_tag` при заполнении таблиц.

⸻

6. Изменения в коде

6.1 DTO и типы

Добавить или зафиксировать общий тип NotificationItem.

Обновить типы:
• шаблонов (`notificationTemplates`),
• хранилищ в базе (`notification_texts`, `notification_text_presets` — поле `image_tag`),
• API, если оно отдает шаблоны на клиент.

6.2 Единая нормализация

Ввести функцию:
• принимает Array<string | object>
• возвращает NotificationItem[]
• валидирует длину текста, префикс, запрещенные поля
• выставляет default imageTag = null

Функция должна использоваться:
• для AI-ответа,
• для шаблонов,
• для загрузки из базы.

6.3 Сервис подбора изображения

Сервис картинок должен принимать imageTag без привязки к источнику.

Если imageTag = null:
• no-image (картинка не прикрепляется)

7. UX и UI требования (если есть экран управления)

Если в интерфейсе пользователь может выбирать “Только шаблоны”:
• кнопка редактирования отображается только для шаблонов.
• для AI-контента редактирование скрыто.

Если появится UI выбора imageTag для пользовательских шаблонов, это отдельная задача.
В этом ТЗ не требуется обязательный UI тегирования, достаточно default null.

⸻

8. Тестирование

8.1 Unit-тесты
• нормализация string[] → NotificationItem[]
• нормализация объектов с мусорными полями (additionalProperties запрещены)
• fallback по imageTag

8.2 Интеграционные тесты
• templates-only режим отрабатывает и ставит картинки
• templates и AI работают раздельно и корректно
• после миграции old data ничего не падает

⸻

9. Критерии приемки
   • Вся система уведомлений работает с единым форматом NotificationItem[].
   • Шаблоны больше не передаются как string[] в основной код-путь.
• Любой источник уведомлений поддерживает imageTag (явно или через fallback).
• Если imageTag = null, картинка не прикрепляется.
   • mixed логика не ломается от шаблонов, потому что subtype у шаблонов всегда null.
   • Никаких harm\_\* в шаблонах и legacy, если контекст это запрещает правилами.
