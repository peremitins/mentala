# Mentala: ТЗ на рефакторинг памяти и оптимизацию токенов в AI-чате

Статус: draft v2.3  
Дата актуализации: 20 марта 2026

Официальные источники OpenAI, на которые должна опираться будущая реализация:

- Conversation state: https://developers.openai.com/api/docs/guides/conversation-state
- Prompt caching: https://developers.openai.com/api/docs/guides/prompt-caching
- Realtime API reference: https://developers.openai.com/api/reference/resources/realtime

## 1. Суть рефакторинга

Рефакторинг теперь состоит из двух связанных задач.

### 1.1. Основная задача

Пересобрать логику памяти текстового чата так, чтобы:

1. `previous_response_id` жил только внутри одной активной `therapySession`.
2. После завершения сессии контекст не продолжался бесконечной OpenAI-цепочкой.
3. Между сессиями переносился не raw conversation state, а компактный summary handoff.

### 1.2. Вторая задача

Параллельно сократить повторную передачу prompt-слоёв внутри активной сессии:

1. отделить стабильный session-level контекст от динамического per-turn контекста;
2. перестать бесконтрольно дублировать стабильные инструкции на каждом ходе;
3. измерять результат по реальным OpenAI usage, а не по локальной приблизительной оценке.

Итог: это единый рефакторинг памяти и токенной экономики, где задача с summary и session-reset считается основной, а prompt-оптимизация остаётся обязательной частью того же этапа.

Дополнительно фиксируется:

1. session-end summary сам по себе недостаточен;
2. внутри длинной активной сессии нужен runtime guard;
3. при превышении порогов должна срабатывать принудительная compaction/reset-политика.

## 2. Цель

Нужно сократить фактический расход токенов в текстовом AI-чате Mentala без заметной деградации качества, без потери safety-поведения и без смешения разных сессий пользователя в одной длинной OpenAI-цепочке.

Ожидаемый результат:

1. В пределах одной активной сессии контекст продолжает работать предсказуемо.
2. После завершения сессии дорогая цепочка `previous_response_id` обрывается.
3. Следующая сессия стартует чисто, но получает компактный смысловой handoff через summary.
4. Prompt-слои внутри активной сессии перестают дублироваться без необходимости.
5. Baseline и эффект изменений измеряются по реальным usage-метрикам OpenAI.
6. Длинная активная сессия не может бесконечно разрастаться: есть runtime token guard и ограничение длины chain.

## 3. Зафиксированное текущее состояние по коду

### 3.1. Обычный текстовый чат

Сейчас текстовый чат работает так:

1. в OpenAI отправляется не вся локальная история, а только:
   - `systemPrelude`;
   - `developerContext`;
   - опциональный `userPrompt`;
   - последнее сообщение пользователя;
2. для продолжения контекста используется `previous_response_id`;
3. `store: true` включается при использовании `previous_response_id`.

Следствие:

1. локальный текущий `input` выглядит небольшим;
2. реальный billable context может быть огромным из-за длинной цепочки `previous_response_id`;
3. повторные `system/developer` блоки продолжают попадать в эту цепочку снова и снова.

### 3.2. Scope памяти сейчас некорректный

Сейчас `response_id` хранится по `userId`, а не по `therapySessionId`.

Следствие:

1. новая чат-сессия пользователя может логически продолжить старую;
2. параллельные и последовательные диалоги смешиваются;
3. стоимость и качество начинают зависеть не от текущей сессии, а от хвоста старых разговоров;
4. это уже подтверждено реальными usage-логами.

### 3.3. Старый summary-механизм не удалён, а выключен

Summary-ветка уже есть в коде, но отключена глобальным флагом:

1. `SUMMARY_ENABLED = false`;
2. `finishSession()` рано выходит и summary не создаёт;
3. текущий runtime опирается почти только на `previous_response_id`.

### 3.4. Что делала старая summary-логика

Старая реализация summary была заготовкой, но не готовым целевым решением:

1. summary строился в `finishSession()`;
2. в prompt на summary уходил только хвост `lastK = allMessages.slice(-12)`;
3. summary сохранялся в `summaryStore`;
4. при использовании summary в чат подмешивались последние несколько summary через `buildSessionMemoryText()`.

Ограничения старой версии:

1. summarization строится не по полной серверной картине сессии, а только по хвосту;
2. summary storage сейчас plaintext, что противоречит требованиям приватности проекта;
3. summary-формат ориентирован на старую механику “контекст прошлых сессий”, а не на целевой handoff между соседними сессиями;
4. старая логика не решает проблему session-scope для `previous_response_id`.

### 3.5. Baseline-логирование уже добавлено

На текущем этапе в проекте уже появились реальные usage-логи для:

1. обычного чата;
2. стримового чата;
3. suggested chips;
4. Realtime Voice.

Это означает, что baseline до рефакторинга уже можно измерять по серверным логам, а не по приблизительной клиентской оценке.

## 4. Главная проблема, которую нужно решить

Проблема состоит не только в длинных prompt-текстах.

Главная проблема сейчас такая:

1. `previous_response_id` живёт слишком долго;
2. он привязан к пользователю, а не к одной therapy-session;
3. в эту цепочку на каждом ходе продолжают добавляться новые копии стабильных инструкций;
4. из-за этого второй или третий запрос локально выглядит маленьким, а по фактическому OpenAI usage уже стоит как большой длинный диалог.

Следствие:

1. стоимость становится плохо контролируемой;
2. latency растёт;
3. контекст между сессиями смешивается;
4. локальная модель “это только второй ответ в сессии” перестаёт совпадать с реальным состоянием OpenAI chain.

## 5. Целевая архитектура

### 5.1. Границы памяти

Новая целевая схема должна быть такой:

1. внутри одной активной `therapySession` память держится через `previous_response_id`;
2. после завершения `therapySession` эта цепочка завершается;
3. в следующую сессию переносится не прежний `previous_response_id`, а summary прошлой сессии.

### 5.2. Handoff между сессиями

Целевой handoff:

1. сессия завершается;
2. сервер инициирует summarization;
3. summary сохраняется в хранилище;
4. связанный с этой сессией `previous_response_id` сбрасывается;
5. следующая сессия стартует без `previous_response_id`, но с summary context.

### 5.3. Что считается “сбросом previous_response_id”

Для логики работы чата сброс считается выполненным, если:

1. следующий запрос больше не отправляет старый `previous_response_id`;
2. локальная запись `response_id`, связанная с завершённой сессией, удалена или помечена как невалидная;
3. новая сессия не наследует старую цепочку.

Важно:

1. для продуктовой логики не требуется обязательно удалять remote response object у OpenAI;
2. достаточно перестать продолжать старую цепочку;
3. remote delete может рассматриваться только как отдельная политика data hygiene, но не как обязательный механизм runtime-reset.

### 5.4. Prompt-оптимизация внутри активной сессии

Даже после введения summary handoff остаётся обязательной вторая часть рефакторинга:

1. разделить контекст на `session-bootstrap` и `per-turn`;
2. не дублировать стабильный session-layer на каждом ходе;
3. не выкидывать safety и flow-зависимые per-turn инструкции.

Иначе стоимость внутри одной длинной активной сессии всё равно будет расти слишком быстро.

### 5.5. Runtime compaction внутри активной сессии

Новая схема должна учитывать не только границу между сессиями, но и длинные активные сессии.

Если chain внутри одной активной `therapySession` становится слишком длинной или слишком дорогой:

1. выполняется принудительная compaction;
2. создаётся обновлённое техническое summary текущего состояния;
3. старая chain сбрасывается;
4. та же `therapySession` продолжает работу уже с новым компактным state.

Это нужно, чтобы не ждать формального конца сессии и не получать повторно экстремальные usage на простом turn.

Runtime compaction не должен использовать тот же контракт, что и session-end handoff.

Фиксируется разделение:

1. `RUNTIME_COMPACTION_CONTRACT = separate_internal_contract`
2. `SESSION_END_SUMMARY_CONTRACT = separate_handoff_contract`

Смысл:

1. runtime compaction решает техническую задачу стабилизации активной session;
2. session-end summary решает продуктовую задачу межсессионного handoff;
3. runtime contract должен быть короче и дешевле handoff-contract.

## 6. Требования к новой summary-схеме

### 6.1. Что именно нужно вернуть из старой логики

Нужно вернуть сам механизм summary, но не в старом виде “как было”, а в скорректированном варианте:

1. снова задействовать серверный `finishSession()` или эквивалентный server-driven summary pipeline;
2. снова использовать summary как межсессионный memory handoff;
3. убрать зависимость продукта от длинной пользовательской chain-памяти между сессиями.

### 6.2. Что в старой логике нужно обязательно поменять

Старая summary-ветка в текущем виде не считается готовой к возврату. Нужно изменить:

1. scope памяти: `response_id` должен быть привязан к `therapySessionId`, а не к `userId`;
2. источник summary: нельзя summariz’ить только последние 12 сообщений, если это искажает смысл сессии;
3. summary storage: plaintext-хранение недопустимо, потому что противоречит требованиям `.docs/security_requirements.md`;
4. summary injection: нельзя бесконтрольно подмешивать много старых summary сразу;
5. lifecycle: summary должен строиться по серверному завершению сессии, а не только по событию “страница закрылась”;
6. storage policy: если пользователь отключил memory через `enablePreviousResponseId`, summary не должен сохраняться и не должен подмешиваться в будущую сессию.

### 6.3. Каким должен быть summary по смыслу

Summary должен быть не “пересказом всего диалога”, а компактной структурированной памятью для следующей сессии.
Summary должен представлять именно state, а не narrative-пересказ.

Он должен передавать:

1. что важно помнить о состоянии пользователя;
2. основные темы и устойчивые паттерны;
3. что уже дало пользу;
4. что осталось незавершённым;
5. есть ли риск или особый safety-контекст;
6. что нужно аккуратно подхватить в следующей сессии.

Summary не должен:

1. превращаться в большой narrative на много абзацев;
2. копировать почти весь диалог в другом виде;
3. становиться источником нового prompt-bloat;
4. ломать требования приватности.

Пример смыслового формата:

```json
{
  "themes": ["тревога", "работа"],
  "patterns": ["избегание"],
  "last_focus": "конфликт с коллегой"
}
```

### 6.4. Формат summary как целевой контракт

В следующей итерации реализации нужно либо адаптировать текущую summary-schema, либо ввести новую. Предпочтительная целевая структура:

1. `session_overview_short`
2. `stable_facts_to_carry`
3. `themes_active`
4. `patterns_or_triggers`
5. `helpful_interventions`
6. `unfinished_threads`
7. `risk_state`
8. `next_session_guidance`

Допускается сохранить часть старых полей, если это упростит миграцию, но целевая схема должна быть ориентирована именно на межсессионный handoff, а не на архивный summary ради summary.

### 6.5. Политика хранения summary

Product rule для первой итерации:

1. если `enablePreviousResponseId = false`, summary не сохраняется;
2. если `enablePreviousResponseId = false`, следующая сессия стартует без memory handoff;
3. summary-память рассматривается как форма memory, а не как “внутреннее исключение”.

### 6.6. Только последнее summary в v1

Для первой итерации фиксируется простая политика:

1. в новую сессию подмешивается только последнее релевантное summary;
2. long-term aggregated profile в v1 не строится;
3. накопление нескольких summary подряд в prompt запрещено.

Long-term профиль допускается рассматривать только как отдельный этап v2 после замеров.

### 6.7. Incremental compaction вместо пересчёта всей истории

Целевая стратегия summary и compaction должна быть incremental.

Нельзя считать целевой схемой:

1. каждый раз брать весь сырой диалог целиком;
2. пересобирать полное summary заново из всей истории.

Нужно ориентироваться на схему:

1. `existing_summary + новые сообщения -> updated_summary`;
2. summary обновляется итеративно;
3. полная сырая история не таскается бесконечно между этапами compaction.

## 7. Требования к lifecycle сессии

### 7.1. Когда создавать summary

Summary должен создаваться по серверному завершению сессии.

Каноническая формула конца сессии:

1. `explicit_end`
2. `OR idle_timeout`
3. `OR new_session_started`

Фиксированное значение для первой итерации:

1. `IDLE_TIMEOUT_MS = 15 * 60 * 1000`

Надёжные триггеры:

1. явное завершение терапии/чата;
2. серверный idle-timeout;
3. принудительное закрытие сессии сервером;
4. запуск новой `therapySession`, если предыдущая ещё не была корректно закрыта.

Слабые сигналы, которые можно использовать только как best effort:

1. уход пользователя со страницы;
2. закрытие вкладки;
3. background/terminate события приложения.

### 7.2. Что делать после завершения сессии

После session-end pipeline обязан:

1. завершить текущий lifecycle сессии на сервере;
2. построить summary или зафиксировать контролируемый fallback;
3. сохранить summary;
4. сбросить session-scoped `previous_response_id`;
5. не позволить следующей сессии продолжать старую OpenAI chain.

### 7.3. Поведение при ошибке summary

Поведение при ошибке summary зафиксировано как обязательное правило.

Если summary не удалось построить:

1. старая chain всё равно сбрасывается;
2. следующая сессия не получает старый `previous_response_id`;
3. используется `fallback_empty` или минимальный fallback-state;
4. сохранение старой дорогой chain “на всякий случай” запрещено.

Формально:

```ts
if (summary_failed) {
  reset_chain = true;
  next_session_memory = fallback_empty;
}
```

Иначе один сбой summarization ломает всю токенную экономику продукта.

### 7.4. Runtime Token Guard

Внутри активной сессии должен существовать принудительный guard:

```ts
if (estimated_tokens > MAX_INPUT_TOKENS) {
  summarize_and_reset();
}
```

Guard обязан срабатывать до того, как стоимость и latency уходят в неконтролируемую область.

Для первой итерации фиксируется двухуровневый token guard:

1. `SOFT_INPUT_TOKENS = 10000`
2. `MAX_INPUT_TOKENS = 15000`

Интерпретация:

1. до `10000` input tokens chain живёт без специальных действий;
2. зона `10000–15000` считается зоной внимания: chain помечается как кандидат на compaction, событие логируется, допускается мягкая compaction на ближайшем удобном turn;
3. при превышении `15000` продолжение текущей chain запрещено, выполняется forced runtime compaction/reset до следующего обычного ответа.

### 7.5. Max chain length

Помимо токенного порога должна существовать жёсткая граница длины chain:

1. вводится `MAX_TURNS_PER_CHAIN`;
2. после достижения лимита выполняется forced summary / compaction;
3. после compaction старая chain сбрасывается и продолжается новая.

Фиксированное значение для первой итерации:

1. `MAX_TURNS_PER_CHAIN = 24`

Правило интерпретации:

1. это не основной trigger compaction;
2. основным guard остаётся реальный размер входного контекста;
3. `MAX_TURNS_PER_CHAIN` используется как fallback safety guard, если токены растут медленно, но chain технически тянется слишком долго.

### 7.6. Max input tokens

В ТЗ обязателен лимит верхней границы входного контекста:

1. вводится `MAX_INPUT_TOKENS`;
2. при его превышении обычный runtime-turn не продолжается по старой chain;
3. сначала выполняется compaction/reset, затем продолжается работа.
4. дополнительно вводится `SOFT_INPUT_TOKENS` для раннего обнаружения chain-кандидатов на compaction.

## 8. Требования к prompt-слоям внутри активной сессии

### 8.1. Явное разделение контекста

Нужно зафиксировать два слоя:

1. `session-bootstrap`
2. `per-turn`

### 8.2. Что относится к `session-bootstrap`

Кандидаты на session-level слой:

1. базовая persona;
2. основные safety-правила общего характера;
3. addressing, если оно стабильно в сессии;
4. tone background;
5. стабильная персонализация пользователя;
6. редкие session-level инструкции.

### 8.3. Что обязано остаться в `per-turn`

На каждом ходе должны оставаться явными:

1. crisis guidance;
2. `responseNumber`-зависимая структура ответа;
3. phobias-flow overlays;
4. welcome-flow overlays;
5. `entryContext` overlays;
6. текущие scenario-specific developer instructions;
7. всё, что зависит от состояния конкретного входа здесь и сейчас.

## 9. Требования к измерению результата

### 9.1. Что измеряется до и после

До и после рефакторинга обязательно сравнивать:

1. `inputTokens`
2. `outputTokens`
3. `totalTokens`
4. `cachedTokens`
5. размер фактически отправленного `input` по ролям;
6. latency;
7. долю запросов с `previous_response_id`;
8. среднюю стоимость второго и третьего хода в активной сессии;
9. стоимость первого хода новой сессии после summary handoff;
10. стоимость summarization itself;
11. частоту срабатывания runtime token guard;
12. частоту forced compaction по длине chain.

### 9.2. Какой источник истины использовать

Источником истины считаются:

1. OpenAI `usage` в серверных логах;
2. серверные логи `chat`, `chat_stream`, `chips`, `realtime`;
3. server-side метрики по session lifecycle.

Локальная approximate cost estimate не считается источником истины для billing.

## 10. Что входит в первую итерацию реализации

### 10.1. Обязательно входит

1. перепривязка `previous_response_id` к `therapySessionId`;
2. session-bounded lifecycle chain-памяти;
3. возврат summary-механизма в обновлённом виде;
4. server-driven reset старой chain после завершения сессии;
5. handoff в новую сессию через summary;
6. сохранение prompt-оптимизации как второй части рефакторинга;
7. сравнение baseline и post-change по реальным usage-логам;
8. корректировка старой summary-логики, которая сейчас выключена;
9. учёт требований приватности к summary storage и логированию;
10. runtime token guard;
11. ограничение `MAX_TURNS_PER_CHAIN`;
12. использование только последнего summary в v1;
13. incremental compaction вместо полного пересчёта всей истории на каждом шаге;
14. двухуровневый token guard `SOFT_INPUT_TOKENS / MAX_INPUT_TOKENS`;
15. отдельный internal contract для runtime compaction и отдельный handoff contract для session-end summary.

### 10.2. Не обязано входить в первую итерацию

1. миграция текстового чата на Conversations API;
2. полное перепроектирование Realtime Voice;
3. полная переработка suggested chips;
4. смена модели;
5. prompt caching как самостоятельная главная стратегия;
6. удаление remote response objects в OpenAI, если для runtime-reset это не требуется.

## 11. Критерии приёмки

Рефакторинг считается успешным, если выполнены все условия:

1. `previous_response_id` больше не шарится между разными `therapySession`;
2. новая сессия не продолжает старую OpenAI chain;
3. после завершения сессии создаётся summary handoff или контролируемый fallback;
4. второй и последующие ходы внутри одной новой сессии становятся дешевле baseline;
5. первый ход следующей сессии после summary handoff становится радикально дешевле, чем продолжение старой длинной chain;
6. не возникает регрессий в:
   - crisis handling;
   - welcome flow;
   - phobias flow;
   - addressing;
   - assistant tone;
   - suggested chips;
7. summary не хранится в виде, нарушающем требования безопасности и приватности проекта;
8. архитектура явно фиксирует:
   - границу active session;
   - механизм summary handoff;
   - правила reset для `previous_response_id`;
   - разделение `session-bootstrap` и `per-turn`;
9. при `enablePreviousResponseId = false` summary не сохраняется и не используется;
10. в v1 в новую сессию подмешивается только последнее summary;
11. при сбое summary старая chain всё равно обрывается;
12. при превышении runtime-порогов выполняется forced compaction/reset;
13. `MAX_TURNS_PER_CHAIN = 24` работает как fallback guard, а не как основной trigger;
14. `SOFT_INPUT_TOKENS = 10000`, `MAX_INPUT_TOKENS = 15000`;
15. runtime compaction использует отдельный internal contract, а не session-end handoff contract.

## 12. Основные риски

### 12.1. Риск деградации качества между сессиями

Если summary будет слишком бедным или слишком общим, новая сессия станет:

1. менее персонализированной;
2. менее связной;
3. хуже подхватывающей незавершённые темы.

### 12.2. Риск дорогого summarization

Если summarization делать на слишком длинном сыром транскрипте без ограничений, можно просто перенести перерасход токенов из runtime в session-end pipeline.

### 12.3. Риск отсутствия runtime compaction

Если summary делать только в конце сессии, а внутри long-running session не делать forced compaction:

1. прежняя проблема может сохраниться внутри одной длинной активной сессии;
2. стоимость будет взрываться до формального session-end;
3. latency останется нестабильной.

### 12.4. Риск ложного завершения сессии

Если session-end триггеры будут определены неаккуратно, можно:

1. рано обрывать полезную chain-память;
2. создавать лишние summary;
3. терять continuity там, где пользователь ещё находится в той же активной сессии.

### 12.5. Риск нарушения приватности

Если вернуть summary “как было”, то:

1. summary останется plaintext;
2. это противоречит требованиям безопасности проекта;
3. решение нельзя будет считать архитектурно корректным.

## 13. Дополнительные архитектурные замечания

1. Realtime Voice не является моделью для текстового чата и не задаёт правила для lifecycle text-session.
2. Suggested chips должны продолжать измеряться отдельно от основного ответа.
3. Prompt caching не заменяет правильный session lifecycle и не решает проблему user-scoped chain state.
4. Если в будущем будет выбран `Conversations API`, нужно отдельно описать lifecycle conversation object и его привязку к `therapySessionId`.
5. Summary pipeline должен опираться на серверную “истину” о сессии, а не на ненадёжные клиентские события ухода со страницы.
6. Для v1 runtime compaction и session-end handoff не используют общий контракт: runtime compaction работает через отдельный internal contract, session-end memory handoff — через отдельный handoff contract.
7. `Turn` для chain-guard определяется как один пользовательский запрос, на который был создан один основной assistant response; retries, chips и summary pipeline не считаются обычными turn-ами chain.
8. Приоритет guard-ов фиксируется так: `explicit_end` и `new_session_started` безусловно завершают текущую session; `MAX_INPUT_TOKENS` важнее `MAX_TURNS_PER_CHAIN`; `SOFT_INPUT_TOKENS` только помечает chain кандидатом; `idle_timeout` не должен перебивать уже идущий active request.
9. При forced runtime compaction текущее новое сообщение пользователя не входит в compaction prompt: compaction строится по уже накопленному состоянию, а текущий user turn становится первым сообщением новой chain после compaction.
10. `estimated_tokens` не должен опираться только на локальную оценку символов: primary signal — реальные usage предыдущих запросов OpenAI плюс серверная оценка размера следующего payload; при невозможности точного расчёта используется conservative estimate по отправляемым ролям и последнему observed usage.
11. Incremental compaction допустим только поверх валидного канонического summary-state; черновой или усечённый summary из хвоста не должен становиться базой для многошагового накопления.
12. Summary storage должен содержать `schemaVersion`, а runtime обязан безопасно игнорировать или отбрасывать неизвестные версии.

## 14. Зафиксированные численные решения для implementation plan

Следующие параметры считаются принятыми для первой итерации и должны использоваться в implementation plan как baseline-конфигурация:

1. `IDLE_TIMEOUT_MS = 15 * 60 * 1000`
2. `MAX_TURNS_PER_CHAIN = 24`
3. `SOFT_INPUT_TOKENS = 10000`
4. `MAX_INPUT_TOKENS = 15000`
5. `RUNTIME_COMPACTION_CONTRACT = separate_internal_contract`
6. `SESSION_END_SUMMARY_CONTRACT = separate_handoff_contract`

Принцип применения:

1. основным runtime-guard является размер входного контекста;
2. лимит `24` turn-ов является fallback-страховкой, а не главным рубильником;
3. мягкая зона начинается с `10000` input tokens;
4. жёсткий forced compaction/reset начинается при `15000` input tokens;
5. runtime compaction и session-end handoff используют разные контракты.
