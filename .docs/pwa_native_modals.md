# Техническое задание

## Название задачи

Переработка mobile install/app-promo flow на web с переходом на Android `native-first` модель и сохранением полноценного web-доступа.

## Цель

Нужно полностью заменить текущий Android PWA install flow на новый Android flow, который учитывает, что нативное приложение уже опубликовано в Google Play, но при этом **не перехватывает у пользователя право пользоваться веб-версией**.

Итоговая модель должна быть такой:

- на Android PWA больше не продвигается и не предлагается к установке;
- вместо PWA используется app-promo flow для нативного Android-приложения;
- если приложение установлено, пользователь может **по своему желанию** открыть его из веба;
- если приложение не установлено, пользователь может перейти в Google Play;
- пользователь всегда может остаться в веб-версии;
- никакого принудительного редиректа в приложение быть не должно;
- web billing flow и возврат из оплаты через сайт должны продолжать работать без поломок.

## Почему это делается

### 1. Android уже должен вести в native flow

Текущая PWA-модель на Android устарела продуктово: нативное приложение уже есть в магазине, поэтому PWA не должно быть основным мобильным сценарием.

### 2. Web остаётся обязательным каналом

Несмотря на наличие Android-приложения, веб нельзя делать "второсортным" или принудительно вытеснять:

- пользователь должен сам выбирать, где продолжать сценарий;
- часть сценариев, в том числе billing, завязана на web;
- в проекте уже есть внешний web flow для подписки и оплаты, включая переходы через:
  - `/subscription`
  - `/auth/external-session/consume`
  - `/payment-success`
- если сайт начнёт жёстко выкидывать пользователя в приложение, это может сломать оплату и возврат из платёжного flow.

### 3. iPhone / iOS пока живёт по другой модели

На iPhone / iOS нативное приложение пока не опубликовано, поэтому текущий PWA guide остаётся актуальным и не заменяется Android-сценарием.

## Текущее состояние кодовой базы

В проекте уже есть централизованный PWA install flow:

- логика находится в `app/composables/usePwaInstall.ts`;
- install UI показывается из `app/layouts/default.vue`;
- на Android сейчас используется PWA install banner / manual guide;
- на iOS сейчас используется отдельный guide по добавлению на экран Домой;
- код PWA install flow уже интегрирован в основной layout и в текущую продуктовую логику.

Также важно:

- в проекте уже есть `/.well-known/assetlinks.json`;
- в проекте уже есть `/.well-known/apple-app-site-association`;
- в текущем manifest **нет** `related_applications`;
- в текущем manifest **нет** `prefer_related_applications`;
- в текущем web flow ещё нет завершённой логики Android installed-app detection + open-app CTA как основного install/app-promo сценария.

## Принципы целевого поведения

### 1. Android = native-first, но не native-only

На Android сайт должен продвигать нативное приложение, а не PWA.  
Но сайт **не должен** навязывать переход в приложение и **не должен** автоматически отнимать у пользователя веб.

### 2. Любое открытие приложения только по явному действию пользователя

Допустимо:

- кнопка `Открыть приложение`;
- кнопка `Установить из Google Play`;
- явный CTA внутри banner/card/sheet.

Недопустимо:

- автоматический redirect в приложение на page load;
- автоматический redirect при каждом заходе на сайт;
- принудительный app takeover, если пользователь уже открыл web;
- скрытая подмена обычной веб-навигации в app-open flow.

### 3. Web billing flow должен быть полностью сохранён

Android app-promo flow не должен мешать сценариям:

- просмотра тарифов на сайте;
- перехода на web checkout;
- возврата после оплаты;
- повторного открытия web subscription flow;
- external session consume flow.

На чувствительных к оплате маршрутах app-promo UI не должен ломать UX и не должен инициировать никакие auto-open переходы.

### 4. PWA на Android больше не является install-путём

На Android необходимо убрать:

- PWA install banner;
- PWA manual install guide;
- любые тексты и CTA, которые продвигают Android PWA как установочный сценарий.

## Что должно быть реализовано

### 1. Новый Android flow вместо PWA

На Android mobile web должен использоваться новый app-promo flow:

- если нативное приложение установлено и это можно надёжно определить, пользователь видит мягкий CTA `Открыть приложение`;
- если приложение не установлено, пользователь видит мягкий CTA `Установить из Google Play`;
- если достоверно определить состояние нельзя, используется безопасный fallback без принудительного перехода.

### 2. Installed-app detection

Для Android необходимо внедрить detection-слой, основанный на платформенно корректной связке:

- `related_applications` в web manifest;
- `Navigator.getInstalledRelatedApps()` там, где браузер поддерживает API;
- verified association сайта и Android-приложения;
- уже существующий `/.well-known/assetlinks.json` как часть этой связки.

Требование:

- нельзя формулировать detection как "простую локальную эвристику по user-agent";
- detection должен строиться на официальных браузерных и платформенных механизмах;
- если API недоступен, это должно вести к предсказуемому fallback-поведению, а не к сломанному UX.

### 3. App open flow

Если Android-приложение определено как установленное, сайт должен дать пользователю **явный** сценарий открытия приложения.

Обязательные требования:

- открытие приложения только по клику пользователя;
- отсутствие автоперехода на mount / load / resume;
- обычный web-сеанс без клика остаётся в браузере;
- пользователь может проигнорировать предложение и продолжить пользоваться сайтом.

### 4. Google Play flow

Если Android-приложение не установлено, сайт должен предлагать переход в Google Play по официальной ссылке на store listing приложения.

Требования:

- не использовать PWA как fallback-install path на Android;
- использовать корректную Google Play ссылку для `com.mentala.app`;
- на Android по клику пользователя приоритетно открывать карточку приложения в установленном приложении Google Play, а не в browser tab;
- browser URL `https://play.google.com/store/apps/details?id=com.mentala.app` использовать только как fallback, если переход в приложение Google Play недоступен;
- в UI использовать аккуратный app-promo CTA, а не агрессивный full-screen takeover.

### 5. Fallback policy

Если браузер:

- не поддерживает `getInstalledRelatedApps()`;
- не отдал ожидаемый результат;
- не позволяет надёжно различить installed / not installed,

поведение должно быть безопасным:

- без автоперехода;
- без навязчивой блокировки;
- с сохранением полноценного web-доступа.

Безопасный fallback для Android должен быть описан и реализован явно.  
Предпочтительный вариант:

- показывать install/app-promo surface, который предлагает Google Play как базовый сценарий;
- не пытаться автоматически открывать приложение;
- оставлять пользователю возможность просто закрыть surface и продолжить web usage.

## UX / UI требования

### 1. Общий принцип

Android app-promo UI должен быть:

- ненавязчивым;
- визуально качественным;
- согласованным с текущим стеком UI;
- понятным с первого взгляда;
- не похожим на рекламу или агрессивный interstitial.

### 2. Формат surface

Для Android не использовать полноэкранную mandatory-модалку как основной entrypoint.  
Основной формат должен быть один из двух:

- компактный floating banner / card;
- аккуратный bottom sheet невысокой приоритетности.

Предпочтение: **компактный banner/card**, потому что он меньше мешает web usage и лучше соответствует требованию "пользователь сам выбирает".

### 3. Поведение UI

Обязательные UX-правила:

- surface должен быть dismissible;
- после dismiss пользователь не должен сразу получать повторный показ в рамках того же активного web-сеанса;
- surface не должен перекрывать критичные элементы интерфейса;
- surface не должен появляться мгновенно на первом кадре;
- surface не должен появляться до того, как пользователь вошёл в продукт или оказался в релевантном mobile контексте;
- на Android web не должно быть PWA install prompt даже как fallback.

Правило частоты показа:

- Android native app-promo flow не должен запоминать dismiss между reload страницы и новой авторизацией;
- если пользователь закрыл Android app-promo, он остаётся скрыт только до конца текущего активного web-сеанса;
- после reload страницы Android promo может быть показан снова;
- после logout -> login Android promo может быть показан снова;
- iOS PWA guide продолжает использовать более мягкий throttling: не чаще одного раза в сутки с ближайшим окном повторного показа в `10:00` локального времени пользователя.

### 4. Сценарии состояний

#### Android, приложение установлено

UI должен предлагать:

- primary CTA: `Открыть приложение`;
- secondary action: `Продолжить в браузере` или закрытие без потери web-сеанса.

#### Android, приложение не установлено

UI должен предлагать:

- primary CTA: `Установить из Google Play` или `Открыть в Google Play`;
- secondary action: `Продолжить в браузере` или закрытие.

#### Android, статус неизвестен

UI должен вести себя консервативно:

- не принуждать к открытию приложения;
- не пытаться auto-detect через хрупкие эвристики;
- не блокировать сайт;
- использовать мягкий install/app-promo сценарий с возможностью закрытия.

### 5. Важное продуктовое ограничение

На маршрутах, связанных с оплатой и возвратом после оплаты, app-promo UI должен быть либо отключён, либо максимально нейтрален и не мешать завершению сценария.

Минимально учитывать:

- `/subscription`
- `/payment-success`
- `/auth/external-session/consume`

Если пользователь пришёл по billing / payment-return flow, приоритет всегда у завершения web-сценария, а не у app-promo.

## Технические требования

### 1. Manifest и browser integration

Нужно доработать web manifest:

- добавить `related_applications`;
- описать Android app как `play` related application;
- не использовать `prefer_related_applications` как основной механизм текущего Android flow.

Важное уточнение:

- `prefer_related_applications` нельзя включать механически "потому что так умеет браузер";
- в текущей задаче приоритет у контролируемого frontend UX, а не у browser-managed install behavior;
- главное продуктное правило: **обычный web-сеанс остаётся в web и не принуждается к переходу в приложение**.

### 2. Android association

Нужно использовать и валидировать связку сайта и Android app через:

- `assetlinks.json`;
- Android App Links / verified association;
- package `com.mentala.app`.

Если для полного `open app` flow нужны доработки на стороне native Android app, это должно быть явно зафиксировано как зависимость, а не замалчиваться во фронтенд-реализации.

### 3. Политика показа

Нужна единая frontend policy-точка, которая решает:

- это Android или нет;
- это обычный web, а не native runtime;
- можно ли показывать app-promo UI;
- разрешён ли показ на текущем маршруте;
- установлен ли related Android app;
- какой CTA должен показываться;
- какой fallback используется.

Эта policy должна быть централизованной, а не размазанной по layout и отдельным компонентам.

### 4. Кроссплатформенность

Обязательно сохранить корректное поведение:

- Android web: новый native-first app-promo flow;
- iPhone / iOS web: текущий PWA guide;
- native iOS / native Android: никаких web install surface;
- desktop web: без агрессивного app-promo поведения, если отдельного решения не требуется.

## Что не нужно делать

В рамках этой задачи не нужно:

- сохранять Android PWA install flow как активный сценарий;
- делать принудительный redirect в приложение;
- ломать web billing flow;
- подменять обычную web-навигацию app-open логикой;
- смешивать Android app-promo flow с будущим iOS Smart App Banner;
- удалять существующий iOS PWA guide;
- внедрять UI, который блокирует пользование сайтом до выбора приложения или веба.

## Критерии приемки

Задача считается выполненной, если одновременно соблюдены все условия ниже:

1. На Android PWA install banner и Android PWA guide больше не показываются.
2. На Android вместо PWA используется новый app-promo flow для нативного приложения.
3. Если installed Android app определяется поддерживаемым способом, пользователь получает ненавязчивый CTA `Открыть приложение`.
4. Если приложение не установлено, пользователь получает CTA перехода в Google Play.
5. Нигде нет автоматического принудительного редиректа в приложение только по факту открытия сайта.
6. Пользователь может продолжить использовать web-версию даже при установленном приложении.
7. Web billing flow не ломается и не перехватывается app-promo логикой.
8. На `/subscription`, `/payment-success` и `/auth/external-session/consume` web-сценарий остаётся приоритетным.
9. На iPhone / iOS текущий PWA guide продолжает работать.
10. Решение о показе install/app-promo UI централизовано в одной frontend policy-точке.

## Зависимости

Для реализации потребуется учесть:

- доработку web manifest;
- корректную конфигурацию `assetlinks.json`;
- поддержку `Navigator.getInstalledRelatedApps()` там, где она доступна;
- fallback на браузеры без поддержки API;
- возможные требования к native Android app для корректного `open app` flow;
- существующий web billing flow проекта.

## Продуктовые допущения

- Android native app уже опубликовано в Google Play.
- Package name остаётся `com.mentala.app`.
- iOS native app пока не опубликовано.
- Web остаётся обязательным каналом, в том числе для платежных сценариев.
- Android app-promo flow должен быть `native-first`, но не `force-open`.

## Источники для проектирования

При реализации нужно опираться на официальные материалы:

- web.dev по `related_applications`, `prefer_related_applications` и `Navigator.getInstalledRelatedApps()`;
- Chrome Developers по Get Installed Related Apps API;
- Android Developers по Google Play linking и Android App Links / Digital Asset Links;
- Apple documentation по Smart App Banner как отдельному будущему iOS-сценарию.
