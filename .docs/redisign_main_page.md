# Техническое задание - редизайн главной страницы и внедрение итогов сессии

## 1. Цель задачи

Перестроить текущую главную страницу приложения так, чтобы она отражала не только сценарий общения с ИИ-чатом, но и другие ключевые функции продукта.

Дополнительно внедрить механизм итогов сессии, который будет формироваться только после содержательных пользовательских сессий по четким условиям, без ложных срабатываний при обычной навигации внутри приложения.

---

## 2. Изменения в навигации

### 2.1. Переименование вкладки

Текущую вкладку `Чат` в нижней навигации переименовать в `Главное`.

### 2.2. Скрытие вкладки практик

На данном этапе страницу `Практики` не удалять.

Необходимо:

- скрыть кнопку `Практики` в нижней навигации;
- сохранить существующий route страницы;
- сохранить весь существующий функционал страницы;
- не удалять компоненты, данные и связанную бизнес-логику.

Фактически страница остается в проекте, но временно исключается из нижней навигации.

## 3. Изменения в верхней части главной страницы

### 3.1. Замена текущего заголовка

На текущей главной странице заменить верхний блок, где сейчас отображаются:

- эмодзи сердечек;
- текст `Ассистент`.

Необходимо:

- убрать эмодзи сердечек;
- заменить текст `Ассистент` на брендовый вариант названия продукта;
- использовать готовый логотип Mentala, если он уже присутствует в проекте.

### 3.2. Правило по брендингу

Предпочтительный вариант:

- использовать готовый логотип, в котором слева расположен знак, а справа текст.

Если в проекте уже есть готовый брендовый компонент или готовый ассет логотипа, необходимо использовать именно его, без создания нового временного решения.

### 3.3. Написание названия

Для текущей реализации использовать название `Mentala` на латинице, если язык en, если ru, то `Ментала`.

## 4. Новая структура главной страницы

### 4.1. Общий принцип

Главная страница должна стать входной точкой в основные сценарии приложения.

### 4.2. Верхний основной блок

В верхней части главной страницы разместить основной блок, связанный с ИИ-чатом.

Требования:

- блок должен располагаться первым;
- блок должен занимать всю ширину доступного контента;
- блок должен быть визуально крупнее остальных блоков;
- в блоке должен оставаться основной вход в чат.

### 4.3. Остальные блоки

Ниже верхнего блока разместить 4 блока, которые сейчас находятся на странице `Практики`:

- Быстрая помощь
- Медитации
- Дыхательные практики
- Дневник благодарности

Требования:

- на данном этапе названия блоков не менять;
- тексты и смысловую структуру пока оставить как есть;
- блоки должны быть меньше верхнего блока;
- сетка размещения: 2 блока в ряд, всего 2 ряда;
- визуально это должна быть компоновка `2 на 2`.

### 4.4. Правило по переносу

На данном этапе используется прямой перенос существующего функционала страницы `Практики` на главную страницу.

То есть:

- карточки и переходы должны сохранить текущее поведение;
- бизнес-логика существующих разделов не должна быть сломана;
- перенос касается именно входных блоков и пользовательского сценария с главной страницы.

## 5. Блок ИИ-чата на главной странице

### 5.1. Что должно быть внутри

В верхнем широком блоке ИИ-чата необходимо предусмотреть:

- основной заголовок блока;
- описание блока;
- кнопку входа в чат;
- кнопку перехода в раздел `Итоги сессии`.

### 5.2. Кнопка перехода в итоги

Внутри верхнего блока должна быть отдельная кнопка `Итоги сессии`.

По нажатию пользователь должен переходить на отдельную страницу со списком сформированных итогов прошлых сессий.

## 6. Новая страница `Итоги сессии`

### 6.1. Название страницы

Название страницы: `Итоги сессии`.

### 6.2. Назначение страницы

Страница должна содержать историю итогов завершенных сессий пользователя.

Это не экран мгновенного одноразового результата, а полноценный раздел, в котором можно просматривать ранее сформированные итоги.

### 6.3. Что должно быть на странице

На странице должен быть список завершенных сессий с возможностью открыть каждую запись отдельно.

Для каждой сессии в деталях необходимо отображать структурированный итог в читабельном виде.

Базовая структура вывода:

-     О чем была эта сессия;
- что было важным;
- рекомендации;
- следующий шаг.

Точный визуальный дизайн в рамках данного задания детально не фиксируется, но вывод должен быть:

- понятным;
- аккуратным;
- хорошо читаемым;
- структурированным.

---

## 7. Логика определения завершенной сессии

### 7.1. Основной принцип

Итог сессии должен формироваться не после каждого диалога, а только после действительно содержательной пользовательской сессии.

### 7.2. Обязательные условия формирования итогов

Запрос на суммаризацию можно отправлять только если одновременно выполнены все 3 условия:

1. Пользователь отправил не менее 5 сообщений.
2. Продолжительность сессии составляет более 4 минут.
3. Выполнен порог по содержательности сообщений пользователя.

### 7.3. Правило по содержательности сообщений

Нужно внедрить дополнительную проверку, чтобы короткие реплики не считались полноценной сессией.

Для первой реализации принять следующее правило:

- считать сообщение содержательным, если длина текста составляет не менее 80 символов без учета пробелов;
- условие по содержательности считается выполненным, если в рамках текущей сессии есть не менее 3 сообщений пользователя, удовлетворяющих этому порогу.

Причина выбора:

- порог в 80 символов без пробелов отсеивает односложные ответы и короткие реплики;
- требование минимум 3 содержательных сообщений снижает вероятность ложной суммаризации.

### 7.4. Что считать началом сессии

Началом сессии считать отправку первого пользовательского сообщения в рамках текущего живого состояния чата.

### 7.5. Что считать длительностью сессии

Длительность сессии считать как разницу между временем первого пользовательского сообщения и моментом завершения сессии.

---

## 8. Когда можно запускать суммаризацию

### 8.1. Разрешенные триггеры

Суммаризация может запускаться только в следующих сценариях:

1. Пользователь нажал кнопку `Завершить сессию`.
2. Происходит очистка текущего chat store, и перед этой очисткой система проверяет условия и при необходимости запускает суммаризацию.

### 8.2. Запрещенные триггеры

Суммаризация не должна запускаться:

- при обычном переходе между страницами приложения;
- при переходе из чата в медитации, дыхательные практики и другие разделы через чипсы или иные элементы навигации;
- при временном уходе пользователя на другую страницу, если текущее состояние чата еще сохранено в store;
- при незавершенной сессии, когда пользователь потенциально собирается вернуться в тот же диалог.

Ключевой принцип:

- простой переход по приложению не равен завершению сессии.

---

## 9. Логика работы через store

### 9.1. Текущее ограничение

Состояние текущего разговора хранится временно в store.

### 9.2. Требуемое поведение

Перед любой фактической очисткой store, связанного с текущей сессией чата, необходимо:

1. проверить, есть ли в store данные текущей сессии;
2. проверить выполнение всех 3 условий суммаризации;
3. если условия выполнены, отправить запрос на суммаризацию;
4. только после этого завершать очистку текущего состояния.

### 9.3. Важное правило

Если store не очищается, то и суммаризация запускаться не должна, кроме сценария явного принудительного завершения через кнопку `Завершить сессию`.

### 9.4. Требование к реализации

Нужно централизовать логику завершения сессии, чтобы не дублировать проверки по разным компонентам.

Желательно реализовать единый сценарий уровня store или отдельного composable или service, например:

- проверка eligibility для итогов;
- запуск суммаризации;
- сохранение результата;
- безопасная очистка текущей сессии.

## 10. Кнопка `Завершить сессию`

### 10.1. Расположение

Разместить кнопку `Завершить сессию` в верхней части интерфейса чата.

### 10.2. Правило видимости или активности

Кнопка должна быть доступна пользователю только тогда, когда одновременно выполнены все 3 условия суммаризации:

- не менее 5 сообщений пользователя;
- длительность сессии более 4 минут;
- не менее 3 содержательных сообщений пользователя длиной от 80 символов без пробелов.

### 10.3. Поведение по нажатию

По нажатию на кнопку необходимо:

1. завершить текущую сессию;
2. запустить запрос на суммаризацию;
3. сохранить итог сессии;
4. очистить текущее живое состояние разговора;
5. показать пользователю результат в предсказуемом сценарии.

### 10.4. Вариант пользовательского сценария после завершения

Оставлять пользователя на главной странице, но показывать подтверждение и давать быстрый переход в `Итоги сессии`.

---

## 11. Хранение итогов сессий

### 11.1. Что нужно сохранять

Для каждой завершенной сессии необходимо сохранять как минимум:

- уникальный идентификатор сессии;
- дату и время завершения;
- длительность сессии;
- количество пользовательских сообщений;
- итог, сформированный моделью;
- структурированные блоки результата;
- технический статус генерации.

### 11.2. Минимальная структура данных

Ориентировочная структура сущности:

```ts
interface SessionSummary {
  id: string;
  createdAt: string;
  sessionStartedAt: string;
  sessionEndedAt: string;
  durationSeconds: number;
  userMessagesCount: number;
  qualifyingUserMessagesCount: number;
  summary: {
    shortSummary: string;
    keyPoints: string[];
    recommendations: string[];
    nextStep: string;
  };
  status: 'pending' | 'completed' | 'failed';
}
```

Структура может быть адаптирована под фактическую архитектуру проекта.

---

## 12. Требования к формату итогов сессии

### 12.1. Цель формата

Формат должен быть кратким, полезным и легко читаемым. Нельзя превращать итог в длинный сплошной аналитический текст.

### 12.2. Обязательная структура ответа модели

Модель должна возвращать результат в следующем логическом формате:

1. `shortSummary` - краткий итог сессии в 2-3 предложениях.
2. `keyPoints` - список из 2-4 ключевых наблюдений или важных моментов.
3. `recommendations` - список из 1-3 рекомендаций на сейчас.
4. `nextStep` - один понятный следующий шаг.

### 12.3. Ограничения по качеству ответа

Нельзя:

- ставить диагнозы;
- использовать категоричные клинические формулировки;
- придумывать факты, которых не было в диалоге;
- повторять весь разговор почти дословно;
- давать чрезмерно длинные рекомендации;
- перегружать итог большим количеством пунктов.

## 13. Промпт для модели ChatGPT для формирования итогов сессии

Ниже приведен базовый промпт, который должен использоваться как основа для серверной или клиентской интеграции, в зависимости от текущей архитектуры проекта.

### 13.1. System prompt

```text
Ты анализируешь завершенную пользовательскую сессию в приложении эмоциональной поддержки.

Твоя задача - сформировать краткие, аккуратные и полезные итоги сессии на русском языке.

Правила:
1. Пиши только на русском языке.
2. Не ставь диагнозы и не используй медицинские или психиатрические ярлыки.
3. Не придумывай факты, которых не было в сообщениях пользователя.
4. Не оценивай пользователя осуждающе.
5. Не используй слишком общие фразы без опоры на содержание диалога.
6. Пиши кратко, понятно и тепло, но без лишней сентиментальности.
7. Не пересказывай весь диалог. Нужна только суть.
8. Рекомендации должны быть мягкими, реалистичными и безопасными.
9. Не давай опасных советов.
10. Если данных недостаточно для уверенного вывода, отрази это аккуратно и не выдумывай детали.

Верни результат строго в JSON формате по следующей схеме:
{
  "shortSummary": "string",
  "keyPoints": ["string"],
  "recommendations": ["string"],
  "nextStep": "string"
}

Требования к содержимому:
- shortSummary: 2-3 предложения.
- keyPoints: от 2 до 4 пунктов.
- recommendations: от 1 до 3 пунктов.
- nextStep: одно короткое и понятное действие.
```

### 13.2. User prompt template

```text
Ниже передана завершенная сессия пользователя.

Проанализируй только фактическое содержание диалога и верни краткий структурированный итог.

Данные сессии:
- Длительность сессии: {{duration}}
- Количество сообщений пользователя: {{userMessagesCount}}
- Количество содержательных сообщений пользователя: {{qualifyingUserMessagesCount}}

Сообщения:
{{messages}}
```

### 13.3. Требование к интеграции

Если в проекте уже существует инфраструктура промптов, этот промпт необходимо встроить в существующий паттерн, а не реализовывать отдельным хаотичным способом.

## 14. Пользовательские сценарии

### 14.1. Сценарий обычной навигации

1. Пользователь общается в чате.
2. Нажимает на чипс или переходит в другой раздел.
3. Store сессии не очищается.
4. Суммаризация не запускается.
5. Пользователь возвращается и продолжает диалог.

### 14.2. Сценарий ручного завершения

1. Пользователь ведет содержательную сессию.
2. Выполняются все 3 условия.
3. Кнопка `Завершить сессию` становится доступной.
4. Пользователь нажимает кнопку.
5. Система формирует итог.
6. Итог сохраняется.
7. Пользователь попадает в `Итоги сессии` или на экран конкретного итога.

### 14.3. Сценарий закрытия приложения

1. Пользователь вел содержательный диалог.
2. Приложение сворачивается или закрывается.
3. Перед очисткой store система проверяет eligibility.
4. Если все условия выполнены, запускается суммаризация.
5. Результат сохраняется.
6. При следующем открытии пользователь видит сохраненный итог в разделе `Итоги сессии`.

---

## 15. Требования к разработке

### 15.1. Нельзя ломать текущие сценарии

Изменения не должны ломать:

- существующий сценарий входа в чат;
- переходы в медитации, дыхательные практики, дневник благодарности и быструю помощь;
- текущую store-логику вне части, которую нужно централизованно доработать.

### 15.2. Минимизировать дублирование логики

Проверки eligibility для итогов сессии должны быть реализованы централизованно и переиспользуемо.

### 15.3. Подготовка к масштабированию

Новая главная страница должна быть собрана так, чтобы в будущем можно было:

- менять порядок блоков;
- добавлять новые блоки;
- возвращать отдельную страницу `Практики`, если потребуется.

---

## 16. Критерии приемки

Задача считается выполненной, если:

1. В нижней навигации вкладка `Чат` переименована в `Главное`.
2. Кнопка `Практики` скрыта из нижней навигации.
3. Сама страница `Практики` и ее route сохранены.
4. На главной странице сверху расположен широкий блок ИИ-чата.
5. Под ним отображаются 4 блока из `Практик` в сетке `2 на 2`.
6. В верхнем хедере вместо сердечек и слова `Ассистент` отображается брендовый логотип `Mentala`.
7. В блоке ИИ-чата есть кнопка `Итоги сессии`.
8. Реализована отдельная страница `Итоги сессии`.
9. Итог сессии формируется только если одновременно выполнены все 3 условия:
   - не менее 5 сообщений пользователя;
   - длительность сессии более 4 минут;
   - не менее 3 содержательных сообщений пользователя длиной от 80 символов без пробелов.
10. Суммаризация не запускается при обычной навигации между страницами.
11. Суммаризация запускается при ручном завершении сессии и при закрытии или сворачивании приложения перед очисткой состояния.
12. Кнопка `Завершить сессию` недоступна до выполнения всех условий.
13. Итоги сохраняются и отображаются на странице `Итоги сессии` в структурированном виде.
14. Для генерации итогов используется промпт со строгим структурированным JSON ответом.

## 17. Рекомендации по реализации

### 17.1. Архитектурно

Рекомендуется выделить:

- отдельный composable или service для завершения сессии;
- отдельную функцию проверки eligibility итогов;
- отдельную сущность хранения итогов сессии.

### 17.2. Технически

Рекомендуется предусмотреть:

- защиту от повторной отправки суммаризации для одной и той же сессии;
- статус `pending` на время генерации;
- fallback на случай ошибки генерации;
- журналирование ошибок суммаризации.

### 17.3. Для будущих итераций

В следующих этапах можно отдельно проработать:

- переименование карточек через пользу, а не через названия инструментов;
- рекомендации на главной странице на основе последних итогов;
- отдельный экран конкретного итога сессии;
- улучшение критериев определения содержательной сессии.
