Release Strategy и совместимость версий (Mentala)

Проблема

Приложение Mentala использует единый бэкенд и три канала доставки:
• веб (обновляется мгновенно);
• iOS (обновляется через App Store с задержкой);
• Android (обновляется через Google Play с задержкой).

При деплое сервера и веба новые изменения применяются сразу, а мобильные клиенты могут оставаться на старых версиях.
Это приводит к рискам:
• несовместимость API;
• падения клиентов;
• некорректная работа платежей, пушей, навигации;
• ошибки из-за изменений в базе данных.

⸻

Цель

Обеспечить стабильную работу приложения при рассинхронизации версий:
• новый сервер совместим со старыми клиентами;
• новые клиенты совместимы со старым сервером;
• изменения выкатываются безопасно и поэтапно.

⸻

Основные принципы

1. Backward compatibility (обязательное правило)

Сервер не должен ломать старые версии клиентов:
• не удалять поля из API;
• не менять типы данных;
• не делать новые поля обязательными;
• добавлять поля, а не заменять;
• сохранять старые endpoint до завершения миграции.

⸻

2. Версионирование клиентов

Каждый запрос должен содержать:
• x-app-platform: ios | android | web
• x-app-version: 1.0.0
• x-app-build: 100

Сервер использует эти данные для:
• условной логики;
• отката форматов;
• диагностики ошибок.

⸻

3. Feature flags

Новые функции включаются через сервер:
• сначала код выкатывается выключенным;
• затем включается для тестовых пользователей;
• затем для части прод-аудитории;
• затем полностью.

Не использовать “жесткие” релизы для логики.

⸻

4. Двухфазные миграции базы данных

Запрещено делать breaking изменения сразу.

Правильный порядок: 1. Добавить новое поле или таблицу; 2. Поддерживать старую и новую схему; 3. Выпустить клиент с новой логикой; 4. Удалить старую схему позже.

⸻

5. Минимальная и рекомендуемая версия

Сервер возвращает:
• minimumSupportedVersion
• recommendedVersion

Поведение клиента:
• если версия ниже minimum → блокировка и требование обновления;
• если ниже recommended → мягкое предложение обновиться.

⸻

6. Разделение типов изменений

Тип A - безопасные (без mobile обновления)
• тексты;
• конфиги;
• feature flags;
• серверная логика;
• контент.

Тип B - frontend изменения
• UI;
• новые страницы;
• клиентская логика.

Требует mobile релиза, если используется Capacitor bundle.

Тип C - нативные изменения
• плагины;
• push;
• платежи;
• permissions.

Всегда требует новый билд и публикацию.

⸻

7. Процесс релиза
   1. Деплой сервера (с поддержкой старых клиентов)
   2. Деплой веба
   3. Сборка мобильных приложений:
      • npm run build
      • npx cap sync
   4. Тестирование:
      • TestFlight
      • Android Internal Testing
   5. Публикация в сторы
   6. Включение фич через feature flags

⸻

8. Безопасность env для mobile

В мобильный билд разрешено включать только:
• публичные URL;
• не секретные параметры.

Запрещено:
• API ключи;
• приватные ключи;
• платежные секреты;
• Firebase Admin;
• любые server-side credentials.

⸻

9. Обновления клиентов

iOS
• проверка минимальной версии через API;
• редирект в App Store при необходимости.

Android
• использовать In-App Updates:
• мягкий режим;
• обязательный режим для критичных обновлений.

⸻

Итог

Система должна быть устойчива к рассинхронизации:
• сервер всегда backward-compatible;
• мобильные клиенты обновляются независимо;
• критичные изменения контролируются через версии и фичефлаги;
• база данных изменяется безопасно;
• релизы проходят поэтапно.

Главный принцип:

не синхронизация релизов, а устойчивость к их рассинхронизации.
