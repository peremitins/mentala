# Техническое задание: Генерация смешанных push-уведомлений одним запросом к модели

**Проект:** Mentala  
**Версия:** 1.0  
**Статус:** Final перед релизом  
**Дата:** 2026-02-03  

---

## 1. Проблема

В системе есть настройка **фокус уведомлений** (NotificationSubtype):

- `reminder` - напоминания  
- `informational` - факты  
- `motivational` - поддержка  
- `mixed` - смешанные

Для каждого из трех конкретных фокусов используются разные промпты, так как они различаются по структуре и смыслу.

Сейчас генерация выполняется пачкой (например, 50 текстов). Если пользователь выбирает `mixed`, требуется получить **контролируемую смесь** трех типов сообщений, сохранив:

- качество текстов, как у специализированных промптов;
- предсказуемые пропорции (квоты) типов;
- минимальную стоимость и минимальную задержку.

---

## 2. Цель

Реализовать генерацию режима `mixed` **одним запросом к модели** вместо трех отдельных запросов, при этом:

- модель возвращает массив объектов, где для каждого элемента указан `subtype`;
- соблюдаются заданные квоты по количеству объектов каждого `subtype`;
- формат ответа валидируется строгой JSON Schema;
- логика выбора `imageTag` согласована с правилами безопасности изображений.

---

## 3. Выбранный подход

### 3.1 Решение

Использовать **один запрос** к модели для `subtype = mixed`, в котором:

1. Модели явно задаются квоты по типам сообщений (например, 16-17-17 на 50 штук).
2. Модель возвращает единый массив объектов.
3. Каждый объект содержит:
   - `subtype` (обязателен только в режиме mixed)
   - `text`
   - `imageTag` (как в ТЗ по изображениям)

### 3.2 Почему один запрос лучше трех

- Ниже стоимость: контекст, правила, схема и инструкции отправляются один раз, а не три.
- Ниже задержка: один вызов вместо трех.
- Меньше точек отказа: один парсинг, одна валидация, одна попытка ретрая.

---

## 4. Контракт ответа модели

### 4.1 Контекст генерации (в запросе, не в ответе)

Контекстные поля уже существуют в системе и передаются в запрос, например:

- `kind`: `habits` | `therapy`
- `entityKey`: string | null
- `directness`: `soft` | `moderate` | `hard`
- `habitIntent`: `build` | `quit` | `custom` | null
- `gender`: `male` | `female` | null (если используется)
- `subtype`: `mixed` (режим этого ТЗ)

### 4.2 Формат одного элемента массива (режим mixed)

```json
{
  "subtype": "informational",
  "text": "Алкоголь нарушает структуру сна и снижает качество восстановления.",
  "imageTag": "harm_mental"
}
```

### 4.3 Поля объекта

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| subtype | enum | да | Тип сообщения: `reminder` | `informational` | `motivational` |
| text | string | да | Текст уведомления |
| imageTag | enum | да | Семантический тег изображения из финального набора |

---

## 5. Квоты (пропорции) для mixed

### 5.1 Базовый вариант на 50 элементов (рекомендовано)

- `reminder`: 16
- `informational`: 17
- `motivational`: 17

Итого: 50.

### 5.2 Вариант на 60 элементов (опционально)

- `reminder`: 20
- `informational`: 20
- `motivational`: 20

Итого: 60.

### 5.3 Замечание по продуктовой логике

Квоты являются параметром системы и могут быть изменены в будущем. На старте используется базовый вариант на 50 элементов.

---

## 6. Правила генерации для каждого subtype (минимальная спецификация)

### 6.1 reminder

- цель: побудить к действию или напомнить
- коротко, конкретно, без фактологии и без страшилок
- допустимы микро-действия (вода, прогулка, пауза, дыхание)
- запрет на медицинские утверждения

### 6.2 informational

- цель: факт, причинно-следственная связь, полезное наблюдение
- нейтральная подача, без морализации
- последствия допускаются в рамках `directness`
- запрет на диагнозы, лечение, лекарства

### 6.3 motivational

- цель: поддержка, мотивация, снижение стыда, укрепление намерения
- эмпатия, без давления
- не использовать запугивание и жесткие последствия

---

## 7. Связка с изображениями (imageTag) и правила безопасности

### 7.1 Финальный набор imageTag (фиксировано)

Вред:

- `harm_organs`
- `harm_appearance`
- `harm_mental`

Позитивные и нейтральные:

- `activity`
- `nature`
- `meditation`
- `daily_life`

Опциональный:

- `neutral_abstract`

### 7.2 Правила запретов harm_* (кратко, как в ТЗ по изображениям)

- Если `kind = therapy`, запрещены все `harm_*`.
- Если `subtype = reminder` или `subtype = motivational`, запрещены все `harm_*`.
- Если `directness = soft`, запрещены все `harm_*`.
- Если `habitIntent = build` или `habitIntent = custom`, запрещены все `harm_*`.
- `harm_organs` разрешен только при:
  - `kind = habits`
  - `habitIntent = quit`
  - `subtype = informational`
  - `directness = hard`
- `harm_appearance` и `harm_mental` разрешены только при:
  - `kind = habits`
  - `habitIntent = quit`
  - `subtype = informational`
  - `directness = moderate` или `hard`

### 7.3 Поведение при конфликте

Если модель вернула запрещенный `imageTag`, система обязана:

1. заменить `imageTag` на fallback тег (`nature`, затем `neutral_abstract`);
2. либо отправить уведомление без изображения.

---

## 8. Реализация промпта для mixed

### 8.1 Требования к промпту

Промпт для mixed должен:

- явно указать квоты по subtype;
- описать правила для каждого subtype кратко и однозначно;
- требовать разнообразие и запрет повторов;
- требовать строгий JSON без лишних полей;
- требовать корректный `imageTag` с учетом правил запретов.

### 8.2 Рекомендуемая структура промпта

1. Общие правила (длина, стиль, запреты).
2. Таблица квот.
3. Три мини-спецификации по subtype.
4. Правила выбора `imageTag`.
5. Строгие требования к формату ответа.

---

## 9. JSON Schema (обязательная строгая валидация)

### 9.1 Общие требования

- `type: array`
- `minItems: N` и `maxItems: N` (N равно 50)
- элементы `type: object`
- `additionalProperties: false`
- `required: ["subtype", "text", "imageTag"]`
- ограничения по длине `text` (например, 1-160 символов)

### 9.2 Enum значений

- `subtype`: `reminder` | `informational` | `motivational`
- `imageTag`: финальный набор из раздела 7.1

---

## 10. Изменения в коде

### 10.1 Роутинг промптов

Добавить ветку:

- если `subtype != mixed`:
  - использовать специализированный промпт для subtype
  - ожидать массив `{ text, imageTag }`
- если `subtype = mixed`:
  - использовать mixed-промпт
  - ожидать массив `{ subtype, text, imageTag }`

### 10.2 Парсинг и обратная совместимость

- если пришел массив строк, трактовать как `{ text, imageTag: "nature" }` или `{ text, imageTag: null }` (по текущей политике проекта)
- если пришли объекты, валидировать схемой
- при ошибке валидации:
  - повторить запрос (retry) с уточняющими инструкциями
  - либо деградировать до шаблонов (если включен режим шаблонов)

### 10.3 Перемешивание результата

После успешной генерации и валидации:

- перемешать массив, чтобы subtype не шел блоками
- сохранить порядок для round-robin доставки или использовать random при выдаче

---

## 11. Критерии приемки

1. При `subtype = mixed` выполняется ровно один запрос к модели.
2. В ответе ровно 50 элементов и соблюдены квоты 16-17-17.
3. Каждый элемент содержит `subtype`, `text`, `imageTag`.
4. Нет `harm_*` в `reminder` и `motivational`.
5. Нет `harm_*` при `kind = therapy` и при `directness = soft`.
6. При конфликтном `imageTag` применяется fallback без падения процесса.
7. Формат ответа всегда проходит JSON Schema валидацию или срабатывает контролируемая деградация.

---

## 12. Примечания

- `mixed` является продуктовым режимом балансировки, поэтому должен оставаться явным выбором в интерфейсе.
- Основная сложность смешанного режима решается не тремя запросами, а строгим контрактом ответа и квотами.
- Эта реализация совместима с ТЗ по выбору изображений и тегов.
