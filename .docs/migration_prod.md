Техническое задание: стабилизация миграций базы данных и устранение 500 при регистрации на production

1. Контекст

На production окружении mentala.app регистрация по email (POST /api/auth/email/register) возвращает 500 Server Error. В логах приложения фиксируются ошибки валидации входных данных и ошибки схемы базы данных.

Также наблюдается 401 Unauthorized при запросе GET /manifest.json, что влияет на работу PWA и приводит к шуму в консоли браузера.

2. Текущие проблемы

2.1 Ошибка схемы базы данных, падение регистрации

Симптом
• POST /api/auth/email/register возвращает 500.
• Логи mentala-web-prod показывают:

column "deletion_requested_at" does not exist

Причина
• Контейнер mentala-web-prod выполняет запрос к таблице users и ожидает колонку deletion_requested_at.
• В production базе Postgres этой колонки нет.
• В базе отсутствует таблица \_\_drizzle_migrations, то есть история миграций Drizzle не ведется и, с высокой вероятностью, миграции не применяются в production деплое.

Итог
• Схема базы не синхронизирована с кодом. Любой код, который обращается к отсутствующим колонкам, падает.

⸻

2.2 Некорректный статус-код при ошибке валидации

Симптом
• При отсутствии acceptTerms: true и acceptPrivacy: true сервер возвращает 500, хотя это клиентская ошибка.

Причина
• Ошибка Zod не транслируется в 400 Bad Request, а поднимается как unhandled error.

Итог
• Клиент и мониторинг получают ложные 500, сложнее диагностировать реальные проблемы.

⸻

2.3 Basic Auth на Traefik ломает публичные ресурсы

Симптом
• GET https://mentala.app/manifest.json возвращает 401 Unauthorized.
• В браузере ошибки Manifest fetch failed.

Причина
• Basic Auth middleware Traefik применяется к запросам на manifest.json (и, вероятно, к другим статическим ресурсам), которые должны быть публичными.

Итог
• PWA функциональность деградирует, консоль засоряется, возможны проблемы установки веб-приложения.

3. Цели

   1. Гарантировать, что production база всегда соответствует версии кода в mentala-web-prod.
   2. Сделать миграции повторяемыми, контролируемыми и атомарными в рамках деплоя.
   3. Исправить обработку ошибок валидации (400 вместо 500).
   4. Обеспечить публичный доступ к manifest.json и, при необходимости, к иным статическим ресурсам PWA.

4. Лучший способ решения

4.1 Внедрить обязательный шаг миграции в процесс деплоя (критично)

Ключевое правило
• Миграции выполняются перед запуском новой версии приложения.

Точная точка входа миграций (обязательно)
• Миграции выполняются внутри Docker-контейнера migrate командой:
npm run db:migrate (скрипт вызывает drizzle-kit migrate).
• Рабочая директория: /app.
• Используемые переменные окружения: NUXT_PRIVATE_DB_URL, NODE_ENV=production.
• В production на сервере используется файл .env, примонтированный в контейнер (локально для prod-миграций используется .env.production).

Почему это важно
• Без этого dev, CI и prod могут запускать разные миграции.
• Можно случайно прогнать миграции не в ту базу.
• Невозможно воспроизвести поведение.

Рекомендуемый подход
• Отдельный job или сервис migrate в docker-compose, который запускается командой миграции и завершается.
• После успешной миграции запускается/обновляется mentala-web-prod.

Почему это лучший способ
• Устраняет человеческий фактор.
• Исключает рассинхронизацию схемы и кода.
• Позволяет откатывать релизы, понимая состояние схемы.

⸻

4.2 Гарантировать доставку миграций в production образ

Требование
• Папка с миграциями должна попадать в Docker image, который используется для миграционного job.

Риски, которые устраняются
• Ситуация, когда команда миграции запускается, но внутри контейнера нет файлов миграций, поэтому ничего не применяется.

⸻

4.3 Привести существующую production базу к режиму Drizzle миграций (критично)

Сейчас в базе нет \_\_drizzle_migrations. Нужно выбрать один корректный способ и зафиксировать его.

Выбранная стратегия baseline (обязательно)
• Baseline-миграция фиксирует текущее состояние production базы без выполнения destructive DDL.
• Baseline применяется один раз на текущем состоянии production базы.
• Миграция не изменяет существующие таблицы.
• Миграция создает таблицу \_\_drizzle_migrations.
• Миграция добавляет запись о baseline версии.
• Сравнение ожидаемой схемы и фактической выполняется вручную до baseline на основе актуальной Drizzle schema.

Почему это важно
• Автоматическое “приведение к ожидаемой схеме” может снести данные.
• Baseline — это точка отсчета, а не волшебная кнопка.

Аварийный вариант (допустим только для быстрого восстановления)
• Ручное добавление отсутствующих колонок (ALTER TABLE ... ADD COLUMN) до восстановления работоспособности.
• После аварийного восстановления все равно перейти к baseline-стратегии.

⸻

4.4 Исправить обработку ошибок валидации в register (очень важно)

POST /api/auth/email/register

Успех
Status: 201 Created
Body:
{
"userId": "number",
"email": "string"
}

Важно: breaking change
• Контракт ответа меняется (201 + { userId, email }).
• Обязать обновление фронта и тестов, чтобы не было несовместимости.

Ошибка валидации
Status: 400 Bad Request
Body:
{
"error": "validation",
"issues": [
{ "path": "acceptTerms", "message": "Must be true" }
]
}

⸻

4.5 Атомарность и идемпотентность миграций (очень важно)

Идемпотентность
• Повторный запуск миграций без изменений должен завершаться успешно без применения DDL и без ошибок.

Защита от параллельного запуска
• Перед выполнением миграций используется PostgreSQL advisory lock.
• При невозможности получить lock миграции не выполняются и job завершается с ошибкой.

⸻

4.6 Бэкапы и откат (обязательно, но кратко)

Перед запуском миграций выполняется pg_dump production базы.

Бэкап
• Тип: pg_dump.
• Выполняется перед каждым запуском миграций.
• Хранится не менее 7 дней.
• Используется для ручного отката при неуспешной миграции.

⸻

4.7 Разделить публичные и защищенные роуты в Traefik (важно, но ниже по приоритету)

Где настраивается
• Исключения для статических публичных ресурсов (PWA-статика) настраиваются на уровне Traefik middleware.

Точный список публичных путей
• /manifest.json
• /site.webmanifest
• /sw.js
• /assets/*
• /icons/*
• /favicon*
• /robots.txt
• все файлы, на которые ссылаются manifest.json и sw.js (включая иконки из корня: /android-icon-*.png, /apple-icon-*.png, /ms-icon-*.png, /web-app-manifest-*.png, /apple-touch-icon.png, /browserconfig.xml)

Важно
• Публичность этих ресурсов не предоставляет доступ к приватным API или данным пользователя.

Дополнительная проверка
• Подтвердить, что 401 Unauthorized для публичных ресурсов генерируется Traefik middleware, а не самим приложением или сервером статики.

⸻

4.8 Локальный запуск миграций и защита от ошибок окружения (обязательно)

Цель
• Разработчик должен уметь безопасно запускать миграции для dev или prod с подробным описанием, исключая случайный запуск на production при работе с dev.

Требования к запуску миграций локально
• Разрешены только явные команды с указанием окружения (dev или prod).
• Любой запуск миграций в production требует дополнительного подтверждения.

Обязательные правила безопасности
• Команда миграций должна явно принимать флаг окружения: --env=development или --env=production.
• Для production должна быть обязательная проверка “Я точно мигрирую prod”, например:
• интерактивное подтверждение (prompt) или
• требование переменной окружения MIGRATE_PROD_CONFIRM=YES.
• При несовпадении выбранного env и NUXT_PRIVATE_DB_URL команда должна завершаться с ошибкой.
• Для local prod-миграций источником NUXT_PRIVATE_DB_URL является .env.production, на сервере — .env.

Минимальная инструкция для разработчика (в ТЗ обязательно)
• Dev:
• npm run db:migrate -- --env=development
• Используется .env.development
• Prod (только при осознанной необходимости):
• MIGRATE_PROD_CONFIRM=YES npm run db:migrate -- --env=production
• Локально используется .env.production, на сервере используется .env

Почему это критично
• Ошибка запуска миграций на prod вместо dev — прямой риск инцидента.

⸻

4.9 Обязательная правка env-логики Drizzle (критично)

Проблема
• Сейчас есть расхождение между ТЗ и фактической загрузкой env в drizzle.config.ts.

Требование
• Обязательная правка конфигурации/скрипта миграций так, чтобы выбор env-файла был явным и предсказуемым.
• Запуск с --env=development должен использовать только .env.development.
• Локальный запуск с --env=production должен использовать .env.production.
• На сервере production используется .env.
• Запрещено молча подмешивать .env поверх выбранного env-файла, если это может привести к запуску не на той БД.

Почему это важно
• Иначе остаётся риск “случайно мигрировать prod” при локальной работе.

⸻

4.10 Миграции при PR и push (обязательно)

Требование
• При каждом pull request и при пуше в main выполняется проверка миграций в CI.

Минимальный набор проверок
• Проверка, что миграции применяются на чистой БД (apply migrations).
• Проверка, что повторный запуск миграций не даёт ошибок (идемпотентность).
• Проверка, что нет изменений схемы без новых миграций (сравнение schema).

Важно
• CI проверяет только тестовую БД и никогда не использует production NUXT_PRIVATE_DB_URL.
• Любые production-переменные должны быть недоступны в PR окружении.

5. План работ

Этап 1. Диагностика и фиксация текущего состояния

1. Снять структуру users на prod:
   • \d+ users
2. Определить полный список отсутствующих колонок относительно актуальной схемы Drizzle.
3. Зафиксировать текущую версию образа mentala-web-prod (тег, digest).

Этап 2. Восстановление работоспособности регистрации

1. Применить корректные миграции, добавляющие deletion_requested_at и остальные необходимые изменения.
2. Проверить регистрацию через curl с корректным payload.

Этап 3. Внедрение миграций в деплой

1. Добавить migrate job в production compose или CI/CD.
2. Обязать деплой выполнять миграции до перезапуска web контейнера.
3. Добавить логирование результата миграций.

Этап 4. Ошибки валидации

1. Обработать ZodError в register и вернуть 400.

Этап 5. Traefik и manifest.json

1. Настроить исключение для GET /manifest.json без Basic Auth.
2. Проверить загрузку PWA ресурсов в браузере без 401.

Этап 6. Локальные миграции и CI

1. Добавить безопасные команды миграций для dev/prod с обязательным подтверждением для prod.
2. Описать в README/документации процесс запуска миграций локально.
3. Включить миграционные проверки в CI для PR и push в main.

Этап 7. Env-логика Drizzle

1. Привести drizzle.config.ts и/или скрипт миграций к явному выбору env-файла (см. п. 4.9).
2. Запретить автоматическое подмешивание .env при явном выборе окружения.

Этап 8. Контракт регистрации (breaking change)

1. Обновить фронт под новый контракт регистрации (201 + { userId, email }).
2. Обновить тесты (API/интеграционные) под новый контракт.

6. Критерии приемки

   1. POST /api/auth/email/register:
      • при корректных данных возвращает 201 и тело ответа указанного формата
      • при отсутствии acceptTerms или acceptPrivacy возвращает 400 и список ошибок указанного формата
   2. В production базе:
      • присутствует \_\_drizzle_migrations
      • миграции применяются автоматически при деплое
   3. В логах migrate job видно:
      • список примененных миграций
      • текущую версию
   4. Повторный запуск миграций:
      • не применяет изменений
      • завершается успешно
   5. В логах mentala-web-prod отсутствуют ошибки вида column ... does not exist при стандартных сценариях (регистрация, логин).
   6. GET https://mentala.app/manifest.json возвращает 200 без Basic Auth.
   7. Процесс деплоя документирован: один сценарий, без ручных действий типа “зайди на сервер и добавь колонку”.
   8. Локальная команда миграций для dev/prod описана и требует явного подтверждения для prod.
   9. CI при PR и push проверяет применение миграций и идемпотентность на тестовой БД.
   10. Env-логика Drizzle соответствует ТЗ: dev использует .env.development, local prod — .env.production, сервер prod — .env.
   11. Фронт и тесты обновлены под контракт регистрации 201 + { userId, email }.

7. Риски и меры

   • Риск: миграции могут быть разрушительными (drop, rename).
   • Мера: запрет destructive миграций без explicit review, бэкап базы перед применением.
   • Риск: параллельные деплои могут запускать миграции одновременно.
   • Мера: advisory lock и одиночный job миграций.
   • Риск: случайный запуск миграций на production при локальной работе.
   • Мера: обязательный флаг окружения + подтверждение MIGRATE_PROD_CONFIRM=YES + валидация NUXT_PRIVATE_DB_URL.
   • Риск: несоответствие env-логики Drizzle приведёт к запуску миграций не на той БД.
   • Мера: явный выбор env-файла и запрет автоматического подмешивания .env.
   • Риск: breaking change регистрации сломает фронт/тесты.
   • Мера: обязательное обновление фронта и тестов до выката.

8. Scope регистрации (полезно, но вторично)

Обязательные поля регистрации:
• email: string, valid email
• password: string, min length N
• acceptTerms: boolean, must be true
• acceptPrivacy: boolean, must be true
