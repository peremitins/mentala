# ТЗ: Онбординг Mentala (Welcome Setup)

## 1. Цель

Собрать минимальные данные для персонализации Mentala **без длинного опроса** и обеспечить корректное обращение к пользователю (имя + пол) во всех AI-генерируемых текстах (ассистент, уведомления).

---

## 2. Принципы UX

- 4–6 экранов, ≤ 60 секунд.
- Дружелюбно и быстро.
- 1 экран = 1 действие.
- Прогресс-бар сверху: `Шаг X из Y`, где `Y` пересчитывается при пропуске опциональных шагов.
- Пропуск разрешён **только** там, где указано (возраст, тон).
- Кнопка «Назад» обязательна на всех шагах, кроме приветствия и финала.
- После прохождения онбординг помечается как пройденный и больше не показывается автоматически.

---

## 3. Структура онбординга (Flow)

### Экран 0 — Приветствие

- **Заголовок:** Добро пожаловать в Mentala
- **Подзаголовок:** Давайте быстро настроим приложение под вас — это займёт меньше минуты
- **Кнопка:** Начать

---

### Экран 1 — Имя

- **Вопрос:** Как к вам обращаться?
- **Поле ввода:** Имя или никнейм
- **Кнопка:** Далее

---

### Экран 2 — Пол

- **Вопрос:** Укажите ваш пол
- **Варианты (radio):**
  - Мужской
  - Женский
- **Кнопка:** Далее

**Правило:** пол обязателен (для русского языка и персонализации).

---

### Экран 3 — Возраст

- **Вопрос:** Сколько вам лет?
- **Варианты (скролл):**
  - До 30
  - 30–45
  - 45+
- **Кнопка:** Далее
- **Пропуск:** Пропустить

---

### Экран 4 — Тон общения (Tone)

- **Вопрос:** Какой тон общения вам ближе?
- **Варианты (chips/radio):**
  - Деликатный
  - Нейтральный
  - Воодушевляющий
  - Решительный
  - Требовательный
- **Кнопка:** Далее
- **Пропуск:** Пропустить

Технические значения:

```ts
const toneOptions = [
  { value: 'delicate', label: 'Деликатный' },
  { value: 'neutral', label: 'Нейтральный' },
  { value: 'uplifting', label: 'Воодушевляющий' },
  { value: 'resolute', label: 'Решительный' },
  { value: 'demanding', label: 'Требовательный' },
];
```

---

### Экран 5 — Финальный экран

- **Заголовок:** Готово, [Имя]
- **Текст:** Mentala настроена под вас. Можно начинать
- **Кнопка CTA:** Перейти в приложение

> Важно: финал без перекоса в «терапию/чат». Формулировки должны восприниматься как старт приложения в целом.

---

## 4. Данные онбординга (что сохраняем)

### Поля профиля

- `name` (string) — имя/никнейм для обращения. Хранится в таблице `users.name`.
- `gender` (enum: `male|female`) — для окончаний и обращений. Хранится в таблице `users.gender`.
- `ageRange` (enum: `under_30|30_45|45_plus|unknown`) — хранится в таблице `users.ageRange`.
- `tone` (enum: `delicate|neutral|uplifting|resolute|demanding|unknown`) — хранится в таблице `userPreferences.tone`.

---

## 5. Логика персонализации AI (ассистент + уведомления)

### 5.1. Имя

- В ассистенте и уведомлениях допускается обращение по имени: «Ник, …».
- Если имя пустое/не задано: генерировать текст без обращения по имени.

### 5.2. Пол и грамматика (обязательно)

- При известном поле: использовать корректные родовые формы (сделал/сделала и т.п.).
- Пол обязателен в онбординге, но **на всякий случай**: если поле недоступно/невалидно в момент генерации — включать нейтральный режим (без рода).

**Строго запрещено** в любых текстах:

- `сделал(а)`, `готов(а)`, `уверен(а)` и любые окончания в скобках.

**Требование к генератору:**

- Если `gender` отсутствует/невалиден → использовать только нейтральные конструкции без рода.

### 5.3. Тон (tone)

`tone` применяется:

- в System Prompt ассистента,
- в промптах генерации уведомлений,
- в выборе вариантов статических шаблонов (если они есть).

---

## 6. Настройки: изменение данных онбординга

### Требование

В настройках должны быть редактируемые поля:

- **Имя (name)** — редактируемое поле
- **Пол (gender)** — выбор из вариантов (мужской/женский)
- **Тон (tone)** — уже существует в настройках

Изменения:

- применяются сразу для ассистента и уведомлений,
- сохраняются в БД (name и gender в `users`, tone в `userPreferences`).

---

## 7. Авторизация через Google/Apple: приоритет имени

### Проблема

OAuth может возвращать имя пользователя (например, `providerName`), но пользователь может указать своё имя в онбординге.

### Правило

Если пользователь прошёл онбординг и ввёл имя, **в БД сохраняется имя из онбординга** и оно имеет приоритет над OAuth именем.
Имя из онбординга **всегда перезаписывает** уже заполненное `users.name` (даже если оно пришло из OAuth).

### Приоритет источников имени

1. Имя, изменённое пользователем в настройках
2. Имя из онбординга (`welcome_setup`)
3. Имя из OAuth provider (Google/Apple), если 1–2 отсутствуют

### Ограничение

При повторной авторизации через OAuth **нельзя** перезаписывать `name` в таблице `users`, если он был задан пользователем (через онбординг/настройки). Имя из онбординга имеет приоритет и сохраняется в поле `users.name`.

## 8. Запуск онбординга и статус прохождения

### 8.1. Когда показываем

- Онбординг запускается **сразу после регистрации** (после создания аккаунта любым способом: OAuth, email/password).
- После успешного завершения: помечается как пройденный, повторно не показывается.

### 8.2. Упрощенная система онбордингов

Архитектура поддерживает несколько онбордингов через простой объект `onboarding` в API пользователя.

#### API пользователя

В эндпоинте `GET /api/user/me` добавляется объект `onboarding`:

```typescript
{
  // ... другие поля пользователя
  onboarding: {
    welcome: boolean, // true если онбординг welcome_setup пройден, false если нет
    // В будущем можно добавить другие онбординги:
    // feature_intro: boolean,
    // safety: boolean,
    // и т.д.
  }
}
```

#### Логика работы

1. **При первом входе** (новый пользователь):

   - `onboarding.welcome = false` или объект `onboarding` отсутствует/пустой
   - Показываем онбординг `welcome_setup`

2. **После завершения онбординга**:

   - Отправляется запрос `POST /api/user/onboarding/complete` с телом:
     ```json
     {
       "flow": "welcome_setup",
       "data": {
         "name": "Имя пользователя",
         "gender": "male",
         "ageRange": "30_45",
         "tone": "neutral"
       }
     }
     ```
   - Сервер сохраняет данные в БД:
     - `name`, `gender`, `ageRange` → в таблицу `users`
     - `tone` → в таблицу `userPreferences`
   - Обновляется `onboarding.welcome = true` в ответе API

3. **При последующих входах**:
   - Если `onboarding.welcome === true` → онбординг не показывается
   - Если `onboarding.welcome === false` или отсутствует → показываем онбординг

#### Минимальные API

- `GET /api/user/me` — возвращает объект `onboarding` с текущим статусом
- `POST /api/user/onboarding/complete` — завершает онбординг и обновляет данные пользователя

## 9. Валидации

- Имя:
  - trim
  - min 1 символ (после trim)
  - max 40 символов
- Пол:
  - обязателен
- Возраст:
  - может быть `unknown` при пропуске
- Тон:
  - может быть `unknown` при пропуске

---

## 10. Acceptance Criteria

1. После регистрации всегда запускается `welcome_setup`.
2. Пол и имя сохраняются и используются в AI-генерации (ассистент + уведомления).
3. В текстах **никогда** не встречаются формы вида `сделал(а)` и аналогичные.
4. Имя из онбординга сохраняется в БД (`users.name`) и имеет приоритет над именем из OAuth.
5. В настройках можно изменить имя, пол и тон; изменения применяются сразу.
6. Онбординг помечается как пройденный через объект `onboarding.welcome = true` в API и повторно не показывается.
7. Архитектура поддерживает добавление новых онбордингов через объект `onboarding` в API.

## 11. Замечания и уточняющие вопросы

### 11.1. Хранение данных онбординга

**Решение:**

- Сохранять данные в существующих таблицах для быстрого доступа:
  - `name`, `gender`, `ageRange` → в таблицу `users` (добавить поля `gender` и `ageRange`)
  - `tone` → в таблицу `userPreferences` (уже существует)
- Поле `displayName` не нужно — используется существующее поле `name` в таблице `users`

### 11.2. Интеграция с существующей системой

**Решение:**

- В таблице `users` есть поле `name` (varchar 120) — используется для хранения имени
- В таблице `userPreferences` есть поле `tone` — уже используется
- Нужно добавить поля: `gender` (enum: `male|female`), `ageRange` (enum: `under_30|30_45|45_plus|unknown`) в таблицу `users`

**Обработка имени:**

- Согласно разделу 7, имя из онбординга имеет приоритет и сохраняется в поле `users.name`
- Если пользователь уже имеет `name` из OAuth, но проходит онбординг — имя из онбординга **всегда** перезаписывает OAuth имя

### 11.3. Использование gender в промптах

**Замечание:** В текущих промптах (`server/application/prompts/index.ts`) используется `user_name`, но нет явного использования `gender` для родовых форм.

**Решение:**

- Добавить в системные промпты явную инструкцию о поле `gender`:
  - **Пример:** "Пользователь: [имя], пол: [male/female]. Используй корректные родовые формы (сделал/сделала) в зависимости от пола. НИКОГДА не используй формы в скобках типа сделал(а)."
- Если `gender` не указан → использовать нейтральные конструкции без рода (раздел 5.2)

### 11.4. Возрастные диапазоны

**Решение:**

- Добавлены диапазоны "До 30" (`under_30`), "30–45" (`30_45`), "45+" (`45_plus`)
- Оставить упрощённые диапазоны, более детальные не нужны

### 11.5. Запуск онбординга

**Решение:**

- "Сразу после регистрации" означает: после создания аккаунта любым способом (OAuth, email/password)
- Показывать онбординг всегда при первом входе, чтобы собрать `gender` и `tone`, даже если имя уже есть из OAuth

### 11.6. Настройки: изменение данных

**Решение:**

- Добавить возможность изменения всех полей онбординга в настройках:
  - Имя (`name`) — сделать редактируемым (сейчас уже есть в настройках)
  - Пол (`gender`) — добавить выбор из вариантов
  - Тон (`tone`) — уже есть в настройках
- Сохранять историю изменений не нужно

### 11.7. API онбординга

**Решение:**

- Упрощенная реализация:
  - `GET /api/user/me` — возвращает объект `onboarding: { welcome: boolean }`
  - `POST /api/user/onboarding/complete` — завершает онбординг и обновляет данные пользователя
- Промежуточное сохранение прогресса не требуется — онбординг проходит за один раз
- Кнопка "Назад" для возврата к предыдущему шагу — обязательна

### 11.8. Валидация и обработка ошибок

**Решение:**

- Если пользователь закрыл онбординг на середине — при следующем входе онбординг показывается снова (так как `onboarding.welcome` останется `false`)
- Валидация на стороне клиента и сервера обязательна

### 11.9. Интеграция с AI-генерацией

**Замечание:** В текущем коде генерации уведомлений (`server/application/notifications/ai-generation.service.ts`) используется `tone` из `userPreferences`, но нет использования `gender` и `displayName`.

**Решение:**

- Передавать `gender` и `name` в промпты генерации уведомлений (согласно разделу 5)
- В промпты ассистента:
  - Используется `user_name` в `buildChatPrelude` и `buildWelcomePrompt` — оставить как есть
  - Добавить `user_gender` в параметры промптов для корректных родовых форм

### 11.10. Архитектура онбордингов

**Вопрос:** Нужна ли возможность показывать несколько онбордингов последовательно?

- **Рекомендация:** Да, архитектура должна поддерживать очередь онбордингов

**Вопрос:** Как определять, какой онбординг показывать следующим?

- **Вариант:** По приоритету или по условиям (например, после первого использования функции)
