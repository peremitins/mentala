# ТЗ: Деплой лендинга как статики

Версия: 1.0  
Дата: 17 февраля 2026  
Статус: черновик (перед реализацией)

## 1. Цель

Разворачивать лендинг Mentala (`apps/landing`) как **статический сайт**: предрендеренный HTML + JS/CSS, без отдельного Node-сервера для лендинга. Домен лендинга — `mentala.app` (и при необходимости dev-домен для лендинга).

## 2. SEO при статическом экспорте

**Вопрос:** будет ли в HTML только один `div` или контент полный?

**Ответ:** при использовании `nuxt generate` (статический экспорт) Nuxt **предрендеривает** все маршруты в момент сборки. В итоге:

- Для каждой страницы (в нашем случае одна — `/`) генерируется **полноценный HTML-документ**.
- В теле документа — **весь видимый контент**: заголовки, текст, секции, разметка, как при SSR.
- В `<head>` попадают актуальные теги: `<title>`, `<meta name="description">`, Open Graph, canonical и т.д.
- Поисковики получают тот же полноценный HTML, что и при серверном рендере; не пустой shell с одним `<div id="app">`.

**Итог:** SEO при статике работает на том же уровне, что и при SSR: полная разметка, индексация контента, мета-теги. Для одностраничного лендинга с фиксированным контентом статический экспорт даёт максимально адаптивный под SEO результат.

## 3. Ограничения и допущения

- Лендинг остаётся одностраничным (одна страница `/`). Динамические маршруты не требуются.
- Конфиг (режим pre/post release, CTA URL) по-прежнему запрашивается в рантайме с бэкенда (`GET /api/landing/config`), т.е. с `my.mentala.app` / `dev.mentala.app`. Статика только подставляет в HTML/JS правильный `landingApiBase` на этапе сборки.
- Форма лидов отправляется на API основного приложения (`POST /api/landing/lead`). CORS и `ALLOWED_ORIGINS` уже учитывают `https://mentala.app` (при необходимости добавить без www — см. ранее анализ).
- Юридические ссылки ведут на `https://my.mentala.app/legal/*` — без изменений.
- Аналитика (Яндекс.Метрика) работает на клиенте; ID счётчика задаётся через env на этапе сборки (`NUXT_PUBLIC_YANDEX_METRIKA_ID`).

## 4. Технический подход

### 4.1 Сборка

- Использовать **статический экспорт** Nuxt: `nuxt generate` для приложения `apps/landing`.
- Команда из корня репозитория: `pnpm landing:generate` (добавить в `package.json`), реализация — вызов `nuxt generate apps/landing` (или эквивалент для Nuxt 4).
- Результат сборки — статические файлы (HTML, JS, CSS, ассеты). Путь вывода — по документации Nuxt/Nitro для generate (например, `apps/landing/.output/public` или общий `.output/public` при запуске из корня — уточнить при реализации).

### 4.2 Конфигурация Nuxt для статики

- В `apps/landing/nuxt.config.ts`:
  - Включить/настроить prerender (Nitro) так, чтобы маршрут `/` (и при необходимости другие будущие страницы лендинга) попадали в статический экспорт.
  - Убедиться, что нет зависимостей от серверных роутов Nitro внутри лендинга (API лендинга живёт в основном приложении).
- Переменные окружения на **момент сборки** (build-time):
  - `NUXT_PUBLIC_API_SERVER_URL` — базовый URL API (например, `https://my.mentala.app` для прод, `https://dev.mentala.app` для dev).
  - `NUXT_PUBLIC_APP_AUTH_URL`, `NUXT_PUBLIC_LANDING_SITE_URL`, `NUXT_PUBLIC_YANDEX_METRIKA_ID` — по необходимости для прод/dev сборок.

### 4.3 Хостинг статики

Выбранный вариант для продакшна: **статика + Nginx**, при этом Nginx может быть:

- либо системным Nginx на хосте (systemd),
- либо Nginx в лёгком контейнере **только для раздачи статики** (это всё равно «статика», потому что Node-сервера нет).

С учётом текущей инфраструктуры (Traefik уже выдаёт TLS и роутит домены) самый простой и надёжный путь - **Nginx-контейнер со статикой в той же proxy-сети**, а Traefik делает маршрутизацию:

- `my.mentala.app` -> приложение (Nuxt web) с basic auth
- `mentala.app` (и `www.mentala.app`, если нужен) -> landing (Nginx со статикой)
- продуктовые пути на `mentala.app` (`/login`, `/auth`, `/api`, и так далее) -> 308 редирект на `https://my.mentala.app/...`

Причина: если делать Nginx на хосте, нужно отдельно решать TLS, редиректы и интеграцию с Traefik. В контейнере это решается одним сервисом и метками.

#### 4.3.1 Поведение роутинга доменов

- `https://mentala.app/` отдаёт статический лендинг
- `https://mentala.app/<product-path>` редиректит на `https://my.mentala.app/<product-path>`
- `https://my.mentala.app/*` остаётся под basic auth

Список `product-path` фиксируется в конфиге Traefik (middleware redirectregex), чтобы лендинг не ломался при будущих изменениях приложения.

#### 4.3.2 Кеширование и заголовки

Для надёжности и скорости обязательно:

- Долгий кеш для ассетов с хешами (`/_nuxt/*`, `/assets/*`) - `Cache-Control: public, max-age=31536000, immutable`.
- Короткий кеш или отсутствие кеша для `index.html` - чтобы деплой сразу применялся (`Cache-Control: no-cache` или `max-age=0`).
- Включить сжатие (gzip, при возможности brotli).

#### 4.3.3 Sitemap и robots

В репозитории должен быть:

- `robots.txt` с ссылкой на sitemap
- `sitemap.xml` (даже если страница одна)

Это ускоряет индексацию и снижает вероятность «пустого» первого обхода.

#### 4.3.4 Развёртывание на сервер

- выкладывать новый билд в директорию вида `/var/www/landing/releases/<timestamp>/` (директория на хосте; при использовании Nginx в контейнере она монтируется в контейнер как volume)
- переключать симлинк `/var/www/landing/current` на новый релиз;
- держать 3-5 последних релизов.

Так обновление становится почти «неубиваемым».

### 4.4 CI/CD

- В GitHub Actions (или текущем пайплайне):
  - При пуше в ветки `main` / `dev` (или по отдельным правилам для лендинга) добавить job или шаги:
    1. Установка зависимостей (уже есть в текущем flow).
    2. Сборка статики лендинга: `pnpm landing:generate` с подстановкой нужного env (prod или dev).
    3. Деплой артефакта (выбранный вариант: Nginx + статика):
       - `rsync` (или `scp`) собранного каталога в директорию релиза на сервере: `/var/www/landing/releases/<timestamp>/`
       - атомарное переключение симлинка `/var/www/landing/current` на новый релиз
       - опционально: удаление старых релизов, оставляя последние 3-5
- Секреты и переменные (пути, ключи доступа к серверу/Storage) — через secrets репозитория.

## 5. Критерии приёмки (Definition of Done)

- [ ] В репозитории есть команда `landing:generate`, успешно выполняющая статический экспорт лендинга.
- [ ] Результат сборки — каталог со статическими файлами; при открытии главной страницы в браузере отображается полный контент лендинга, форма и CTA работают (запросы уходят на заданный API).
- [ ] В сгенерированном HTML главной страницы присутствует полный контент (не только один пустой div), мета-теги и структура, пригодная для SEO.
- [ ] В CI добавлены шаги: сборка статики лендинга и деплой на выбранный хостинг (nginx или Storage+CDN).
- [ ] На проде (и при необходимости на dev) домен лендинга (`mentala.app` / dev) открывает статический лендинг; CORS и `ALLOWED_ORIGINS` настроены так, что запросы к API с лендинга проходят.
- [ ] Документация обновлена: `.docs/architecture.md` и при необходимости `.docs/landing.md` — способ деплоя лендинга описан как «статический экспорт + хостинг статики».
- [ ] На домене `mentala.app` корректно настроены `robots.txt` и `sitemap.xml`.
- [ ] Для `index.html` отключён долгий кеш, для ассетов включён `immutable`.
- [ ] Деплой лендинга выполняется атомарно (через releases + current) и поддерживает быстрый откат.
- [ ] Если используется `www.mentala.app`, настроен единый канонический домен (редирект `www` -> без `www` или наоборот).

## 6. Риски и открытые моменты

- **Путь вывода generate:** подтверждён: `apps/landing/.output/public` (после `pnpm landing:generate` из корня репозитория). Копирование не требуется — rsync в CI берёт содержимое этой директории.
- **Две сборки (prod и dev):** если нужны отдельные деплои для prod и dev лендинга (разные домены или разные API), в CI должно быть два набора env и два шага деплоя (или один шаг с параметром окружения).
- **Инвалидация кэша CDN:** (актуально, если перед Nginx появится CDN) при варианте Storage+CDN или CDN-перед Nginx описать в runbook момент инвалидации/обновления кэша после выкладки новой сборки.
- **Смешение ролей Traefik:** если `mentala.app` сейчас обслуживается приложением, нужно явно перевести домен `mentala.app` на лендинг, иначе редиректы и basic auth будут мешать индексации и конверсии.

## 7. Связанные документы

- `.docs/landing.md` — ТЗ лендинга (контент, API, аналитика).
- `.docs/architecture.md` — общая архитектура, раздел про лендинг и CI/CD.
- Анализ деплоя (контейнер vs статика) — в истории чата; выбран вариант «статика».
