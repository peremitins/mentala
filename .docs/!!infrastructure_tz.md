Техническое задание

Инфраструктура Mentala (Docker, VPS, Postgres, Redis, мониторинг)

1. Цель документа

Настоящее ТЗ описывает целевую архитектуру инфраструктуры Mentala для сред разработки, тестирования и продакшена с целью:
• предотвращения переполнения диска
• обеспечения стабильной работы PostgreSQL и Redis
• введения мониторинга и алертов
• обеспечения управляемого роста данных
• минимизации ручных аварийных вмешательств

Документ ориентирован на Docker-стек и VPS-инфраструктуру.

⸻

2. Текущее состояние (as-is)

2.1 Сервер
• Тип: VPS
• Диск: 10 GB (недостаточно)
• Docker используется напрямую на хосте
• Все данные хранятся на одном диске

2.2 PostgreSQL
• Контейнер: postgres:15-alpine
• Тип хранения: bind mount
• Путь на хосте:

/opt/mentala/dev/pgdata

    •	WAL и служебные файлы хранятся на том же диске, что и Docker overlay

2.3 Redis
• Контейнер: redis:7-alpine
• Хранение:

redis-data:/data

    •	Append Only File включён
    •	Отсутствует maxmemory policy

2.4 Проблема

PostgreSQL перешёл в режим recovery из-за нехватки места на диске.
Ошибка:

PANIC: could not write to file ... No space left on device

Причина:
• отсутствие лимитов на Docker-логи
• отсутствие очистки Docker cache
• слишком маленький диск
• отсутствие мониторинга и алертов

⸻

3. Принципы целевой архитектуры (to-be)
   1. Диск никогда не должен заполняться внезапно.
   2. Все накопительные источники должны иметь лимиты.
   3. Критические сервисы должны иметь мониторинг и алерты.
   4. Данные должны расти управляемо.
   5. Dev, Stage и Prod должны быть логически разделены.

⸻

4. Среды

4.1 Dev

Назначение: разработка и тестирование.

Допускается:
• сброс данных
• ручные операции

Обязательно:
• алерт по диску
• лимиты логов
• защита от полной остановки Postgres

4.2 Stage

Назначение: тест релизов.

Требования:
• максимально близка к Prod
• обязательные бэкапы
• полный мониторинг

4.3 Prod

Назначение: пользователи.

Требования:
• отказоустойчивость
• бэкапы
• строгие лимиты
• runbook

⸻

5. Ресурсы VPS (рекомендуемые)

5.1 Dev
• Disk: 30–50 GB
• RAM: 2–4 GB
• CPU: 2 vCPU

5.2 Stage
• Disk: 50–80 GB
• RAM: 4–8 GB
• CPU: 2–4 vCPU

5.3 Prod (MVP)
• Disk: 80–150 GB
• RAM: 8 GB
• CPU: 4 vCPU

Важно: увеличение диска не решает проблему само по себе без лимитов и мониторинга.

⸻

6. Docker требования

6.1 Лимиты логов контейнеров (обязательно)

Все контейнеры должны использовать log rotation.

Требования:
• max-size: 10–50MB
• max-file: 3–5

Цель: исключить рост логов до гигабайтов.

⸻

6.2 Очистка Docker cache

Обязательно настроить регулярную очистку:
• dangling images
• build cache
• stopped containers

Рекомендуемая периодичность:
• Dev: ежедневно
• Stage: раз в 2–3 дня
• Prod: раз в неделю (контролируемо)

⸻

6.3 Политика деплоя
• хранить ограниченное число старых образов
• не допускать накопления десятков тегов

⸻

7. PostgreSQL

7.1 Хранение данных

Текущее решение:

/opt/mentala/dev/pgdata

Допустимо для Dev.

Для Stage и Prod рекомендуется:
• либо отдельный диск
• либо managed PostgreSQL
• либо отдельный volume с гарантированным пространством

⸻

7.2 WAL и рост

PostgreSQL активно пишет WAL.
При заполнении диска Postgres не может завершить recovery.

Требования:
• всегда иметь минимум 10–15% свободного диска
• мониторить размер базы и WAL

⸻

7.3 Бэкапы

Обязательно для Stage и Prod.

Требования:
• ежедневный логический бэкап
• retention 7–30 дней
• хранение вне основного диска VPS
• регулярная проверка восстановления

⸻

8. Redis

8.1 Ограничение памяти (обязательно)

Redis должен иметь maxmemory policy.

Требования:
• задать maxmemory
• выбрать eviction policy (например volatile-lru)

Цель: Redis не должен приводить к OOM и падению контейнеров.

⸻

8.2 Персистентность
• Dev: допустима упрощённая
• Stage и Prod: включён AOF или RDB с контролем размера

⸻

9. Мониторинг и алерты

9.1 Что мониторить
• Disk usage (% и свободные GB)
• Inodes
• RAM
• CPU
• Docker directory size
• PostgreSQL availability
• Redis availability
• HTTP доступность API

⸻

9.2 Пороги алертов по диску

Уровень Условие
Warning > 70%
Alert > 85%
Critical > 92%

Дополнительно:
• warning если свободно < 10 GB
• critical если свободно < 5 GB

⸻

9.3 Каналы алертов

Минимум:
• Telegram
• Email

Prod:
• минимум два канала одновременно

⸻

10. Логи системы

10.1 systemd journal

Требования:
• задать лимиты по размеру
• задать срок хранения

Цель: исключить переполнение /var/log

⸻

11. Автоматические задачи

11.1 Cron задачи
• docker cleanup
• journal cleanup
• проверка диска
• отправка алертов

⸻

12. Runbook (обязательно)

Документ с инструкциями:

Если диск > 90%
• проверить top directories
• очистить Docker
• проверить логи
• проверить WAL

Если Postgres в recovery
• проверить свободное место
• проверить volume
• при необходимости восстановить из бэкапа

⸻

13. Критерии готовности

Инфраструктура считается готовой, если:
• Postgres не падает при деплоях
• Docker-логи имеют лимиты
• диск не может заполниться незаметно
• алерты приходят заранее
• есть бэкапы и проверка восстановления
• есть runbook

⸻

14. Пояснение про рост диска (ответ на ключевой вопрос)

Диск не имеет «естественного потолка».
Он будет заполняться всегда, если:
• нет лимитов
• нет ротации
• нет алертов

При корректной архитектуре:
• рост становится предсказуемым
• диск расширяется планово
• аварийные падения исключаются
