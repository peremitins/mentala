# Техническое задание: AI Gateway и роутинг провайдеров для Mentala

## 0. Цель

Обеспечить надежную работу ИИ-чата в Mentala при следующих условиях:

- Основная инфраструктура (аккаунты, БД, платежи, логи) размещена в РФ.
- Внешний AI-провайдер может быть недоступен из РФ или запрещать предоставление сервиса пользователям из неподдерживаемых стран. ([OpenAI Help Center][1])
- Требуется отказоустойчивость, безопасность, контроль расходов, возможность быстро переключать провайдера без релиза клиента.

## 1. Ключевые принципы дизайна

1. **Provider Abstraction**: приложение не зависит от одного AI-провайдера.
2. **AI Gateway**: отдельный сервис интеграции, который:

   - держит секреты провайдеров
   - нормализует запросы/ответы
   - делает rate-limit, retries, circuit breaker, аудит, метрики

3. **Policy-aware routing**: роутинг запросов учитывает страну/регион пользователя и правила провайдера.
4. **Data minimization**: в провайдера уходит минимально необходимый текст; PII по возможности редактируется.
5. **No raw chat logs** по умолчанию: в логах не хранить тело сообщений.

---

## 2. Архитектура

### 2.1 Компоненты

**A. RU Backend (основной сервер в РФ)**

- Авторизация, профили, подписки, лимиты
- Хранение summary, настроек, контекста
- Endpoint для клиента: `/api/chat`

**B. AI Gateway (в поддерживаемой стране, если провайдер требует)**

- Единственная точка выхода к внешним AI API
- Доступ к gateway только от RU backend (mTLS или подпись)
- Внутренний роутинг к провайдерам
- Набор защит и метрик

**C. Provider Connectors**

- Модуль “провайдер A” (в т.ч. OpenAI)
- Модуль “провайдер B” (резерв, например локальный/региональный)
- Единый интерфейс

### 2.2 Схемы трафика

**Основной режим (рекомендуемый):**
Client (RU) -> RU Backend -> AI Gateway (non-RU) -> Provider

**Fallback режим (если внешний провайдер недоступен/запрещен):**
Client -> RU Backend -> Provider B (доступный для РФ)
или: “ограниченный режим чата” (см. ниже).

> Важно: просто “проксировать” запросы ради скрытия РФ IP рискованно по правилам доступа в неподдерживаемых странах. ([OpenAI Help Center][2])

## 3. Политика совместимости с провайдерами (обязательный раздел)

### 3.1 Риски OpenAI для РФ

- OpenAI публикует список поддерживаемых стран и предупреждает, что доступ/предоставление доступа из неподдерживаемых стран может привести к блокировке. ([OpenAI Help Center][1])
- Следовательно, для РФ нужно одно из решений:

  1. **Не использовать OpenAI для пользователей из РФ**, пока правила не изменятся.
  2. **Ограничить доступ** (геофенсинг) и включать OpenAI только в поддерживаемых регионах.
  3. Иметь **контракт/разрешение** (если когда-то будет) и документально это зафиксировать.

### 3.2 Требование в реализации

- В систему роутинга добавить правило: `if region == RU -> provider = B` (или “restricted mode”).
- Провайдер OpenAI включать только если пользователь из поддерживаемого региона (или есть явное основание).

## 4. Функциональные требования

### 4.1 API RU Backend (для клиента)

`POST /api/chat`

- Вход:

  - `conversationId`
  - `message: string`
  - `mode` (therapy/habits/meditation/support etc.)
  - `stream: boolean`

- Выход:

  - если `stream=false`: `reply`, `usage`, `provider`, `requestId`
  - если `stream=true`: SSE поток токенов + финальное событие

Backend отвечает за:

- проверку подписки и лимитов
- запись summary/контекста
- выбор провайдера через routing policy
- вызов AI Gateway или локального провайдера

### 4.2 API RU Backend -> AI Gateway

`POST /v1/generate`

- Заголовки:

  - `X-Signature` (HMAC подпись тела + timestamp)
  - `X-Timestamp`
  - `X-Request-Id`

- Тело:

  - `input`: нормализованный промпт
  - `userContext`: только минимальные настройки (без email, без прямых идентификаторов)
  - `policy`: region, allowProviderA boolean
  - `stream`: boolean

### 4.3 AI Gateway: нормализация и защита

- Валидация схемы
- Проверка подписи/времени (anti-replay)
- Rate limiting по:

  - `clientId` (backend)
  - `conversationId`

- Retries только для безопасных ошибок (сетевые, 429) с backoff
- Circuit breaker на провайдера
- Таймауты:

  - connect: 3-5s
  - response: 60-120s (в зависимости от модели/стрима)

### 4.4 Fallback логика

Если провайдер A вернул:

- `unsupported_country`/`request_forbidden`/403 или похожее ([OpenAI Help Center][2])
- или 5xx/timeout N раз

то:

1. переключиться на провайдера B
2. если B недоступен: вернуть пользователю “ограниченный режим”:

   - короткий ответ: “Сервис временно недоступен, попробуйте позже”
   - и кнопка “Повторить”

## 5. Безопасность и приватность (реальные меры)

### 5.1 Что запрещено логировать

- Тела сообщений пользователя
- Сырые промпты
- Полные ответы модели

Разрешено логировать:

- requestId, latency, provider, statusCode, token usage, error type, region
- длину входа/выхода (символы), но не содержание

### 5.2 Секреты

- Ключи провайдеров хранятся только в AI Gateway (если он используется)
- RU backend не содержит ключей провайдера A
- Ротация секретов: раз в 30-90 дней

### 5.3 Минимизация данных

- Внешнему провайдеру не отправлять:

  - email, имя, userId в явном виде

- Использовать `pseudonymousUserKey` (хеш)

### 5.4 Контроль доступа

- AI Gateway принимает запросы только от RU backend:

  - allowlist IP + HMAC подпись
  - желательно mTLS

## 6. Эксплуатация и мониторинг

### 6.1 Метрики (обязательные)

- `chat_requests_total{provider,region,status}`
- `chat_latency_ms_p95{provider}`
- `provider_errors_total{provider,error_code}`
- `fallback_triggered_total{from,to,reason}`
- `token_usage_total{provider}`
- `cost_estimate_total` (если считаешь стоимость)

### 6.2 Алерты

- Ошибки `unsupported_country` > 1% за 10 минут
- 5xx > 2% за 5 минут
- p95 latency > 5s (настраиваемо)
- резкий рост cost_estimate

## 9. Критерии приемки

1. При запросах из РФ:

- система не падает, не зависает
- либо отвечает через провайдера B, либо корректно сообщает о недоступности

2. При недоступности провайдера A:

- происходит автоматический fallback

3. Секреты провайдера A отсутствуют на RU backend
4. В логах отсутствуют тела сообщений
5. Метрики и алерты работают

## 10. Что я рекомендую именно для Mentala (MVP)

- Делать gateway как полноценный компонент, но маленький.
- Сразу внедрить provider abstraction и fallback.
- Для РФ ориентированного MVP не закладываться на OpenAI как на единственную опору, потому что правила доступа и геоблоки могут “выстрелить” без предупреждения. ([OpenAI Help Center][1])
