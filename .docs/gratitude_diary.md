# Техническое задание

## Практика «Дневник благодарности»

Документ обновлён с учётом реальной структуры Mentala и уточнения по навигации:

- основная точка входа должна находиться в разделе `Практики`;
- `Дневник благодарности` добавляется как 4-й раздел на странице практик;
- связка с `Привычками` сохраняется, но как вторичный вход и точка настроек уведомлений;
- приложенные скриншоты используются как ориентир по структуре и сценариям, но не как прямой дизайн-референс.

Важно: визуальный стиль, компоненты, анимации и поведение должны оставаться в языке текущего приложения Mentala.

---

## Терминология

В документе используются следующие термины:

- `дневник` - основная практика `Дневник благодарности` в разделе `Практики`;
- `запись` - одна сохранённая запись пользователя в дневнике;
- `промпт` - вопрос, помогающий начать запись;
- `worksheet` - готовая шаблонная структура записи, которую пользователь может вставить в поле и затем отредактировать;
- `голосовой ввод` / `voice-to-text` - преобразование речи в текст без сохранения аудиофайла;
- `привычка gratitude` - существующая сущность в разделе `Привычки`, через которую открываются настройки уведомлений и вторичный вход.

---

## 1. Роль фичи в продукте

`Дневник благодарности` - это новая практика внутри раздела `Практики`, а не новый корневой модуль приложения и не отдельный таб нижней навигации.

Задача практики:

- помогать пользователю быстро фиксировать благодарности и маленькие позитивные моменты дня;
- формировать регулярность через streak;
- снижать порог входа в письмо за счёт промптов и простого интерфейса;
- держать создание записи и историю в одном месте.

Целевая продуктовая метрика:

- пользователь может сделать запись за 10–20 секунд;
- в базовом сценарии не требуется переход между несколькими экранами;
- запись, история и поиск доступны на одной странице.

## 2. Позиционирование в навигации

### 2.1. Каноническая точка входа

Основная точка входа в дневник должна быть из страницы `Практики`.

На странице `Практики` добавляется 4-я карточка:

- `Дневник благодарности`

Карточка открывает основной экран дневника.

### 2.2. Вторичная точка входа

`Дневник благодарности` остаётся в каталоге `Привычек`, потому что:

- там уже существует привычка `gratitude`;
- там логично хранить настройки уведомлений;
- в будущем может понадобиться дополнительная связка между привычкой и практикой.

Но экран дневника не должен дублироваться в двух независимых реализациях.

### 2.3. Основное правило архитектуры

У фичи должен быть один канонический экран дневника.

Рекомендованная модель:

- основной экран дневника открывается из `Практик`;
- карточка `gratitude` в `Привычках` ведёт на тот же экран;
- настройки уведомлений для `gratitude` остаются в контуре привычек и открываются по deep link из основного экрана дневника.

## 3. Маршруты и переходы

### 3.1. Канонический маршрут

Предпочтительный канонический маршрут:

`/practices/gratitude-diary`

### 3.2. Переход со страницы практик

Путь пользователя:

`/practices` -> карточка `Дневник благодарности` -> `/practices/gratitude-diary`

### 3.3. Переход из привычек

Карточка привычки `gratitude` в `Привычках` не должна открывать отдельную реализацию дневника.

Для первой поставки фиксируется один сценарий:

- карточка `gratitude` в `Привычках` сразу открывает `/practices/gratitude-diary`.

Промежуточный bridge-экран внутри `Привычек` в первую поставку не входит.

### 3.4. Настройки

Иконка настроек на основном экране дневника должна открывать настройки уведомлений для `gratitude` через существующий контур `Привычек`.

Ожидаемый смысл:

- сам дневник живёт в `Практиках`;
- настройки напоминаний живут в `Привычках`.

Для первой поставки использовать существующий маршрут настроек привычки `gratitude` или его прямой эквивалент.

### 3.5. Поведение кнопки «Назад»

На основном экране дневника:

- `router.back()` используется как основной сценарий;
- fallback-маршрут - `/practices`.

Это важно, потому что пользователь может прийти как из `Практик`, так и из `Привычек`.

## 4. Что должно войти в первую поставку

### 4.1. Обязательный MVP

В первую поставку входят:

- 4-я карточка `Дневник благодарности` на странице `Практики`;
- один канонический экран дневника;
- deeplink из `Привычек` на этот экран;
- streak;
- текущий промпт;
- каталог промптов;
- `Worksheet`;
- текстовый ввод;
- voice-to-text;
- загрузка фото;
- выбор mood;
- tags;
- list mode;
- сохранение записи;
- история записей на том же экране;
- поиск по тексту и тегам;
- settings entrypoint в настройки уведомлений привычки `gratitude`.

### 4.2. Что не входит в первую поставку

Во избежание размывания объёма и блокеров первая поставка не включает:

- `Help me write` (откладывается на потом, не в первой волне);
- запись звукового файла;
- хранение звукового файла;
- отдельный voice note player;
- редактирование существующей записи;
- удаление существующей записи;
- расширенную аналитику и челленджи;
- отдельный домашний экран в стиле `john's journal`.

**Важно:** функция `Color` (цветовой акцент записи) не планируется к реализации ни в первой волне, ни в будущем — полностью исключена из scope.

### 4.3. Что допускается как вторая итерация

Во второй итерации можно добавить:

- `Help me write`;
- челленджи;
- редактирование и удаление записи.

### 4.4. Правила доступа по тарифам

Экран дневника доступен всем пользователям.

Базовые функции дневника доступны всем:

- промпты;
- worksheet;
- voice-to-text;

## 6. Основной сценарий пользователя

### 6.1. Happy path

1. Пользователь открывает `Практики`.
2. Нажимает `Дневник благодарности`.
3. Попадает на основной экран дневника.
4. Видит текущий вопрос-промпт.
5. Вводит текст или диктует голосом.
6. При необходимости использует `Worksheet`, выбирает настроение, теги, фото и формат списка.
7. Нажимает `Сохранить`.
8. Запись мгновенно появляется в истории на этом же экране.

### 6.2. Вторичные сценарии

- пользователь меняет промпт кнопкой `Новый вопрос`;
- пользователь открывает весь каталог промптов через `Показать все`;
- пользователь открывает `Worksheet`;
- пользователь прикрепляет фото;
- пользователь ищет записи по тексту или тегам;
- пользователь открывает настройки уведомлений через иконку настроек;
- пользователь приходит на тот же экран из `Привычек`.

## 7. Информационная архитектура экрана дневника

Экран состоит из следующих блоков сверху вниз:

1. Header
2. Summary-блок со streak
3. Блок текущего промпта
4. Поле создания записи
5. Нижняя панель инструментов записи
6. Primary CTA `Сохранить`
7. История записей

История и создание записи находятся на одном экране.

## 8. Header

### 8.1. Состав

Левая часть:

- кнопка `Назад`;
- заголовок `Дневник благодарности`.

Правая часть:

- иконка поиска;
- иконка настроек.

### 8.2. Поведение

Кнопка `Назад`:

- возвращает пользователя на предыдущий экран;
- если предыдущего экрана нет, ведёт в `/practices`.

Иконка поиска:

- раскрывает inline-поле поиска на том же экране;
- не уводит пользователя на отдельную страницу.

Иконка настроек:

- открывает существующий экран настроек уведомлений привычки `gratitude`.

---

## 9. Summary-блок и streak

### 9.1. Назначение

Блок должен быстро показывать:

- текущую серию дней подряд;
- краткий статус активности пользователя;
- мотивацию продолжать практику.

### 9.2. Минимальный состав для MVP

- streak в формате `🔥 5 дней подряд`;
- подпись-пояснение;
- маленький popover/tooltip по нажатию.

Текст:

`Вы записываете благодарности уже 5 дней подряд. Продолжайте.`

### 9.3. Правила streak

Серия увеличивается, если пользователь сделал хотя бы одну запись в календарный день.

Если между двумя активными днями есть пропуск:

- серия сбрасывается.

Если пользователь сделал несколько записей в один день:

- streak увеличивается только один раз.

## 10. Промпт-блок

### 10.1. Назначение

Промпт помогает быстро начать запись без долгого размышления.

На экране одновременно показывается один активный вопрос.

### 10.2. Состав блока

- текущий вопрос;
- `Новый вопрос`;
- `Показать все`.

### 10.3. Примеры вопросов

- Что сегодня поддержало тебя?
- Что сегодня вызвало у тебя улыбку?
- Кто сегодня помог тебе почувствовать опору?
- За что ты благодарен своему телу сегодня?
- Какая маленькая вещь сделала день лучше?

### 10.4. Поведение

`Новый вопрос`:

- меняет вопрос;
- не очищает уже введённый текст.

`Показать все`:

- открывает bottom sheet на mobile и modal на desktop;
- показывает категории и список промптов;
- позволяет выбрать новый активный вопрос.

## 12. Поле создания записи

### 12.1. Основные требования

Поле ввода:

- многострочное;
- автоматически растёт по высоте;
- поддерживает ручной ввод и голосовой ввод;
- ограничено 2000 символами.

### 12.2. Placeholder

`Сегодня я благодарен за...`

### 12.3. Поведение

- текст не сбрасывается при смене промпта;
- поле остаётся главным фокусом экрана;
- при пустом значении кнопка `Сохранить` неактивна;
- при достижении лимита показывается понятное ограничение.

### 12.4. Допустимые UX-детали

Можно добавить:

- счётчик символов;
- быстрые маркеры для list mode;
- мягкую анимацию фокуса;
- локальный draft до сохранения.

## 13. Голосовой ввод

### 13.1. Статус

Функция обязательна для MVP.

### 13.2. Поведение

При нажатии на иконку микрофона:

- начинается распознавание речи;
- текст вставляется в поле записи;
- пользователь видит состояние `слушаю`;
- после завершения распознавания текст остаётся редактируемым.

### 13.3. Техническая привязка к проекту

В кодовой базе уже есть готовый reusable helper для диктовки:

- `app/composables/useVoiceDictationInput.ts`

Он уже используется минимум в:

- `app/pages/quick-help/thought-dump.vue`
- `app/pages/index.vue`

Для реализации voice-to-text в дневнике благодарности необходимо использовать именно этот composable и текущий speech stack под ним, а не придумывать новый механизм.

Под капотом остаются текущие платформенные источники:

- Web Speech API для web;
- `@capacitor-community/speech-recognition` для iOS/Android.

Сохраняется только текст.

Запись аудиофайла, хранение аудио и voice notes запрещены и не должны реализовываться ни в каком виде.

### 13.4. Fallback

Если распознавание недоступно:

- показывается toast;
- ручной ввод остаётся основным fallback-сценарием.

## 14. Нижняя панель инструментов записи

Панель должна быть мобильной, компактной и визуально встроенной в текущий UI приложения.

### 14.1. Состав MVP

- Mood
- Photo
- Voice
- List
- Tag

### 14.2. Photo

`Photo` входит в первую поставку.

Правила доступа:

- `Basic` -> фото недоступно, при нажатии показывается стандартная готовая paywall-модалка с предложением перейти на `Premium`;
- `Pro` -> фото недоступно, при нажатии показывается та же стандартная paywall-модалка;
- `Premium` -> фото доступно и работает полноценно.

Ограничения:

- до 1 фото на запись;
- источники: камера или галерея;
- перед загрузкой изображение сжимается;
- рекомендуемая ширина до 1200 px;
- формат `webp` или `jpeg`;
- хранение в Yandex Object Storage.

## 17. List mode

Пользователь может переключить формат записи в список.

Поддерживаются варианты:

- маркированный список;
- нумерованный список.

Пример:

```text
Сегодня я благодарен за:

- прогулку
- поддержку друга
- вкусный кофе
```

или

```text
1. прогулку
2. поддержку друга
3. вкусный кофе
```

Важно:

- это не rich text editor;
- форматирование должно быть простым и не перегружать ввод.

## 18. Кнопка сохранения

Primary CTA:

`Сохранить`

После сохранения:

- запись добавляется в историю без перезагрузки страницы;
- поле ввода очищается;
- выбранные параметры сбрасываются по согласованным правилам;
- показывается микроанимация;
- показывается toast `Запись сохранена`.

Обязательные требования:

- состояние загрузки;
- защита от двойного submit;
- ощущение мгновенного сохранения.

## 20. Карточка записи

Каждая карточка записи должна содержать:

- mood badge;
- дату/время;
- текст записи;
- теги;
- фото, если оно прикреплено.

Допустимо добавить:

- иконку голосового ввода, если запись начата голосом.

В первой поставке не требуются:

- редактирование;
- удаление;
- challenge-блоки;
- отдельные CTA внутри карточек.

## 21. Поиск

### 21.1. По каким данным ищем

Поиск работает по:

- тексту записи;
- тегам.

### 21.2. Поведение

- поиск выполняется на том же экране;
- результаты фильтруют текущую историю;
- выход из поиска возвращает полную ленту.

### 21.3. UX

Поиск реализуется как:

- иконка в header;
- inline search field под header или перед историей.

## 22. Данные записи

Пример объекта записи:

```ts
{
  id: string,
  userId: string,
  text: string,
  mood: string | null,
  tags: string[],
  photoUrl: string | null,
  inputMethod: 'text' | 'voice' | 'mixed',
```

- `currentPrompt`;

- `searchQuery`.

## 23. Минимальный технический контракт для первой поставки

Чтобы фронтенд и бэкенд могли идти параллельно, в первой поставке нужен минимальный набор контрактов.

Названия endpoint можно скорректировать, но смысл должен остаться таким:

### 23.1. Получить состояние экрана дневника

`GET /api/gratitude-diary`

Ответ должен включать:

- `streak`;
- `entriesCount`;
- `currentPrompt`;
- `entries` или `groupedEntries`;
- поддержку search query;
- признак пустого состояния.

### 23.2. Создать запись

`POST /api/gratitude-diary/entries`

Payload MVP:

```ts
{
  text: string,
  mood: string | null,
  tags: string[],
  photoUrl: string | null,
  inputMethod: 'text' | 'voice' | 'mixed'
}
```

### 23.3. Получить каталог промптов

`GET /api/gratitude-diary/prompts`

Ответ должен включать:

- категории;
- список промптов;
- возможность получить случайный промпт или выбрать конкретный.

### 23.4. Загрузка фото

Для premium-функции фото в первой поставке нужен upload-контур.

Допустимые варианты реализации:

- signed upload URL;
- backend proxy upload;
- уже существующий upload API приложения, если он подходит по security и UX.

### 23.5. Что не требуется в первой поставке

В первую поставку не входят отдельные backend-контракты для:

- редактирования и удаления записи.

## 24. Ограничения и fail-soft поведение

### 24.1. Ограничения

- максимум 2000 символов;
- пустую запись сохранить нельзя;
- теги нормализуются и дедуплицируются;
- слишком длинные теги обрезаются по лимиту.

### 24.2. Fail-soft

Если дополнительная функция недоступна:

- voice не работает -> остаётся ручной ввод;
- фото недоступно по тарифу -> показывается стандартная готовая paywall-модалка перехода на `Premium`;
- загрузка фото упала -> текст записи и остальная форма не теряются;
- поиск ничего не нашёл -> показывается пустое состояние;
- настройки не загрузились -> основной экран дневника продолжает работать.

## 25. Интеграция с привычкой `gratitude`

### 25.1. Что сохраняем

В `Привычках` сохраняется сущность `gratitude`, потому что она нужна как минимум для:

- настроек уведомлений;
- будущих связок между привычкой и практикой;
- продуктовой консистентности.

### 25.2. Как связаны `Практики` и `Привычки`

Нужно зафиксировать следующее правило:

- у пользователя один дневник благодарности;
- один набор записей;
- один streak;
- одна каноническая точка работы с дневником;
- настройки уведомлений открываются через привычку `gratitude`.

### 25.3. Что не допускается

Не допускается:

- две отдельные базы записей;
- два отдельных streak;
- два разных экрана дневника с разным поведением.

## 29. Итоговая концепция

`Дневник благодарности` - это новая практика в разделе `Практики`, а не отдельный параллельный модуль.

Продуктовая идея:

- основной пользовательский вход идёт через `Практики`;
- `Привычки` дают связку и настройки уведомлений;
- вся ежедневная работа с дневником происходит на одном каноническом экране;
- первая поставка остаётся компактной и реально реализуемой без лишних архитектурных рисков.
