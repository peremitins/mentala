# ТЗ: Глобальная оркестрация расписания уведомлений

**Версия:** 1.0  
**Дата:** 2025-01-XX  
**Статус:** В разработке

## 1. Проблема

### 1.1 Текущие проблемы

1. **Неравномерное распределение по дням**: Каждый источник генерирует слоты независимо, из-за чего в один день может быть 3 уведомления, в другой — 8, хотя у всех источников установлено по 5 уведомлений в день.

2. **Отсутствие чередования тем**: Уведомления из одной темы идут подряд, хотя должны чередоваться.

### 1.2 Причина проблемы

В `scheduler.service.ts` функция `generateAllSlotsForUser` вызывает `regenerateSlotsForSource` для каждого источника независимо. Каждый источник генерирует свои слоты без учета других источников и без глобального распределения.

## 2. Требования

### 2.1 Распределение по дням

- **Строго соблюдать `timesPerDay`** для каждого источника
- Если у пользователя 3 источника по 5 уведомлений в день, то в день должно быть ровно 15 уведомлений (по 5 от каждого)
- Учитывать частичное распределение в текущий день при позднем включении

### 2.2 Частичное распределение в текущий день

Если уведомления включены поздно:

- **Учитывать `activeDays`** — слоты генерируются только для активных дней недели
- **Учитывать диапазон через полночь** (`crossesMidnight = timeRangeStart > timeRangeEnd`) — правильно вычислять оставшееся время
- Вычислить средний интервал: `интервал = (timeRangeEnd - timeRangeStart) / timesPerDay` (с учетом `crossesMidnight`)
- Если оставшееся время до конца диапазона < `интервал`, не впихивать все уведомления
- В текущий день создать только те слоты, которые помещаются с учетом интервала
- Со следующего дня — полное количество (если день активный по `activeDays`)

**Пример:**

- Диапазон: 10:00–22:00 (12 часов = 720 минут)
- `timesPerDay = 5`
- Средний интервал: 720 / 5 = 144 минуты (2.4 часа)
- Включение в 21:00, до конца диапазона 1 час (60 минут)
- 60 < 144 → в текущий день 0 слотов, со следующего дня — все 5

### 2.3 Чередование тем

- **В норме: не более 2 уведомлений подряд** из одной темы (entityKey)
- **При фиксированных временах (`customSlotTimes`): допускается локально не более 3 подряд**, но только из-за фиксированных времен (фиксированные времена не сдвигаются)
- Если активна только одна группа (только терапия или только привычки), допускается 2 подряд из одной темы
- Если активны обе группы (терапия и привычки), чередовать группы и темы внутри групп
- **Допускается перевес** у группы с большим количеством слотов (weighted round-robin)

**Примеры:**

- Только терапия (anxiety, stress, selfesteem): допустимо `anxiety → anxiety → stress`, но не `anxiety → anxiety → anxiety`
- Терапия + привычки: чередовать группы и темы, например: `anxiety → alcohol → stress → water → selfesteem`

### 2.4 Кастомные времена

- Если у источника заданы `customSlotTimes`, эти времена **не сдвигать и не изменять**
- Кастомные времена имеют приоритет при распределении
- Остальные слоты распределять с учетом кастомных времен
- Если фиксированные времена конфликтуют с минимальным интервалом, сдвигать только гибкие слоты

### 2.5 Горизонт планирования

- Оставить **2 дня** (сегодня + завтра)
- Генерировать слоты на 2 дня вперед с учетом частичного распределения в текущий день

### 2.6 Идемпотентность на текущий день

- При генерации учитывать уже отправленные уведомления за текущий день (`sent`)
- **ВАЖНО:** `planned` и `queued` слоты **сегодня и завтра** удаляются перед генерацией на этапе 0, поэтому в расчёте остатка учитываем только `sent` слоты
- Нельзя создавать больше `timesPerDay` слотов на источник в пределах одного дня
- Это гарантирует, что при повторной генерации не будет дубликатов

## 3. Алгоритм работы

### 3.0 Этап 0: Сброс текущего расписания

**ВАЖНО:** Перед генерацией нового расписания необходимо полностью удалить все существующие planned слоты пользователя.

1. Удалить все слоты со статусом `'planned'` и `'queued'` для пользователя
2. Удалять **только слоты сегодня и завтра** (в пределах горизонта планирования): `scheduledAt >= начало_сегодня` и `scheduledAt <= конец_завтра` (в локальном времени)
3. Сохранить слоты со статусом `'sent'` (они не должны удаляться)
4. Это обеспечит чистое состояние для новой генерации без конфликтов со старыми слотами

**Реализация:**

- Использовать существующую функцию `deletePlannedFutureSlotsForSource` или создать аналогичную для всех источников пользователя
- Удалять слоты с `scheduledAt >= начало_сегодня_локальное` и `scheduledAt <= конец_завтра_локальное` и `status IN ('planned','queued')`

### 3.1 Этап 1: Подготовка данных

1. Получить все активные `notification_preferences` пользователя
2. Сгруппировать по источникам: `kind:entityKey`
3. Для каждого источника:
   - Получить `timesPerDay`, `timeRangeStart`, `timeRangeEnd`, `customSlotTimes`, `activeDays`
   - Определить `crossesMidnight = timeRangeStart > timeRangeEnd`
   - Вычислить средний интервал: `интервал = (timeRangeEnd - timeRangeStart) / timesPerDay` (с учетом `crossesMidnight`, если `customSlotTimes` не заданы)
   - Вычислить оставшееся количество слотов на день: `remainingSlots = timesPerDay - sentToday` (если день активный по `activeDays`)
   - Получить число слотов, уже отправленных сегодня:
     - `sentToday` — слоты со статусом `'sent'` за текущий день (локальное время)
     - **ВАЖНО:** `plannedToday` и `queuedToday` будут 0, так как они удаляются на этапе 0
4. Получить timezone пользователя

### 3.2 Этап 2: Расчет слотов для текущего дня

Для каждого источника:

1. Проверить, является ли текущий день активным по `activeDays`
2. Если день неактивен → 0 слотов на сегодня
3. Определить текущее время в локальной зоне
4. Проверить, попадает ли текущее время в диапазон `[timeRangeStart, timeRangeEnd]` (с учетом `crossesMidnight`)
5. Если попадает:
   - Вычислить оставшееся время до конца диапазона
   - Вычислить максимум слотов по времени: `maxByTime = floor(remaining / interval)`
   - Вычислить оставшееся количество к планированию:
     - `remainingByCount = max(0, timesPerDay - sentToday)`
     - **Примечание:** `plannedToday` и `queuedToday` не учитываются, так как они удаляются на этапе 0
   - Итоговое количество на сегодня:
     - `slotsToday = min(maxByTime, remainingByCount)`
     - Если `remaining < interval` → `slotsToday = 0`
6. Если не попадает:
   - Если текущее время < `timeRangeStart`: генерировать все `timesPerDay` слотов
   - Если текущее время > `timeRangeEnd`: 0 слотов на сегодня

### 3.3 Этап 3: Генерация временных меток

Для каждого источника и каждого дня (сегодня + завтра):

1. Проверить, является ли день активным по `activeDays` — если нет, пропустить день
2. Учесть `crossesMidnight` при вычислении временных меток
3. Если заданы `customSlotTimes`:
   - Использовать их как приоритетные времена
   - Остальные слоты распределить равномерно между кастомными временами
   - Пометить такие слоты как фиксированные (`fixedTime = true`)
4. Если `customSlotTimes` не заданы:
   - Распределить слоты равномерно по диапазону с учетом интервала и `crossesMidnight`
   - Применить детерминированный джиттер (±15 минут)

### 3.4 Этап 4: Глобальная оркестрация и чередование

1. Сначала построить **последовательность слотов** без времени на каждый день:
   - Использовать weighted round-robin по группам (habits/therapy)
   - **Вес группы** = сумма оставшихся слотов на день по группе (или "количество тем с remaining > 0" + учёт их `timesPerDay`)
   - **Пример:** Если терапия: anxiety (remaining=5), stress (remaining=3), selfesteem (remaining=5) → вес = 13
   - Если привычки: alcohol (remaining=5), water (remaining=5) → вес = 10
   - **Алгоритм:** чередовать группы пропорционально их весу (в примере: терапия → привычки → терапия → терапия → привычки → ...)
   - Внутри группы чередовать темы, не допуская 3 подряд одной темы (в норме ≤2)
   - **ВАЖНО:** При построении последовательности учитывать, какие слоты имеют фиксированные времена (`customSlotTimes`)
2. Затем **назначить времена** для полученной последовательности:
   - Фиксированные слоты (`customSlotTimes`) закрепить на своих временах в правильных позициях последовательности
   - Гибкие слоты распределить по окну равномерно с джиттером, заполняя промежутки между фиксированными временами
   - Учитывать `activeDays` и `crossesMidnight` при назначении времен
3. Если фиксированные времена ломают чередование — допускается локальное нарушение правил (не более 3 подряд, только из-за фиксированных времен), но фиксированные времена не сдвигаются

### 3.5 Этап 5: Предотвращение пересечений

После чередования:

1. Вызвать `preventSimultaneousNotifications` для предотвращения одновременных уведомлений
2. Минимальный интервал: 10 минут (как сейчас)
3. Не сдвигать слоты с `fixedTime = true`, сдвигать только гибкие

### 3.6 Этап 6: Создание слотов в БД

Для каждого слота:

1. Выбрать текст через `text-selection.service.ts`
2. Создать payload
3. Сохранить в БД через `insertSlot`

## 4. Архитектура решения

### 4.1 Новые файлы

1. **`server/application/notifications/global-orchestration.service.ts`**
   - `orchestrateAllSlotsForUser(userId)` — главная функция оркестрации
   - `deleteAllPlannedSlotsForUser(userId)` — удаление всех planned слотов перед генерацией
   - `calculatePartialSlotsForToday(sourcePref, nowLocal, timezone, sentToday)` — расчет частичных слотов
   - `alternateTopics(slots)` — чередование тем
   - `distributeSlotsEvenly(sources, days)` — равномерное распределение
   - `buildDailySequence(sources)` — построение последовательности слотов на день с учетом групп и тем

### 4.2 Модификация существующих файлов

1. **`scheduler.service.ts`**:

   - Заменить логику в `generateAllSlotsForUser` на вызов `orchestrateAllSlotsForUser`
   - Сохранить `regenerateSlotsForSource` для случаев, когда нужно регенерировать только один источник

2. **`slot-times.service.ts`**:
   - Добавить функцию `generateSlotTimesWithInterval(timesPerDay, interval, ...)` для генерации с учетом интервала

### 4.3 Сохранение совместимости

- `regenerateSlotsForSource` оставить для случаев регенерации одного источника
- При изменении настроек одного источника использовать `regenerateSlotsForSource` с последующей глобальной оркестрацией (для соблюдения чередования)

## 5. Примеры работы

### Пример 1: Частичное распределение

**Настройки:**

- Источник: anxiety, `timesPerDay = 5`
- Диапазон: 10:00–22:00 (12 часов)
- Средний интервал: 144 минуты (2.4 часа)
- Включение в 21:00

**Результат:**

- Текущий день (21:00–22:00): 0 слотов (60 минут < 144 минут)
- Следующий день: 5 слотов равномерно распределены

### Пример 2: Чередование тем

**Настройки:**

- Терапия: anxiety (remaining=5), stress (remaining=5), selfesteem (remaining=5) — вес группы = 15
- Привычки: alcohol (remaining=5), water (remaining=5) — вес группы = 10
- Всего: 25 уведомлений в день
- Weighted round-robin: терапия (вес 15) vs привычки (вес 10) → соотношение 3:2

**Результат:**

- Чередование с учетом весов: `anxiety → alcohol → stress → water → selfesteem → anxiety → alcohol → stress → ...`
- В норме не более 2 подряд из одной темы
- Группы чередуются пропорционально весу (примерно 3:2)

### Пример 3: Кастомные времена

**Настройки:**

- Источник: anxiety, `timesPerDay = 5`
- `customSlotTimes = [540, 720, 1080]` (09:00, 12:00, 18:00)
- Диапазон: 09:00–22:00

**Результат:**

- 3 слота на кастомные времена
- 2 дополнительных слота распределены равномерно между кастомными временами
- Кастомные времена не изменяются

## 6. Критерии приемки

1. **Распределение по дням:**

   - Если у всех источников `timesPerDay = 5`, то в день ровно `5 × количество_источников` уведомлений
   - Частичное распределение работает корректно при позднем включении
   - Уже отправленные слоты (`sent`) за текущий день учитываются при расчете остатка
   - При повторной генерации не создаются дубликаты (идемпотентность)

2. **Чередование тем:**

   - В норме: не более 2 уведомлений подряд из одной темы
   - При фиксированных временах: допускается локально не более 3 подряд, но только из-за фиксированных времен
   - При активных обеих группах чередуются группы и темы с допустимым перевесом у группы с большим количеством оставшихся слотов

3. **Кастомные времена:**

   - Не изменяются и не сдвигаются
   - Имеют приоритет при распределении
   - При конфликте с минимальным интервалом сдвигаются только гибкие слоты

4. **Предотвращение пересечений:**

   - Минимальный интервал между уведомлениями: 10 минут
   - `preventSimultaneousNotifications` работает корректно

5. **Производительность:**
   - Генерация слотов для пользователя с 10 источниками выполняется < 1 секунды
   - Алгоритм чередования не увеличивает время генерации более чем на 20%

## 8. Риски и ограничения

1. **Производительность**: При большом количестве источников может потребоваться оптимизация
2. **Сложность алгоритма чередования**: Нужно учесть все кейсы
3. **Миграция существующих слотов**: При первом запуске нужно полностью удалить все planned слоты и пересоздать их заново на основе новой логики
