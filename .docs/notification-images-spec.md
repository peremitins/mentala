# Техническое задание: Система семантической привязки изображений к push-уведомлениям Mentala

**Версия:** 1.3  
**Статус:** Final перед релизом  
**Дата:** 2026-02-03

---

## 1. Цель задачи

Устранить несоответствие между текстом push-уведомлений и прикрепляемыми изображениями.

Обеспечить:

- семантическое соответствие картинки содержанию текста;
- запрет визуально жесткого контента в мягких и поддерживающих уведомлениях;
- масштабируемую и простую архитектуру без усложнения на старте;
- отсутствие дублирования универсальных изображений между привычками и терапией.

---

## 2. Ключевая идея

1. AI генерирует не строки, а объекты уведомлений.
2. Каждый объект содержит семантический тег изображения (`imageTag`).
3. Изображения хранятся по каталогам, сгруппированным по тегам.
4. Подбор изображения осуществляется строго по тегу и правилам совместимости.
5. Универсальные изображения не дублируются, они берутся из `common`.
6. При отсутствии подходящих изображений используется fallback.

---

## 3. Структура AI-уведомления и контекст

### 3.1 Контекст генерации (уже есть в системе, не часть ответа AI)

| Поле        | Тип            | Описание                                                                                                        |
| ----------- | -------------- | --------------------------------------------------------------------------------------------------------------- |
| kind        | enum           | `therapy` / `habits`                                                                                            |
| entityKey   | string \| null | Ключ сущности (habitKey или therapy topic key). Может быть `null` для кастомных сущностей                       |
| subtype     | enum \| null   | NotificationSubtype: `reminder`, `informational`, `motivational`, `mixed`                                       |
| directness  | enum           | Directness: `soft`, `moderate`, `hard`                                                                          |
| habitIntent | enum \| null   | Только для habits: `build`, `quit`, `custom`                                                                    |
| tone        | enum           | `delicate`, `neutral`, `uplifting`, `resolute`, `demanding`, `unknown` (в правилах изображений не используется) |

Важно: `subtype` и `directness` уже есть в системе и передаются в генерацию. Их не нужно дублировать в объектах ответа AI, кроме режима `mixed`.

### 3.2 Формат объекта уведомления (то, что возвращает AI)

Базовый формат:

```json
{
  "text": "Тяга - это волна. Она спадет, если дать ей время.",
  "imageTag": "nature"
}
```

Режим mixed (обязательное поле `subtype` на каждом элементе):

```json
{
  "text": "Риск возрастает уже при регулярном употреблении.",
  "imageTag": "harm_mental",
  "subtype": "informational"
}
```

### 3.3 Поля объекта

| Поле     | Тип    | Описание                                                                                                                    |
| -------- | ------ | --------------------------------------------------------------------------------------------------------------------------- |
| text     | string | Текст уведомления                                                                                                           |
| imageTag | enum   | Семантический тег изображения                                                                                               |
| subtype  | enum   | Обязателен только если исходный режим `subtype = mixed`. Значение для элемента: `reminder`, `informational`, `motivational` |

## 4. Enum значений (фактические в проекте)

### 4.1 subtype (NotificationSubtype)

- `reminder` - напоминание о действии
- `informational` - факты и полезная информация
- `motivational` - поддержка и мотивация
- `mixed` - смесь типов

Единственный маппинг legacy-терминов:

- support -> motivational
- facts -> informational
- reminders -> reminder
- mixed -> mixed

### 4.2 directness (Directness)

- `soft` - мягкий
- `moderate` - сдержанный
- `hard` - жесткий

### 4.3 habitIntent (HabitIntent)

- `build` - формирование полезной привычки
- `quit` - отказ от вредной привычки
- `custom` - кастомная привычка

### 4.4 imageTag (закрепленный финальный набор)

Вред и негативные последствия:

1. `harm_organs` - внутренние органы, медицинские и визуально тяжелые последствия.
2. `harm_appearance` - внешние негативные эффекты: кожа, отеки, старение.
3. `harm_mental` - психика, тревожность, сон, когнитивные нарушения.

Позитивные и нейтральные:

4. `activity` - физическая активность: спорт, бег, движение.
5. `nature` - природа, пейзажи, вода, лес, небо.
6. `meditation` - медитация, дыхание, спокойные позы.
7. `daily_life` - повседневные здоровые сцены: сон, вода, еда, прогулка.

Опциональный:

8. `neutral_abstract` - абстрактные фоны, минимализм, универсальные изображения.

## 5. Структура хранения изображений (без дублирования)

Цель структуры - не дублировать общие изображения между привычками и терапией, при этом сохранить возможность иметь уникальные изображения для конкретной сущности.

Принцип:

- Общие изображения хранятся в `common` и подходят большинству сущностей.
- Сущностные изображения хранятся в каталоге конкретной сущности и используются как override.
- Дублирование запрещено: если изображение универсальное, оно должно лежать в `common`, а не копироваться в `habits/*` или `therapy/*`.

### 5.1 Базовые каталоги

```
/notifications/common/
/notifications/habits/
/notifications/therapy/
```

### 5.2 Общие изображения (основа)

```
/notifications/common/activity/
/notifications/common/nature/
/notifications/common/meditation/
/notifications/common/daily_life/
/notifications/common/neutral_abstract/
/notifications/common/harm_organs/
/notifications/common/harm_mental/
```

`harm_*` в `common` допустимы только как универсальные медицинские визуалы без предметных контекстов (бутылки, сигареты, вейпы и т.д.).

### 5.3 Сущностные изображения для habits (override)

Сущностные изображения нужны, когда картинка привязана к конкретной привычке и не должна применяться где-либо еще.

Пример для привычки `alcohol`:

```
/notifications/habits/alcohol/activity/
/notifications/habits/alcohol/nature/
/notifications/habits/alcohol/meditation/
/notifications/habits/alcohol/daily_life/
/notifications/habits/alcohol/neutral_abstract/

/notifications/habits/alcohol/harm_organs/
/notifications/habits/alcohol/harm_appearance/
/notifications/habits/alcohol/harm_mental/
```

Важно:

- Папки `activity/nature/meditation/daily_life/neutral_abstract` внутри `habits/{entityKey}` создаются только если там действительно есть уникальные изображения. Если уникальных нет, используется `common`.
- `harm_*` для `habits` чаще всего сущностные (алкоголь, курение), поэтому допустимо держать их в `habits/{entityKey}/harm_*`.

### 5.4 Therapy (сущностные папки разрешены, возможны вложенные)

Для терапии допускаются уникальные изображения по конкретной теме:

```
/notifications/therapy/{entityKey}/{imageTag}/
/notifications/therapy/{entityKey}/**/{imageTag}/
```

Если сущностных изображений нет, используется `common`.
Если есть изображения и на верхнем уровне, и во вложенных папках — они должны быть смешаны (без жесткого приоритета).

### 5.5 Гендерные подкаталоги запрещены

- Подкаталоги `male`/`female` не используются.
- Все изображения складываются в единый нейтральный набор (без сегментации по полу).
- Если ранее использовались `male`/`female`, их нужно перенести в нейтральные папки и удалить старые пути.
- Для миграции используем скрипт `scripts/normalize-notification-images.mjs`, после чего выполняем синхронизацию в Yandex Object Storage через `scripts/upload-notification-images.sh`.

## 6. Правила совместимости текста и изображений

### 6.1 Эффективный subtype

Эффективный `subtype` определяется так:

- если общий `subtype != mixed`, используем его;
- если `subtype = mixed`, используем `subtype` конкретного элемента (после восстановления, если нужно).

### 6.2 Жесткие запреты

1. Если `kind = therapy` - запрещены все `harm_*`.
2. Если эффективный `subtype` = `motivational` или `reminder` или `null` - запрещены все `harm_*`.
3. Если `directness = soft` - запрещены все `harm_*`.
4. Если `habitIntent = build` или `habitIntent = custom` - запрещены все `harm_*`.
5. `harm_organs` разрешен только если:
   - `kind = habits`
   - `habitIntent = quit`
   - эффективный `subtype = informational`
   - `directness = hard`
6. `harm_appearance` и `harm_mental` разрешены только если:
   - `kind = habits`
   - `habitIntent = quit`
   - эффективный `subtype = informational`
   - `directness = moderate` или `hard`

### 6.3 Особое правило для mixed

По умолчанию для `subtype = mixed` все `harm_*` запрещены.

Разрешение точечное, только если одновременно:

1. `kind = habits`
2. `habitIntent = quit`
3. `directness = hard`
4. конкретный элемент в массиве имеет `subtype = informational`

### 6.4 entityKey = null (кастомные сущности)

Если `entityKey = null`, разрешены только нейтральные теги:

- `activity`, `nature`, `meditation`, `daily_life`, `neutral_abstract`

`harm_*` всегда запрещены независимо от остальных параметров.

### 6.5 Восстановление subtype в mixed (устойчивость)

Если в режиме `mixed` элемент пришел без `subtype`, применяется восстановление:

1. Если `imageTag` относится к `harm_*`, принудительно ставим `subtype = informational`.
2. Иначе ставим `subtype = motivational` (самый безопасный).
3. При перекосе квот допускается пост-распределение:
   - если в тексте есть маркеры поддержки (например, "держись", "ты справишься") -> `motivational`;
   - если есть маркеры фактов/рисков (числа, "риск", "повышает", "снижает") -> `informational`;
   - иначе `reminder` или `motivational` по дефициту квоты.

Если элемент невалиден (пустой текст, слишком длинный, токсичный), он отбрасывается и заменяется из резервного пула.

### 6.6 Микс common + сущностные (если есть оба набора)

Если изображения есть и в `common`, и в `habits/{entityKey}` или `therapy/{entityKey}`, итоговая последовательность должна быть смешанной, а не строго сущностной или строго common.

Рекомендация: равномерное чередование (interleave) или рандом с сохранением пропорций.

Если у therapy изображения есть и на верхнем уровне, и во вложенных папках — они тоже миксуются между собой.

### 6.7 Устойчивая ротация без повторов

Выбор изображения должен обеспечивать:

- бесконечный показ по кругу;
- минимизацию повторов на короткой дистанции;
- сохранение позиции между перегенерациями текстов и изменениями настроек.

Если индекс ротации хранится отдельно (например, per user + entityKey + imageTag), новые тексты должны продолжать последовательность, а не начинать с начала.

### 6.8 Поведение при нарушении

Если тег запрещен:

- выбирается fallback тег (`nature`, затем `neutral_abstract`);
- либо уведомление отправляется без изображения.

### 6.9 Legacy пулы (старый формат без imageTag/subtype)

Если пул старого формата (массив строк, без `imageTag` и без `subtype`):

- не пытаемся угадывать тег;
- применяем только safe‑only визуалы;
- fallback строго: `nature` → `neutral_abstract`;
- `harm_*` всегда запрещены.

Это мягкая деградация до перегенерации пула.

## 7. Алгоритм подбора изображения

1. Получить `imageTag` из объекта уведомления.
2. Определить эффективный `subtype` (см. п. 6.1 и 6.5).
3. Проверить совместимость с контекстом (`kind`, `subtype`, `directness`, `habitIntent`, `entityKey`).
4. Сформировать список путей поиска, в порядке приоритета:
   - если `kind = habits` и `entityKey != null`:
     1. `/notifications/habits/{entityKey}/{imageTag}/`
     2. `/notifications/common/{imageTag}/`
   - если `kind = therapy`:
     1. `/notifications/therapy/{entityKey}/{imageTag}/`
     2. `/notifications/therapy/{entityKey}/**/{imageTag}/`
     3. `/notifications/common/{imageTag}/`
   - если `entityKey = null`:
     1. `/notifications/common/{imageTag}/`
5. Если есть оба источника (common + сущностный), их нужно миксовать (см. п. 6.6).
6. Если по `imageTag` ничего не найдено:
   - fallback на `/notifications/common/nature/`
   - затем `/notifications/common/neutral_abstract/`
   - затем отправить уведомление без изображения.
7. Выбор изображения осуществляется round-robin или random.

## 9. Обратная совместимость

- Старые уведомления без `imageTag`:
  - используют текущую логику подбора;
  - либо получают `nature` по умолчанию.
- Если AI вернул массив строк, каждая строка трактуется как `{ text, imageTag: null }`.

Новая система внедряется постепенно.

---

## 10. Критерии приемки

- Нет случаев визуального вреда при `kind = therapy`, `subtype = motivational/reminder/null`, `directness = soft`, `habitIntent != quit`.
- Для `mixed` допускаются `harm_*` только на `informational` элементах при `directness = hard`.
- Универсальные изображения берутся из `common` и не дублируются в `habits` и `therapy`.
- Если common и сущностные изображения есть одновременно, результат смешан (нет жесткого приоритета одного источника).
- `harm_*` в `common` содержат только универсальные медицинские визуалы без предметных контекстов.
- Добавление новых изображений не требует изменения кода.
- Система работает без мета-файлов и без базы данных для изображений.

---

## 11. Примечания

- Теги описывают визуальное содержание, а не психологический смысл.
- Семантика текста управляется через `subtype` и `directness` (и `habitIntent` для habits).
- `tone` из user_preferences не участвует в правилах выбора изображений.
- Гендерные подкаталоги запрещены, используется единый нейтральный набор.
- Архитектура минимальна и рассчитана на быстрый релиз.
- Ротация изображений должна быть устойчивой: без частых повторов и с сохранением позиции между перегенерациями текстов и изменениями настроек.
