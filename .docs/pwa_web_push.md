# PWA и Web Push для Mentala

## 1. Техническое задание на внедрение PWA

### 1.1. Статус документа

Этот документ фиксирует предварительное техническое задание на внедрение PWA в проект Mentala.

Важно:

- это не окончательное решение;
- документ подлежит дополнительному согласованию;
- по итогам проектирования, тестирования и продуктового обсуждения в документ могут быть внесены правки;
- отдельные технические детали могут быть скорректированы после проверки на реальных устройствах iOS, Android и desktop.

### 1.2. Цель внедрения PWA

Внедрение PWA требуется как промежуточный и частично постоянный канал доступа к приложению Mentala, чтобы:

- ускорить выпуск продукта без ожидания завершения ревью в App Store и Google Play;
- дать пользователю возможность установить Mentala на устройство уже сейчас;
- приблизить внешний вид и поведение веб-версии к формату нативного приложения;
- обеспечить запуск приложения с домашнего экрана без типичного браузерного интерфейса;
- подготовить инфраструктуру для Web Push уведомлений;
- сохранить возможность дальнейшего параллельного существования PWA и нативных приложений.

### 1.3. Что именно считается PWA в рамках проекта

В рамках Mentala PWA внедряется не на лендинг, а на основное приложение.

Принятое решение:

- `mentala.app` остается лендингом;
- `my.mentala.app` становится installable PWA.

Причина:

- пользователь должен устанавливать не маркетинговую страницу, а полноценную рабочую часть продукта;
- именно в `my.mentala.app` находятся авторизация, основная бизнес-логика, чат, уведомления, привычки и настройки.

### 1.4. Ожидаемый результат

После внедрения PWA пользователь должен иметь возможность:

- открыть `my.mentala.app` в браузере;
- установить приложение на устройство;
- запускать Mentala с домашнего экрана;
- видеть интерфейс в режиме, максимально близком к приложению;
- получать Web Push уведомления, если платформа это поддерживает;
- продолжать пользоваться тем же сервером, той же учетной записью и той же бизнес-логикой, что и в обычной веб-версии.

### 1.5. Ограничения и платформенные особенности

#### Android

На Android PWA и Web Push остаются поддерживаемой web-инфраструктурой, но install UX больше не строится вокруг PWA как основного мобильного сценария.

Ожидаемое поведение:

- основной mobile-promo flow на web ведёт пользователя к нативному Android-приложению;
- если related Android app установлен и это подтверждено поддерживаемым браузерным способом, сайт предлагает явный CTA `Открыть приложение`;
- если related Android app не установлен или статус не подтверждён, сайт предлагает Google Play как install path;
- принудительного редиректа в приложение при обычном web-сеансе быть не должно;
- Web Push web-канала остаётся технически поддерживаемым для браузерного сценария.

#### iPhone и iPad

На iOS и iPadOS PWA работает через сценарий добавления приложения на экран Домой.

Ожидаемое поведение:

- пользователь открывает `my.mentala.app` в Safari;
- вручную добавляет приложение на экран Домой;
- после этого запускает Mentala как web app;
- только после этого может использовать сценарии Web Push, если платформа и версия системы поддерживают это.

Важно:

- нельзя проектировать UX так, будто iOS ведет себя идентично Android;
- для iOS потребуется отдельная пользовательская инструкция по установке PWA и отдельный сценарий включения уведомлений.

#### Desktop

На desktop PWA также поддерживается и должна рассматриваться как отдельный канал использования продукта.

### 1.6. Объем работ по внедрению PWA

На текущем этапе требуется зафиксировать не только продуктовую идею PWA, но и минимально достаточную техническую спецификацию, чтобы команда могла без двусмысленностей спроектировать frontend, backend, инфраструктуру, аналитику и QA-покрытие.

#### 1.6.1. Manifest

Необходимо создать и подключить web app manifest.

Manifest должен содержать:

- `name`;
- `short_name`;
- `description`;
- `start_url`;
- `scope`;
- `display: standalone`;
- `background_color`;
- `theme_color`;
- набор иконок в необходимых размерах;
- при необходимости `screenshots` и дополнительные поля, если они понадобятся для улучшения install experience.

Требования:

- manifest должен относиться к `my.mentala.app`;
- стартовый маршрут должен вести в пользовательскую часть приложения, а не на лендинг;
- `scope` должен ограничивать PWA только доменом и маршрутами приложения;
- необходимо явно определить поведение при открытии авторизованного и неавторизованного пользователя;
- если пользователь не авторизован, `start_url` должен корректно приводить его к экрану входа без потери installable-сценария;
- если пользователь авторизован, приложение после запуска должно открывать основной рабочий маршрут без лишних промежуточных экранов;
- иконки должны быть подготовлены под Android, iOS, desktop и общую PWA-установку;
- необходимо проверить корректное отображение имени приложения, иконки, splash screen и стартового цвета на поддерживаемых устройствах.

#### 1.6.2. Service Worker

Необходимо внедрить service worker.

Service worker нужен для:

- регистрации PWA как installable приложения;
- поддержки Web Push;
- возможности контролировать кэширование ресурсов;
- корректной фоновой обработки push-событий.

Требования:

- service worker должен регистрироваться только в клиентской среде;
- логика регистрации должна быть устойчивой к повторным инициализациям;
- ошибки регистрации должны логироваться;
- должна быть предусмотрена стратегия обновления service worker без разрушения пользовательского опыта;
- необходимо зафиксировать стратегию кеширования: какие ресурсы допускается кешировать, а какие всегда должны идти в сеть;
- нельзя кешировать чувствительные API-ответы, пользовательские токены, персональные данные и динамические данные, которые могут устаревать критично быстро;
- необходимо определить поведение приложения при offline или poor network сценариях;
- необходимо предусмотреть безопасный механизм инвалидирования старых кешей после релиза новой версии.

#### 1.6.3. HTTPS и окружение

PWA и Web Push должны работать только в безопасном окружении.

Требования:

- production должен работать по HTTPS;
- staging и preview-среды должны быть проверены отдельно;
- локальная разработка должна поддерживать отладочный сценарий, допустимый для браузеров.

#### 1.6.4. Установка PWA

Необходимо реализовать пользовательский сценарий установки PWA.

Решение:

- не показывать агрессивную всплывашку на лендинге;
- не продвигать установку до того, как пользователь увидел ценность продукта;
- предлагать установку внутри `my.mentala.app`;
- момент показа продумать отдельно, например после входа, после нескольких успешных сессий или после использования ключевых функций.

Требования:

- для Android реализовать `native-first` app-promo flow без forced redirect: `Открыть приложение` при подтверждённой установке related app или `Google Play` как install path;
- для iOS реализовать отдельную визуальную инструкцию, объясняющую, как добавить Mentala на экран Домой;
- предусмотреть возможность скрыть подсказку после установки или после явного отказа.

##### 1.6.4.1. Продуктовые правила показа установки

Необходимо заранее зафиксировать базовые правила показа install prompt или install-инструкции.

Рекомендуемая политика первого этапа:

- не показывать предложение установки на лендинге;
- не показывать предложение установки до авторизации;
- не показывать предложение установки в первые секунды первого визита;
- показывать установку только после того, как пользователь уже совершил хотя бы одно осмысленное действие внутри продукта;
- после отказа пользователя не повторять показ слишком агрессивно;
- состояние показа и отказа должно сохраняться, чтобы не раздражать пользователя повторяющимися сценариями.

Техническое требование:

- frontend должен иметь возможность управлять частотой показа install-подсказки через локальное состояние или серверный флаг;
- точный продуктовый триггер показа может быть уточнен отдельно после первых тестов.

#### 1.6.5. Отображение в app-like режиме

PWA должно открываться с интерфейсом, максимально приближенным к приложению.

Требования:

- использовать `display: standalone`;
- проверить визуальное поведение status bar, safe areas и layout на iOS;
- проверить отсутствие лишних браузерных панелей после установки;
- при необходимости доработать отступы, верхние и нижние зоны интерфейса отдельно для PWA-режима.

#### 1.6.6. Web Push на PWA

PWA должно быть подготовлено для приема Web Push уведомлений.

Требования:

- использовать Firebase Cloud Messaging как единый канал отправки push-уведомлений;
- зарегистрировать web client в Firebase;
- подключить уже созданный публичный VAPID key на frontend и использовать его при получении web push token;
- реализовать получение web token;
- сохранять token на сервере как отдельный push endpoint;
- предусмотреть пере-регистрацию token при его изменении;
- предусмотреть деактивацию невалидных и устаревших token.

##### 1.6.6.1. Клиентский сценарий регистрации Web Push

На frontend необходимо реализовать следующий сценарий:

1. проверить поддержку PWA и Web Push в текущем браузере;
2. проверить, находится ли пользователь в поддерживаемом окружении;
3. запросить разрешение на уведомления только в подходящий момент, а не при первом открытии страницы;
4. зарегистрировать service worker;
5. получить web push token через Firebase Cloud Messaging;
6. отправить token на backend;
7. сохранить у себя факт успешной регистрации endpoint;
8. подписаться на сценарий обновления token и повторной регистрации при необходимости.

##### 1.6.6.2. Требования к UX включения уведомлений

Необходимо соблюдать следующие правила:

- не запрашивать разрешение на push при первом заходе на сайт;
- не запрашивать разрешение до того, как пользователь понял ценность уведомлений;
- объяснять пользователю, зачем именно Mentala просит доступ к уведомлениям;
- для iOS предусмотреть отдельный UX-путь, если уведомления доступны только после установки PWA на экран Домой;
- если браузер или платформа не поддерживают Web Push, необходимо показать понятный fallback без ложных обещаний.

### 1.7. Архитектурный принцип

PWA не должно становиться отдельным продуктом с отдельной логикой.

Принцип внедрения:

- один backend;
- единая бизнес-логика;
- единая учетная запись пользователя;
- единая система уведомлений;
- PWA рассматривается как еще один клиентский канал доступа.

### 1.8. Нефункциональные требования

Необходимо обеспечить:

- корректную работу на Android, iPhone, iPad и desktop;
- корректную деградацию на неподдерживаемых браузерах;
- отсутствие критичных визуальных дефектов после установки;
- отсутствие дублей уведомлений в продуманном сценарии маршрутизации;
- прозрачное логирование и диагностику проблем с регистрацией PWA и push;
- устойчивость к повторной установке, повторной регистрации token и смене пользователя на одном устройстве;
- безопасную обработку logout-сценариев;
- возможность контролируемо расширить решение после релиза без полной переработки архитектуры.

### 1.9. Что не входит в текущий этап

На текущем этапе не закладываются:

- пользовательский выбор точки доставки уведомлений в настройках;
- сложные пользовательские сценарии ручного управления каналами push;
- отдельный installable лендинг;
- полная продуктовая полировка всех edge case сценариев установки на всех браузерах.

Это может быть добавлено позже отдельным этапом.

## 1.10. Детализированная техническая спецификация первого этапа

### 1.10.1. Изменения на frontend

На frontend необходимо реализовать следующие блоки:

- подключение manifest и PWA-настроек;
- регистрация service worker;
- UI для предложения установить приложение;
- UI для iOS-инструкции по добавлению на экран Домой;
- UI для объяснения пользы push-уведомлений;
- сценарий запроса разрешения на уведомления;
- получение и обновление web push token;
- отправка token на backend;
- корректная очистка клиентского состояния при logout;
- повторная регистрация endpoint после повторного login.

### 1.10.2. Изменения на backend

На backend необходимо реализовать:

- таблицу или сущность для хранения push endpoints;
- endpoint регистрации push endpoint;
- endpoint деактивации push endpoint;
- серверную логику выбора primary endpoint;
- обработку невалидных token;
- обработку logout и смены пользователя;
- аудит событий регистрации, деактивации и маршрутизации;
- механизм безопасного обновления endpoint при повторной регистрации того же клиента.

### 1.10.3. Изменения в инфраструктуре и конфигурации

Необходимо подготовить:

- Firebase Web App конфигурацию;
- публичный VAPID key для frontend;
- server-side конфигурацию отправки push через Firebase;
- переменные окружения для production, staging и локальной разработки;
- политику логирования ошибок регистрации, ошибок отправки и случаев дедупликации.

#### 1.10.3.1. Что уже подтверждено по текущему Firebase проекту

На текущий момент в Firebase уже зарегистрировано Web App приложение для проекта Mentala.

Это означает, что базовый шаг регистрации web app уже выполнен, и проект уже имеет:

- `apiKey`;
- `authDomain`;
- `projectId`;
- `storageBucket`;
- `messagingSenderId`;
- `appId`;
- `measurementId`, если используется Analytics.

Практический вывод:

- повторно создавать Firebase Web App не требуется, если используется именно текущий проект `mentala-prod`;
- эти параметры должны быть вынесены в переменные окружения frontend-приложения;
- конфигурация должна использоваться только как клиентская конфигурация Firebase Web SDK, а не как server secret.

#### 1.10.3.2. Прямые действия владельца проекта в Firebase Console

Помимо кода, владелец проекта должен отдельно проверить и, при необходимости, выполнить следующие действия в Firebase Console:

1. Убедиться, что используется правильный Firebase Web App для `my.mentala.app`.
2. Убедиться, что VAPID key pair уже создан в `Project settings -> Cloud Messaging -> Web configuration -> Web Push certificates`.
3. Скопировать публичный VAPID key для frontend.
4. Убедиться, что server-side часть проекта использует корректные учетные данные Firebase Admin SDK для отправки push.
5. Проверить, что production-домен приложения работает по HTTPS.
6. При необходимости проверить, нужен ли Analytics именно в PWA-сценарии, чтобы не подключать лишний код без продуктовой необходимости.

Важно:

- шаг создания VAPID key уже выполнен;
- повторно генерировать VAPID key не требуется, если текущая пара ключей будет использоваться в проекте и не планируется ее ротация;
- `firebaseConfig` из консоли не заменяет сам публичный VAPID key и не заменяет server credentials для Firebase Admin SDK.

### 1.10.4. Минимальные backend endpoints

На первом этапе рекомендуется предусмотреть следующие backend routes:

- `POST /api/push/endpoints/register`;
- `POST /api/push/endpoints/deactivate`;
- `POST /api/push/endpoints/deactivate-current-user`;
- `POST /api/push/test`, только для внутреннего использования или dev-окружения;
- `GET /api/push/endpoints/me`, если потребуется диагностика текущих endpoint пользователя.

Назначение:

- `register` - создать новый endpoint или обновить существующий;
- `deactivate` - деактивировать конкретный endpoint;
- `deactivate-current-user` - массово выключить активные push endpoint текущего пользователя в рамках заданного сценария, например при logout;
- `test` - отправить тестовое уведомление в контролируемом окружении;
- `me` - вернуть список endpoint текущего пользователя для отладки и диагностики.

### 1.10.5. Минимальный payload регистрации endpoint

Backend должен принимать структурированный payload. На первом этапе рекомендуется следующая форма:

```json
{
  "userId": "string",
  "platformFamily": "ios | android | desktop",
  "channelType": "pwa | native",
  "pushToken": "string",
  "installationId": "string",
  "deviceFingerprint": "string | null",
  "appVersion": "string | null",
  "userAgent": "string | null",
  "locale": "string | null",
  "timezone": "string | null",
  "notificationsEnabled": true
}
```

Примечания:

- финальный состав полей может быть скорректирован после проектирования API;
- `installationId` обязателен, потому что без него будет слишком трудно различать переустановки и повторные регистрации;
- `deviceFingerprint` не должен использоваться как единственный источник истины;
- `userId` может извлекаться из авторизации, а не из тела запроса, если это соответствует принятой серверной архитектуре.

#### 1.10.5.1. Что не нужно путать

Нужно явно различать три разные сущности:

- `firebaseConfig` для frontend;
- публичный `VAPID key` для получения web push token;
- server credentials для Firebase Admin SDK.

Правило:

- `firebaseConfig` используется на клиенте для инициализации Firebase Web SDK;
- `VAPID key` используется на клиенте при вызове `getToken()` для Web Push;
- server credentials используются только на backend для отправки push через Firebase.

Эти сущности нельзя смешивать между собой.

Практическое правило размещения:

- `firebaseConfig` нужно вынести в env-переменные frontend-приложения;
- публичный `VAPID key` также нужно вынести в env-переменную frontend-приложения;
- server credentials нельзя хранить во frontend env и нельзя отдавать в браузер.

Рекомендуемый минимальный вариант env на frontend для текущего этапа:

- `VITE_FIREBASE_VAPID_PUBLIC_KEY`.

Если остальные параметры Firebase Web App уже хранятся и используются в проекте другим способом, дублировать их в рамках этого документа не требуется.

Если проект использует Nuxt runtime config вместо прямых `VITE_*`, допускается аналогичная схема через публичный runtime config, но публичный VAPID key все равно должен попадать именно во frontend-часть приложения, потому что он используется в браузере при вызове `getToken()`.

### 1.10.6. Минимальная SQL-модель

Ниже базовый ориентир для проектирования таблицы. Это не финальная миграция, а отправная точка.

```sql
create table push_endpoints (
  id bigserial primary key,
```

### 1.10.7. Правила обновления записи endpoint

При повторной регистрации endpoint backend не должен слепо создавать дубликаты.

Необходимо определить стратегию upsert-обновления:

- если пришел тот же `installation_id` и тот же `user_id`, обновить существующую запись;
- если изменился `push_token`, сохранить новый token и деактивировать устаревший, если это отдельная запись;
- если тот же `installation_id` внезапно привязан к другому `user_id`, предыдущую привязку необходимо корректно деактивировать и перевести устройство в новый пользовательский контекст;
- если пользователь разлогинился, endpoint не должен продолжать считаться активным для старого пользователя.

### 1.10.8. Logout и смена пользователя

Это обязательный блок, который нельзя оставлять неформализованным.

Требования:

- при logout PWA должен отправлять сигнал на backend о деактивации текущего endpoint или о снятии связи endpoint с текущим пользователем;
- если после logout на том же устройстве логинится другой пользователь, endpoint должен быть перепривязан к новому пользователю без риска, что уведомления уйдут старому;
- нельзя допускать сценарий, в котором один и тот же активный mobile endpoint остается одновременно привязан к двум пользователям;
- при невозможности точно перепривязать endpoint безопаснее временно деактивировать его до следующей успешной регистрации.

## 2. Синхронизация push-уведомлений между PWA и нативным приложением

### 2.1. Проблема

После появления нативных приложений возможен сценарий, при котором у одного и того же пользователя одновременно установлены:

- PWA Mentala;
- нативное iOS-приложение Mentala;
- нативное Android-приложение Mentala.

Если не управлять этим на сервере, пользователь может получать дубли уведомлений.

Пример проблемы:

- одно и то же уведомление уходит в PWA;
- то же самое уведомление уходит в нативное приложение;
- пользователь получает два одинаковых push-уведомления.

Это недопустимо.

### 2.2. Базовый принцип решения

Управление доставкой push-уведомлений должно происходить на стороне сервера.

Необходимо ввести единый реестр push endpoints, где каждый канал доставки хранится отдельно.

Push endpoint - это отдельная запись о конкретной установке и конкретном канале доставки, например:

- PWA на iPhone;
- нативное приложение на iPhone;
- PWA на Android;
- нативное приложение на Android;
- desktop browser.

### 2.3. Упрощенная продуктовая политика

Принято решение не давать пользователю ручной выбор точки доставки уведомлений в настройках.

Вместо этого используется серверный приоритет доставки.

Правило:

- если у пользователя на устройстве активен нативный канал, отправляем уведомление туда;
- если нативного канала нет, но есть PWA, отправляем уведомление в PWA;
- если речь идет о desktop, desktop web рассматривается как отдельный канал;
- если активны несколько каналов на разных устройствах и это не приводит к дублям одного и того же мобильного устройства, доставка допускается.

### 2.4. Важное уточнение по разным пользователям

Нужно учитывать сценарий, при котором на одном устройстве или в рамках одной экосистемы задействованы разные учетные записи.

Принятое правило:

- дедупликация нужна только тогда, когда совпадают и устройство, и пользователь;
- если в PWA авторизован один пользователь, а в нативном приложении другой пользователь, это не считается дублем;
- в таком сценарии отправка уведомлений двум разным пользователям допустима.

Иными словами:

- не дублируем уведомления только для одного и того же `userId` на одном и том же устройстве или в рамках одной и той же мобильной платформенной установки, если одновременно есть и PWA, и native;
- если `userId` различается, каналы считаются независимыми.

### 2.5. Предлагаемая модель данных

Необходимо ввести сущность, например `push_endpoints`.

Рекомендуемые поля и смысл каждого поля:

- `id` - уникальный идентификатор записи endpoint;
- `user_id` - идентификатор пользователя, которому в данный момент принадлежит endpoint;
- `platform_family` - `ios` | `android` | `desktop` для правил маршрутизации;
- `channel_type` - `native` | `pwa` для определения приоритета;
- `push_token` - token конкретного канала доставки;
- `installation_id` - стабильный идентификатор конкретной установки приложения или PWA;
- `device_fingerprint` - вспомогательный идентификатор устройства, если его использование допустимо;
- `app_build` или `app_version` - версия клиента для диагностики;
- `user_agent` - строка user agent для дополнительной диагностики;
- `locale` - локаль клиента;
- `timezone` - часовой пояс клиента;
- `notifications_enabled` - доступно ли получение уведомлений с точки зрения клиента;
- `is_active` - может ли endpoint использоваться для отправки прямо сейчас;
- `is_primary` - выбран ли endpoint как основной канал доставки в своей платформенной группе;
- `last_seen_at` - последнее подтвержденное использование endpoint;
- `last_push_at` - время последней отправки push на endpoint;
- `created_at` - дата создания записи;
- `updated_at` - дата последнего обновления записи.

Примечания:

- `installation_id` нужен для различения установок;
- `platform_family` нужен для грубой платформенной маршрутизации;
- `channel_type` нужен для определения приоритета;
- `is_primary` нужен как итог вычисленной сервером приоритетности;
- конкретный набор полей может быть скорректирован после проектирования backend-схемы.

### 2.6. Правило приоритета доставки

Для mobile-платформ вводится приоритет:

#### iOS

1. `native`
2. `pwa`

#### Android

1. `native`
2. `pwa`

#### Desktop

1. `pwa` или browser web endpoint

Это означает:

- если для одного и того же пользователя на iOS активны и `native`, и `pwa`, то primary endpoint должен быть `native`;
- `pwa` в таком случае переводится в secondary или muted состояние для мобильной доставки;
- аналогичное правило действует для Android.

### 2.7. Серверная логика маршрутизации

Необходимо реализовать серверную функцию выбора целевого push endpoint.

Логика высокого уровня:

1. получить все активные push endpoints пользователя;
2. сгруппировать их по `platform_family`;
3. внутри mobile-платформ применить правило приоритета `native > pwa`;
4. исключить вторичные mobile endpoints для того же пользователя, если они потенциально дублируют доставку;
5. сохранить desktop endpoints как независимый канал, если это не нарушает продуктовую политику;
6. отправлять push только в выбранные primary endpoints.

#### 2.7.1. Практическое правило выбора

На первом этапе можно использовать следующую практическую схему:

- для каждого `user_id` собрать все активные endpoint;
- отдельно рассмотреть `ios`, `android`, `desktop`;
- внутри `ios` выбрать один primary endpoint по правилу `native > pwa`;
- внутри `android` выбрать один primary endpoint по правилу `native > pwa`;
- на desktop оставить активный browser или PWA endpoint как отдельный канал, если нет отдельного продуктового запрета;
- если один и тот же пользователь одновременно присутствует в PWA и native на одной mobile-платформе, отправлять push только в primary endpoint;
- если `user_id` отличается, каналы считать независимыми.

### 2.8. Правило дедупликации

Дедупликация должна срабатывать по совокупности факторов:

- одинаковый `user_id`;
- одинаковая платформенная группа, например `ios` или `android`;
- наличие одновременно `native` и `pwa` endpoint, относящихся к одному и тому же пользовательскому сценарию доставки.

Не нужно считать дублем:

- разные `user_id`;
- desktop и mobile как независимые сценарии, если продуктово это допустимо;
- разные устройства одного пользователя, если решение о мультидевайс доставке сохраняется.

### 2.9. Поведение после появления нативного приложения

После выхода нативного приложения система должна поддерживать мягкую миграцию с PWA на native.

Рекомендуемое поведение:

- пользователь устанавливает PWA и получает push через PWA;
- позже пользователь устанавливает нативное приложение;
- после входа в тот же аккаунт нативное приложение регистрирует свой push endpoint;
- сервер обнаруживает более приоритетный канал;
- mobile PWA endpoint этого же пользователя переводится в secondary или muted состояние;
- дальнейшие мобильные push-уведомления отправляются в native.

Дополнительное требование:

- перевод PWA endpoint в secondary или muted состояние должен происходить не по факту установки native-приложения как таковой, а по факту успешной регистрации native endpoint на backend для того же пользователя;
- это защищает систему от ложного отключения PWA в ситуации, когда native-приложение установлено, но пользователь еще не вошел в аккаунт или не включил уведомления.

### 2.10. Что важно не делать

Необходимо явно избежать следующих решений:

- не отправлять одно и то же уведомление во все token подряд без маршрутизации;
- не перекладывать дедупликацию только на клиент;
- не вводить на текущем этапе ручной выбор канала уведомлений в настройках;
- не полагаться только на свежесть token как на средство борьбы с дублями.

### 2.11. Требование к диагностике

Нужно предусмотреть диагностическую информацию для каждого push endpoint.

Минимально требуется логировать:

- источник регистрации endpoint;
- user id;
- platform family;
- channel type;
- результат выбора primary endpoint;
- факт отключения secondary endpoint;
- факт ошибки доставки;
- факт невалидности token.

### 2.12. Итоговое правило системы

Итоговая политика на текущем этапе такая:

- PWA внедряется как дополнительный клиентский канал;
- до релиза нативных приложений PWA может быть основным мобильным каналом;
- после появления нативного приложения для одного и того же пользователя на той же мобильной платформе приоритет всегда у native;
- если `userId` в PWA и native различается, это не считается дублем, и доставка допускается;
- пользователь не управляет выбором точки доставки вручную;
- сервер является единственным источником истины для маршрутизации push-уведомлений.
