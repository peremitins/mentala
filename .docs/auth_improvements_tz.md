# ТЗ: Доработка системы авторизации Mentala

## 1. Обзор

Данное ТЗ описывает доработку системы авторизации для обеспечения:

- Email-верификации при регистрации через email+пароль
- Линковки аккаунтов Google и email+пароль
- Установки пароля для аккаунтов, созданных через Google
- Защиты от брутфорса и спама

**КРИТИЧНО:** Все описанные функции должны работать на всех платформах:

- **Web** (браузеры)
- **iOS** (через Capacitor)
- **Android** (через Capacitor)

При реализации необходимо учитывать особенности каждой платформы (хранение токенов, работа с cookies, нативные OAuth-флоу и т.д.).

## 2. Текущее состояние

### 2.1. Структура БД

**Таблица `users`:**

- `email` (unique, nullable)
- `emailVerifiedAt` (timestamp, nullable) — есть поле, но не используется
- `passwordHash` (text, nullable)
- `name`, `avatarUrl`, `locale`, и др.

**Таблица `oauthAccounts`:**

- `userId` (FK → users.id)
- `provider` ('google' | 'vk')
- `providerUserId` (не unique на уровне БД, но должно быть уникально для provider+providerUserId)
- **Для MVP:** НЕ храним `accessToken`, `refreshToken`, `expiresAt` (не нужны, если не работаем с Google API)

### 2.2. Текущая логика

**Регистрация через email+пароль:**

- Создается пользователь с `passwordHash`, но без `emailVerifiedAt`
- Нет проверки верификации email перед входом

**Вход через Google:**

- Если найден `oauthAccounts` по `provider` + `providerUserId` → логин
- Если не найден, но есть пользователь с таким `email` → линковка (создание `oauthAccounts`)
- Если пользователя нет → создание нового пользователя и `oauthAccounts`

**Проблемы:**

1. Нет верификации email при регистрации
2. Нет возможности установить пароль для Google-аккаунтов
3. Нет защиты от дублей аккаунтов (не unique constraint на `providerUserId`)
4. Нет защиты от брутфорса кодов верификации

## 3. Требования

### 3.0. Нативный Google Sign-In для мобильных (iOS/Android)

**Цель:** убрать зависимость от web-redirect на мобилках и обеспечить стабильный вход в сторах.

**Требования:**

1. **Мобильные платформы используют нативный вход:**

   - iOS/Android → нативный Google Sign-In через Capacitor плагин/SDK.
   - Web → остаётся текущий web OAuth redirect.

2. **Отдельный backend endpoint для нативного входа:**

   - `POST /api/auth/google/native`
   - Body: `{ idToken: string }`
   - Сервер валидирует ID Token у Google и создаёт сессию (как в web-callback).

3. **Отдельные OAuth клиенты в Google Cloud Console:**

   - Web (Dev), Web (Prod)
   - Android (package name + SHA-1)
   - iOS (bundle id + team id при необходимости)

4. **Платформенный switch на фронте:**

   - `loginWithGoogle()` должен сам решать, какой способ использовать:
     - Web → redirect на `/api/auth/google/start`
     - iOS/Android → нативный sign-in → `POST /api/auth/google/native`

5. **Конфигурация через env:**

   - Dev и Prod должны использовать разные OAuth client ids.
   - Все значения только через env (без хардкода).

6. **UX/ошибки:**
   - Ошибки нативного входа должны показываться через toast.
   - Нельзя показывать технические детали пользователю.

**Важно:** WebView для Google OAuth на мобилках не использовать.

### 3.1. Email-верификация при регистрации

#### 3.1.1. Процесс регистрации

**Шаг 1: Заполнение формы**

- Пользователь вводит: `email`, `password`, `name` (опционально)
- При отправке формы:
  - **Нормализация email:** `email.toLowerCase().trim()` (всегда первой, до всех проверок, влияет на уникальность, rate limit ключи и предотвращает дубли)
  - Валидация email и пароля
  - **Проверка существующего пользователя:**
    - Если пользователь с таким email уже существует и `emailVerifiedAt = null`:
      - НЕ создавать нового пользователя
      - **Обработка пароля (критично):**
        - **Обязательно просим пароль снова** (даже если TTL предыдущего истёк)
        - Хешируем новый пароль через `argon2`
        - **Заменяем** предыдущий `passwordHash` в Redis (overwrite ключ `auth:email_verification_password:{email}`)
        - Если предыдущего `passwordHash` нет (TTL истёк) → создаём новый
        - **Важно:** При успешной верификации будет установлен **последний введенный пароль**
      - Генерируем новый код (с учётом rate limit)
      - Отправляем код на email
      - Переводим пользователя на шаг ввода кода
    - Если пользователь не существует:
      - Создание записи в БД с `emailVerifiedAt = null`
      - **Хранение пароля до верификации:**
        - Хешируем пароль через `argon2`
        - Сохраняем `passwordHash` в Redis с ключом `auth:email_verification_password:{email}` и TTL 15 минут
        - **НЕ сохраняем passwordHash в БД до успешной верификации**
        - После верификации переносим `passwordHash` из Redis в БД
      - Генерация 6-значного кода
      - Отправка кода на email через Яндекс SMTP
      - Сохранение кода в Redis с TTL (см. параметры ниже)
  - **Возврат одинакового сообщения для защиты от enumeration:**
    - Всегда: `{ "message": "Мы отправили письмо с кодом подтверждения.\nЕсли вы уже использовали Mentala ранее, вы сможете войти или восстановить доступ" }`
    - **НЕ возвращаем** `email`, `requiresVerification`, `success` и другие детали

**Шаг 2: Ввод кода верификации**

- Пользователь переходит на экран ввода кода
- Показывается поле для ввода 6-значного кода
- Показывается email, на который отправлен код
- Показывается таймер обратного отсчета для повторной отправки
- Показывается количество оставшихся попыток

**Шаг 3: Завершение регистрации**

- При успешном вводе кода:
  - Устанавливается `emailVerifiedAt = now()`
  - **Загружаем `passwordHash` из Redis** (`auth:email_verification_password:{email}`)
  - **Сохраняем `passwordHash` в БД** (перенос из временного хранилища)
  - **Удаляем `passwordHash` из Redis** (больше не нужен)
  - **Код инвалидируется (удаляется из Redis) — одноразовое использование**
  - **Повторное использование кода невозможно**
  - Создается сессия
  - Активируется Trial подписка
  - Пользователь перенаправляется в приложение

#### 3.1.2. Параметры кода верификации

- **Формат:** 6 цифр (000000-999999)
- **Срок действия:** 15 минут (TTL в Redis)
- **Количество попыток ввода:** 5 попыток на один код
- **Интервал между повторными отправками:** 60 секунд (rate limit)
- **Хранение:** Redis с ключом `auth:email_verification:{email}` (сохраняем хеш кода и метаданные)
- **Неймспейс:** Все Redis-ключи для авторизации используют префикс `auth:` для унификации и упрощения мониторинга
- **Поведение при повторной регистрации/ресенде (MVP):**
  - Используем один активный набор ключей на email: `auth:email_verification:{email}` и `auth:email_verification_password:{email}`
  - При ресенде/повторной регистрации данные **перезаписываются**
  - Активным считается **последний** отправленный код и **последний** введенный пароль

**Структура в Redis:**

```json
{
  "codeHash": "sha256(code + secret)",
  "attempts": 0,
  "expiresAt": "timestamp",
  "createdAt": "timestamp"
}
```

**Важно:** Используем `sha256(code + secret)` вместо `argon2` для одноразовых кодов. Argon2 предназначен для паролей и избыточен для 6-значных кодов с коротким TTL (15 минут).

**Требования к secret management:**

- Secret хранится в переменных окружения (env)
- Должна быть возможность ротации secret без нарушения работы (graceful migration)
- Сравнение хешей выполняется в constant-time (защита от timing attacks)
- Использовать криптографически стойкие функции сравнения (например, `crypto.timingSafeEqual` в Node.js)

#### 3.1.3. Rate limiting

**По IP:**

- Максимум 5 отправок кода в час с одного IP
- Ключ: `auth:rate_limit:email_verification:ip:{ip}`

**По email:**

- Максимум 3 отправки кода в час с одного email
- Ключ: `auth:rate_limit:email_verification:email:{email}`

**По комбинации IP+email:**

- Дополнительная защита от злоупотреблений

#### 3.1.4. UI/UX

**Экран ввода кода:**

- Поле для ввода 6-значного кода (автоматический переход между полями или единое поле с маской)
- Кнопка "Отправить код повторно" (disabled на 60 секунд с таймером)
- Отображение количества оставшихся попыток
- Кнопка "Изменить email" (возврат на шаг 1)
- Индикатор загрузки при проверке кода

**Сообщения об ошибках:**

- "Неверный код" — при неправильном вводе
- "Код истек" — при истечении TTL
- "Превышено количество попыток" — при достижении лимита
- "Слишком много запросов" — при rate limit

### 3.2. Линковка аккаунтов при входе через Google

#### 3.2.1. Критические правила безопасности

**ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА:**

- ❌ **Никогда не создавать новый аккаунт, если email уже существует**
- ❌ **Никогда не линковать без подтверждения владения аккаунтом**
- ✅ **Линковка выполняется только после доказательства владения существующим аккаунтом**

**Обоснование:**
Email — не секрет. Google подтверждает владение Google-аккаунтом, но не доказывает владение локальным аккаунтом Mentala. Автоматическая линковка по совпадению email создает риск компрометации аккаунта, если кто-то получит доступ к Google-аккаунту с тем же email.

#### 3.2.2. Алгоритм линковки

**При входе через Google:**

1. **Получение данных от Google:**

   - `sub` (providerUserId)
   - `email` (нормализуем: `toLowerCase().trim()`)
   - `email_verified` (может быть `false` в редких случаях)
   - `name`, `picture`
   - **Обработка `email_verified = false`:**
     - Если `email_verified = false` → **НЕ создаем аккаунт и НЕ линкуем**
     - Возвращаем ошибку: "Google не подтвердил ваш email. Подтвердите email в аккаунте Google и попробуйте снова."
     - Это защита от создания аккаунтов с неподтвержденными email

2. **Поиск существующего OAuth-аккаунта (приоритет):**

   - **ВАЖНО:** Сначала ищем по `oauthAccounts.provider = 'google'` + `providerUserId = sub`
   - **Если найден:** логин в этот аккаунт (обновляем данные, создаем сессию)
     - **Игнорируем email** из Google-токена, даже если он отличается
     - Это предотвращает неожиданный логин в чужой аккаунт
   - Если не найден → переходим к шагу 3

3. **Проверка существующего пользователя по email:**

   - Ищем пользователя по `users.email = email`
   - **Если найден:**
     - **НЕ линкуем автоматически** (независимо от `emailVerifiedAt`)
     - **Генерируем `linkingToken`:**
       - UUID v4 (128 бит энтропии) или криптографически стойкая случайная строка (минимум 32 символа)
       - Используется как ключ для доступа к временным данным
     - Сохраняем данные Google (sub, email, name, picture) во временное хранилище Redis с ключом `auth:oauth_link:{linkingToken}` и TTL 15 минут
       - **Сопоставление:** `linkingToken` → ключ Redis `auth:oauth_link:{linkingToken}`
       - **Защита от подбора:** высокая энтропия (UUID v4), короткий TTL (15 минут), rate limiting на verify endpoints
       - **Примечание (опционально на будущее):** Можно упростить схему, храня код верификации в том же объекте Redis вместо отдельного ключа `auth:oauth_link_code:{linkingToken}`. Это уменьшит количество ключей и точек рассинхронизации, но потребует больше логики в одном месте.
     - **НЕ сохраняем accessToken/refreshToken** (не нужны для MVP, только для работы с Google API)
     - Возвращаем специальный статус: `requiresAccountLinking: true, linkingToken: string`
     - Показываем экран подтверждения владения аккаунтом (см. раздел 3.2.5)
     - **Важно:** `linkingToken` хранится только на клиенте (in-memory/state), НЕ в localStorage
     - **Важно:** `linkingToken` одноразовый, TTL = 15 минут, максимум 5 попыток подтверждения на один `linkingToken`
   - **Если не найден:**
     - **Проверяем `email_verified` от Google:**
       - Если `email_verified = false` → ошибка (см. шаг 1)
     - Создаем нового пользователя:
       - `email = email` (уже нормализован)
       - `emailVerifiedAt = now()` (Google верифицирует email, `email_verified = true`)
       - `passwordHash = null`
       - `name`, `avatarUrl`, `locale`
     - Создаем `oauthAccounts`
     - Активируем Trial подписку
     - Создаем сессию

4. **Защита от дублей:**
   - Добавить unique constraint на `(provider, providerUserId)` в таблице `oauthAccounts`
   - **Поведение при конфликте:**
     - Если `providerUserId` уже привязан к существующему аккаунту → логин в этот аккаунт (обновляем данные, создаем сессию)
     - Если попытка привязать `providerUserId` к другому аккаунту (отличному от того, к которому он уже привязан) → security error + логирование события

#### 3.2.3. Обработка неподтвержденного email

**КРИТИЧНО:** Если пользователь с таким email существует, но `emailVerifiedAt = null`:

- ❌ **НЕ создавать новый аккаунт** (это гарантированно создаст дубликаты)
- ✅ Показать флоу подтверждения:
  - "Мы нашли аккаунт с этим email. Подтвердите email или войдите по паролю, чтобы привязать Google."
  - Вариант A: Верификация email (отправка кода на email)
  - Вариант B: Вход по паролю (если пароль уже установлен)
- После подтверждения → разрешаем Google-линковку

**Обоснование:** Создание нового аккаунта при совпадении email создает дубликаты, проблемы с данными, подписками и саппортом. Всегда используем существующий аккаунт и требуем подтверждения владения.

#### 3.2.4. Подтверждение владения аккаунтом

**КРИТИЧЕСКИЕ ИНВАРИАНТЫ:**

1. **Инвариант №1 — один linkingToken = один email:**

   - `linkingToken` всегда привязан ровно к одному email и одному `providerUserId`
   - Использование `linkingToken` с другим email запрещено и считается invalid
   - Это защищает от "подмены шага" на фронте и упрощает валидацию на бэке

2. **Инвариант №2 — linking ≠ login:**
   - Подтверждение линковки не является логином до момента успешного завершения процесса и создания сессии
   - Это предотвращает случайную авторизацию после проверки пароля, но до линковки
   - Не должно появляться "полуавторизованного" состояния

**Процесс линковки после подтверждения:**

1. **Пользователь выбирает способ подтверждения:**

   - **Вариант A: Ввод пароля** (если `passwordHash != null`)
     - Пользователь вводит пароль существующего аккаунта
     - Проверяем через `argon2.verify`
   - **Вариант B: Email-код** (если `passwordHash = null` или пользователь забыл пароль)
     - Отправляем 6-значный код на email
     - Пользователь вводит код
     - Проверяем код (аналогично верификации при регистрации)

2. **После успешного подтверждения:**

   - Загружаем временные данные из Redis по `linkingToken`
   - **Валидация инварианта №1:** Проверяем, что email из `linkingToken` совпадает с email пользователя
   - Проверяем, что `providerUserId` не привязан к другому пользователю
   - **Только после всех проверок:** Создаем `oauthAccounts` для существующего пользователя
   - Устанавливаем `emailVerifiedAt = now()` (если еще не установлен)
   - Обновляем `name`, `avatarUrl` если они пустые
   - Удаляем временные данные из Redis
   - **Инвариант №2:** Только сейчас создаем сессию (до этого момента пользователь НЕ авторизован)
   - **Важно:** Разделение сценариев:
     - **Линковка во время логина через Google:** Создаём новую сессию для пользователя, которого подтвердили
     - **Линковка из настроек (уже залогинен):** Не трогаем существующую сессию, только добавляем OAuth-аккаунт
   - **Важно:** Линковка не должна затрагивать сессии других пользователей, даже если email совпадает
   - Логируем успешную линковку

3. **При неудачном подтверждении:**
   - Показываем ошибку
   - Позволяем повторить попытку (с rate limiting)
   - После истечения TTL (15 минут) → требуется новый вход через Google

#### 3.2.5. UI/UX экрана подтверждения линковки

**Экран появляется после входа через Google, если найден существующий аккаунт:**

**Заголовок:** "Привязать Google к существующему аккаунту"

**Текст:**

```
Мы нашли существующий аккаунт с email {email}.
Чтобы привязать Google, подтвердите вход.
```

**Варианты подтверждения:**

1. **Если есть пароль (`passwordHash != null`):**

   - Поле "Пароль" (type="password")
   - Кнопка "Подтвердить"
   - Ссылка "Забыли пароль?" → переключение на вариант 2

2. **Если нет пароля или выбрано "Забыли пароль":**
   - Кнопка "Отправить код на email"
   - После отправки → поле для ввода 6-значного кода
   - Таймер обратного отсчета для повторной отправки (60 секунд)
   - Кнопка "Подтвердить"

**Дополнительно:**

- Кнопка "Отмена" → возврат на экран входа (без линковки, временные данные удаляются)
- Индикатор загрузки при проверке
- Сообщения об ошибках:
  - "Неверный пароль"
  - "Неверный код"
  - "Код истек" (если TTL истек)
  - "Превышено количество попыток"

**Важно:** Экран должен быть понятным и не пугать пользователя. Текст должен объяснять, зачем нужно подтверждение (безопасность аккаунта).

**Обработка закрытия вкладки/перезагрузки:**

- Если пользователь закрыл вкладку или перезагрузил страницу, процесс линковки считается прерванным
- Для продолжения требуется повторный вход через Google
- Это упрощает фронт, убирает "зомби-состояния" и нормально для UX (редкий кейс)

**Сообщения об ошибках:**

- ❌ Нельзя писать: "Аккаунт с таким email уже существует"
- ✅ Вместо этого: "Не удалось подтвердить вход. Попробуйте другой способ."
- Это защита от enumeration и спокойнее для пользователя

### 3.3. Установка пароля для Google-аккаунтов

#### 3.3.1. Доступность функции

- Раздел в настройках: **Настройки → Пользователь → Пароль**
- Показывается только если `passwordHash = null` (аккаунт создан через Google)
- Если пароль уже установлен → показывается раздел "Изменить пароль"

#### 3.3.2. Процесс установки пароля

**Для аккаунтов без пароля:**

1. Пользователь вводит новый пароль
2. Пользователь подтверждает пароль (повторный ввод)
3. Валидация:
   - Минимум 8 символов
   - Без обязательных классов символов (UX > формальный security)
4. При успешной валидации:
   - Хешируем пароль через `argon2`
   - Сохраняем `passwordHash`
   - Показываем успешное сообщение

**Для аккаунтов с паролем:**

1. Пользователь вводит текущий пароль
2. Пользователь вводит новый пароль
3. Пользователь подтверждает новый пароль
4. Валидация:
   - Проверка текущего пароля
   - Валидация нового пароля
5. При успешной валидации:
   - Обновляем `passwordHash`
   - **Инвалидируем все сессии пользователя** (кроме текущей, если нужно)
   - Показываем успешное сообщение

**Важно:** При смене пароля рекомендуется инвалидировать все сессии для безопасности (пользователь должен войти заново на всех устройствах).

#### 3.3.3. UI/UX

**Раздел в настройках:**

- Заголовок: "Пароль" или "Установить пароль" / "Изменить пароль"
- Описание: "Установите пароль для входа по email и паролю" / "Измените пароль для входа"
- Поля ввода с валидацией
- Кнопка "Сохранить"
- Индикатор успеха/ошибки

### 3.4. Вход по email+паролю

#### 3.4.1. Проверка верификации email

**Требование:** Вход возможен только если `emailVerifiedAt` не null.

**Логика:**

1. **Нормализация email:** `email.toLowerCase().trim()`
2. **Rate limiting (защита от брутфорса):**
   - Максимум 10 попыток входа в 15 минут по комбинации IP+email
   - Ключ Redis: `auth:rate_limit:login:ip:{ip}:email:{email}`
   - При превышении → возвращаем общее сообщение: "Неверный email или пароль"
   - Это критично, так как `/email/login` — самый атакуемый endpoint
3. Находим пользователя по email
4. **Защита от enumeration (публичный API):**
   - Всегда возвращаем одинаковое сообщение: "Неверный email или пароль"
   - Независимо от того, существует пользователь или нет, подтвержден email или нет
5. Проверяем, что `emailVerifiedAt` не null
6. Если null → возвращаем:
   - **Только общее сообщение:** "Неверный email или пароль" (защита от enumeration)
   - **НЕ возвращаем флаг `requiresEmailVerification`** (это раскрывает состояние аккаунта)
   - Фронт может показывать нейтральную подсказку ("Если вы не подтверждали email — запросите код") и использовать отдельный endpoint для запроса верификации
7. Проверяем `passwordHash`
8. Если null → возвращаем общее сообщение: "Неверный email или пароль"
9. Проверяем пароль через `argon2.verify`
10. Если пароль неверный → возвращаем общее сообщение: "Неверный email или пароль"
11. Проверяем `isBlocked`
12. Создаем сессию

**Важно:** Детальная информация о статусе аккаунта доступна только после успешной аутентификации (в настройках профиля).

#### 3.4.2. Обработка существующих пользователей (UI-поведение после успешной аутентификации)

**Разделение публичного API и UI:**

- **Публичный API (`POST /api/auth/email/login`):** Всегда возвращает одинаковое сообщение для защиты от enumeration
- **UI после успешной аутентификации:** Может показывать детальную информацию о статусе аккаунта

**Для пользователей без верификации (редкий legacy-кейс):**

- Возможен только если пользователь уже авторизован **не через email+пароль** (например, через Google) или пришел из старой версии
- В настройках профиля показываем: "Email не подтвержден"
- Предлагаем отправить новый код верификации через отдельный безопасный endpoint
- После ввода кода → устанавливаем `emailVerifiedAt`

**Важно:** Это отдельный флоу, доступный только авторизованным пользователям, не раскрывающий информацию через публичный API.

#### 3.5.4. Обработка ошибок отправки email

**КРИТИЧНО:** Все ошибки отправки email должны обрабатываться и логироваться.

**Требования:**

1. **Try-catch в `sendVerificationEmail`:**

   - Обернуть `transporter.sendMail()` в try-catch
   - Логировать все ошибки с контекстом:
     - Email получателя
     - Причина ошибки (error.message, error.code)
     - SMTP настройки (host, port, НЕ пароль)
     - Timestamp
   - Пробрасывать ошибку с понятным сообщением для пользователя

2. **Структурированное логирование:**

   ```typescript
   console.log(`[Email] 📧 Sending verification code`, {
     to: email,
     smtpHost: smtp.host,
     smtpPort: smtp.port,
     timestamp: new Date().toISOString(),
   });

   console.error(`[Email] ❌ Failed to send verification code`, {
     to: email,
     error: errorMessage,
     errorCode: errorCode,
     smtpHost: smtp.host,
     smtpPort: smtp.port,
     timestamp: new Date().toISOString(),
   });
   ```

3. **Очистка при ошибке:**

   - Если отправка не удалась, удалить код из Redis
   - Не оставлять "висячие" коды верификации

4. **Сообщения пользователю:**
   - При ошибке отправки возвращать: `"Не удалось отправить письмо. Попробуйте позже или обратитесь в поддержку."`
   - НЕ раскрывать технические детали (SMTP ошибки, credentials и т.д.)
   - В development режиме можно показывать больше информации для отладки

#### 3.5.5. Возможные причины неполучения писем

**Технические причины:**

1. **SMTP конфигурация неверна или отсутствует:**

   - Отсутствуют переменные окружения
   - Неверные credentials для SMTP сервера
   - Неверный порт или настройки безопасности

2. **SMTP сервер недоступен:**

   - Проблемы с сетью
   - SMTP сервер временно недоступен
   - Firewall блокирует соединение

3. **Провайдер email блокирует письма:**

   - Mail.ru, Gmail и другие провайдеры могут блокировать письма от определенных отправителей
   - Письма попадают в спам
   - Проблемы с репутацией отправителя (SPF, DKIM, DMARC)

4. **Ошибки в коде:**
   - Исключения при отправке не обрабатываются
   - Ошибки "проглатываются" без логирования

**Диагностика:**

- Проверить логи на наличие `[Email] ❌ Failed to send`
- Проверить переменные окружения SMTP
- Проверить доступность SMTP сервера
- Проверить SPF/DKIM/DMARC записи в DNS

### 3.6. Изменения в БД

#### 3.6.1. Миграции

1. **Добавить unique constraint на `oauthAccounts`:**

   ```sql
   ALTER TABLE oauth_accounts
   ADD CONSTRAINT uk_oauth_accounts_provider_user_id
   UNIQUE (provider, provider_user_id);
   ```

2. **Убрать поля `accessToken`, `refreshToken`, `expiresAt` из `oauthAccounts` (для MVP):**

   - Эти поля не нужны, если не работаем с Google API
   - Можно оставить в схеме как nullable, но не заполнять

3. **Уточнение про `email`:**

   - В текущей схеме `email` — `unique, nullable`
   - Для MVP: `email NOT NULL` (всегда есть email, даже у Google-аккаунтов)
   - Если появятся анонимные аккаунты — тогда думать отдельно

4. **Проверить, что `emailVerifiedAt` используется:**

   - Поле уже есть в схеме, но нужно убедиться, что оно обновляется

5. **Индексы (опционально, для производительности):**
   ```sql
   CREATE INDEX IF NOT EXISTS idx_users_email_verified
   ON users(email) WHERE email_verified_at IS NOT NULL;
   ```

#### 3.6.2. Обратная совместимость

**Для существующих пользователей:**

- Пользователи с `emailVerifiedAt = null` и `passwordHash != null`:
  - При следующем входе показываем экран верификации email
  - После верификации разрешаем вход
- Пользователи с `emailVerifiedAt = null` и `passwordHash = null` (Google-аккаунты):
  - Считаем, что email верифицирован Google (`emailVerifiedAt` можно установить при следующем входе через Google)
  - Или оставляем как есть и требуем верификацию при установке пароля

**Рекомендация:** Установить `emailVerifiedAt = now()` для всех существующих пользователей с `passwordHash != null` (одноразовая миграция).

#### 3.6.3. Политика очистки незавершённых аккаунтов

**Проблема:** Аккаунты с `emailVerifiedAt = null` могут накапливаться, если пользователь не завершил верификацию.

**Решение:**

1. **Фоновая задача очистки:**

   - Запускается периодически (например, раз в сутки)
   - Находит пользователей с `emailVerifiedAt = null`, созданных более 24 часов назад
   - Удаляет таких пользователей и связанные данные
   - Очищает связанные временные ключи Redis (`auth:email_verification:*`, `auth:email_verification_password:*`)

2. **Повторная регистрация:**
   - После очистки регистрация пойдёт "с нуля"
   - Это закрывает и UX, и гигиену базы

**Важно:** Политика очистки предотвращает "кладбище" незавершённых аккаунтов и странные UX-ситуации.

#### 3.6.4. Политика удаления аккаунта

**При удалении аккаунта:**

1. **Очистка связанных данных:**

   - Удаление всех `oauthAccounts` пользователя (каскадное удаление или явное)
   - Удаление всех сессий пользователя
   - Удаление всех связанных данных (подписки, привычки, сообщения и т.д.)

2. **Повторное использование email:**

   - После удаления аккаунта email можно использовать повторно для регистрации
   - Новый аккаунт создается как новый пользователь (без связи со старым)

3. **Повторное использование Google-аккаунта:**

   - После удаления аккаунта `providerUserId` можно использовать повторно
   - Новый аккаунт создается как новый пользователь

4. **Важно:**
   - При удалении аккаунта все связи с OAuth-провайдерами разрываются
   - Удаление аккаунта не сохраняет историю линковок и не блокирует повторную регистрацию
   - Пользователь может зарегистрироваться заново с тем же email/Google-аккаунтом
   - Это важно при GDPR-подобных запросах и снимает юридические и UX-вопросы

### 3.7. API Endpoints

#### 3.7.1. Регистрация

**`POST /api/auth/email/register`**

- Body: `{ email: string, password: string, name?: string }`
- Логика:
  - Нормализация email: `email.toLowerCase().trim()`
  - Валидация email и пароля
  - Проверка существующего пользователя:
    - **КРИТИЧНО:** Если пользователь с таким email уже существует и `emailVerifiedAt != null` (email подтвержден):
      - **Бросать ошибку 409 (Conflict):** `"Аккаунт с таким email уже существует. Войдите в аккаунт или восстановите пароль."`
      - **НЕ отправлять письмо** (пользователь уже зарегистрирован)
      - **НЕ создавать нового пользователя**
    - Если пользователь с таким email уже существует и `emailVerifiedAt = null`:
      - НЕ создавать нового пользователя
      - **Обязательно хешируем новый пароль** (даже если TTL предыдущего истёк)
      - Сохранение `passwordHash` в Redis с ключом `auth:email_verification_password:{email}` и TTL 15 минут (overwrite)
      - Генерировать новый код (с учётом rate limit)
      - Отправить код на email
    - Если пользователь не существует:
      - Создание записи в БД с `emailVerifiedAt = null`
      - Хеширование пароля через `argon2`
      - Сохранение `passwordHash` в Redis с ключом `auth:email_verification_password:{email}` и TTL 15 минут
      - Генерация 6-значного кода
      - Отправка кода на email через Яндекс SMTP
      - Сохранение кода в Redis с ключом `auth:email_verification:{email}` и TTL 15 минут
  - **Обработка ошибок отправки email:**
    - Если отправка email не удалась (SMTP ошибка, сеть и т.д.):
      - Логировать ошибку с контекстом (email, причина ошибки, SMTP настройки)
      - Удалить код из Redis (если был сохранен)
      - Бросать ошибку 500: `"Не удалось отправить письмо. Попробуйте позже или обратитесь в поддержку."`
  - **Защита от enumeration:** Для неподтвержденных email всегда возвращать одинаковое сообщение:
    - `{ "message": "Мы отправили письмо с кодом подтверждения.\nЕсли вы уже использовали Mentala ранее, вы сможете войти или восстановить доступ" }`
    - **НЕ возвращать** `email`, `success`, `requiresVerification` и другие детали

#### 3.7.2. Верификация email

**`POST /api/auth/email/verify`**

- Body: `{ email: string, code: string }`
- Логика:
  - Нормализация email: `email.toLowerCase().trim()`
  - Загрузка кода из Redis по ключу `auth:email_verification:{email}`
  - Проверка кода (сравнение `sha256(code + secret)`)
  - Проверка количества попыток (максимум 5)
  - Проверка TTL (15 минут)
  - При успехе:
    - Установка `emailVerifiedAt = now()`
    - **Загрузка `passwordHash` из Redis** по ключу `auth:email_verification_password:{email}`
    - **Сохранение `passwordHash` в БД** (перенос из временного хранилища)
    - **Удаление `passwordHash` из Redis** (больше не нужен)
    - Создание сессии
    - Активация Trial подписки
    - Удаление кода из Redis
  - Возврат: `{ user, sessionToken? }`

#### 3.7.3. Повторная отправка кода

**`POST /api/auth/email/resend-code`**

- Body: `{ email: string }`
- Логика:
  - Нормализация email: `email.toLowerCase().trim()`
  - Проверка rate limit (по IP и email)
  - Генерация нового кода
  - Отправка на email
  - Сохранение в Redis (заменяет старый код)
  - **Защита от enumeration:** Всегда возвращать одинаковое сообщение:
    - `{ "message": "Мы отправили письмо с кодом подтверждения.\nЕсли вы уже использовали Mentala ранее, вы сможете войти или восстановить доступ", "retryAfter": number? }`
    - `retryAfter` в секундах, если rate limit (опционально)

#### 3.7.3.1. Запрос верификации email (публичный, безопасный)

**`POST /api/auth/email/request-verification`**

- Body: `{ email: string }`
- Логика:
  - Нормализация email: `email.toLowerCase().trim()`
  - Проверка rate limit (по IP и email)
  - **Защита от enumeration:** Всегда возвращать одинаковое сообщение, независимо от существования аккаунта
  - Если пользователь существует и `emailVerifiedAt = null`:
    - Генерация нового кода
    - Отправка кода на email
    - Сохранение кода в Redis
  - **Возврат:** `{ "message": "Мы отправили письмо с кодом подтверждения.\nЕсли вы уже использовали Mentala ранее, вы сможете войти или восстановить доступ", "retryAfter": number? }`
  - **НЕ возвращаем** информацию о существовании аккаунта или статусе верификации

**Использование:** UI может показывать нейтральную подсказку ("Если вы не подтверждали email — запросите код") и вызывать этот endpoint. Это сохраняет anti-enumeration и даёт пользователю путь.

#### 3.7.4. Установка пароля

**`POST /api/auth/password/set`**

- Требует авторизации
- Body: `{ password: string, confirmPassword: string }`
- Логика:
  - Проверка, что `passwordHash = null` (или разрешить переустановку)
  - Валидация пароля
  - Хеширование и сохранение
  - Возврат: `{ success: true }`

#### 3.7.5. Изменение пароля

**`POST /api/auth/password/change`**

- Требует авторизации
- Body: `{ currentPassword: string, newPassword: string, confirmPassword: string }`
- Логика:
  - Проверка текущего пароля
  - Валидация нового пароля
  - Хеширование и сохранение
  - Возврат: `{ success: true }`

#### 3.7.6. Вход (изменения)

**`POST /api/auth/email/login`**

- Body: `{ email: string, password: string }`
- Логика:
  - Нормализация email: `email.toLowerCase().trim()`
  - Rate limiting (максимум 10 попыток в 15 минут по комбинации IP+email)
  - Находим пользователя по email
  - **Защита от enumeration (публичный API):**

    - **НЕ возвращаем флаг `requiresEmailVerification`** (это раскрывает состояние аккаунта)

  - Если null → возвращаем общее сообщение: "Неверный email или пароль"

  - Если пароль неверный → возвращаем общее сообщение: "Неверный email или пароль"

  - Возврат: `{ user, sessionToken? }`

**Важно:** Детальная информация о статусе аккаунта доступна только после успешной аутентификации. Для запроса верификации используйте отдельный endpoint `/api/auth/email/request-verification`.

#### 3.7.6.1. Нативный Google вход (iOS/Android)

**`POST /api/auth/google/native`**

- Body: `{ idToken: string }`
- Логика:
  - Валидация ID token через Google (audience = web client id)
  - Проверка `email_verified = true`
  - Поиск/создание пользователя как в web OAuth
  - При необходимости возвращаем `requiresAccountLinking: true` + `linkingToken`
  - При успехе создаём сессию и возвращаем `{ user, sessionToken? }`

**Важно:** Этот endpoint используется только из нативных приложений (Capacitor).

#### 3.7.7. Подтверждение линковки аккаунта (пароль)

**`POST /api/auth/oauth/link-verify-password`**

- Body: `{ linkingToken: string, password: string }`
- Логика:
  - Загрузка временных данных из Redis по `linkingToken`
  - Проверка TTL (если истек → ошибка)
  - Поиск пользователя по email из временных данных
  - Проверка пароля через `argon2.verify`
  - При успехе:
    - Проверка, что `providerUserId` не занят
    - Создание `oauthAccounts`
    - Обновление `emailVerifiedAt` (если нужно)
    - Обновление `name`, `avatarUrl` (если пустые)
    - Удаление временных данных из Redis
    - Создание сессии
    - Логирование успешной линковки
  - Возврат: `{ user, sessionToken? }`

#### 3.7.8. Подтверждение линковки аккаунта (email-код)

**`POST /api/auth/oauth/link-send-code`**

- Body: `{ linkingToken: string }`
- Логика:
  - Загрузка временных данных из Redis по `linkingToken`
  - Проверка TTL
  - Получение email из временных данных
  - Проверка rate limit
  - Генерация 6-значного кода
  - Отправка кода на email
  - Сохранение кода в Redis с ключом `auth:oauth_link_code:{linkingToken}` и TTL 15 минут
  - Возврат: `{ success: true, retryAfter?: number }`

**`POST /api/auth/oauth/link-verify-code`**

- Body: `{ linkingToken: string, code: string }`
- Логика:
  - Загрузка временных данных из Redis по `linkingToken`
  - Загрузка кода из Redis по `auth:oauth_link_code:{linkingToken}`
  - Проверка кода и количества попыток
  - Поиск пользователя по email из временных данных
  - При успехе:
    - Проверка, что `providerUserId` не занят
    - Создание `oauthAccounts`
    - Обновление `emailVerifiedAt` (если нужно)
    - Обновление `name`, `avatarUrl` (если пустые)
    - Удаление временных данных и кода из Redis
    - Создание сессии
    - Логирование успешной линковки
  - Возврат: `{ user, sessionToken? }`

#### 3.7.9. Отмена линковки аккаунта

**`POST /api/auth/oauth/link-cancel`**

- Body: `{ linkingToken: string }`
- Логика:
  - Удаление временных данных из Redis
  - Возврат: `{ success: true }`

### 3.8. Безопасность

#### 3.8.1. Защита от брутфорса

**Коды верификации:**

- Лимит попыток: 5 на один код
- После превышения → блокировка на 15 минут (или до истечения TTL кода)
- Хранение счетчика попыток в Redis

**Вход по паролю:**

- Существующая защита (rate limiting на уровне middleware)
- Дополнительно: логирование подозрительных попыток

#### 3.8.2. Защита от спама

**Rate limiting:**

- По IP: 5 отправок в час
- По email: 3 отправки в час
- Использование Redis для счетчиков

#### 3.8.3. Защита от enumeration

**Проблема:** По API можно понять, существует email или нет, подтвержден он или нет.

**Решение:**

- На публичных эндпоинтах (регистрация, вход, восстановление пароля) возвращаем одинаковые сообщения
- Пример: "Если аккаунт существует, мы отправили письмо с инструкциями"
- Детальная информация о статусе аккаунта доступна только после успешной аутентификации

**Применяется к:**

- `POST /api/auth/email/register` — всегда "Код отправлен на email"
- `POST /api/auth/email/login` — всегда "Неверный email или пароль" (если неверные данные)
- `POST /api/auth/email/resend-code` — всегда "Если аккаунт существует, код отправлен"
- `POST /api/auth/email/request-verification` — всегда "Если аккаунт существует, код отправлен"

#### 3.8.4. Логирование

**Security events:**

- Превышение лимита попыток ввода кода
- Превышение rate limit отправки кода
- Попытка линковки с занятым `providerUserId`
- Попытка входа с неподтвержденным email
- Попытка привязать `providerUserId` к другому аккаунту

### 3.10. Тестирование

#### 3.10.1. Сценарии

1. **Регистрация нового пользователя:**

   - Заполнение формы → отправка кода → ввод кода → успешная регистрация

2. **Повторная отправка кода:**

   - Запрос нового кода → получение → ввод → успех

3. **Превышение лимита попыток:**

   - 5 неверных попыток → блокировка → запрос нового кода

4. **Вход через Google (новый пользователь):**

   - Первый вход → создание аккаунта → успех

5. **Вход через Google (линковка):**

   - Существующий email+пароль → вход через Google → экран подтверждения → ввод пароля/кода → линковка → оба способа входа работают

6. **Установка пароля для Google-аккаунта:**

   - Вход через Google → настройки → установка пароля → вход по email+паролю

7. **Вход с неподтвержденным email:**
   - Регистрация без верификации → попытка входа → ошибка → верификация → успех

## 4. Оставшиеся вопросы

### 4.1. Линковка аккаунтов

**Вопрос:** Если пользователь с email+паролем входит через Google, следует ли автоматически привязывать Google-аккаунт к существующему аккаунту или запрашивать подтверждение (например, ввод пароля)?

**Ответ (РЕШЕНО):** Линковка выполняется только после подтверждения владения аккаунтом (ввод пароля или email-код). Автоматическая линковка по совпадению email не допускается из соображений безопасности. Подробности в разделе 3.2.1-3.2.4.

### 4.2. UI/UX

**Вопрос:** Нужны ли уведомления или баннеры о неподтвержденном email?

**Ответ:** Да, показывать баннер в настройках и при попытке входа, если email не подтвержден.

### 4.3. Обратная совместимость

**Вопрос:** Нужна ли миграция для существующих данных пользователей?

**Ответ:** Да, установить `emailVerifiedAt = now()` для всех пользователей с `passwordHash != null` (одноразовая миграция).

### 4.4. Безопасность

**Вопрос:** Нужна ли дополнительная защита от спама, например, лимит отправок с одного email-адреса?

**Ответ:** Да, лимит 3 отправки в час с одного email (указано в разделе 3.1.3).

## 6. Критические исправления (приоритет)

### 6.1. Обработка существующего подтвержденного email при регистрации

**Проблема:** Если пользователь пытается зарегистрироваться с email, который уже существует и подтвержден, код не отправляется, но пользователю возвращается сообщение "Мы отправили письмо с кодом подтверждения.\nЕсли вы уже использовали Mentala ранее, вы сможете войти или восстановить доступ".

**Решение:**

- В `server/api/auth/email/register.post.ts` добавить проверку:
  ```typescript
  if (existing.length && existing[0].emailVerifiedAt) {
    throw createError({
      statusCode: 409,
      statusMessage:
        'Аккаунт с таким email уже существует. Войдите в аккаунт или восстановите пароль.',
    });
  }
  ```
- Обновить обработку ошибок на фронтенде (`app/pages/auth/index.vue`) для показа понятного сообщения при ошибке 409

### 6.2. Обработка ошибок отправки email

**Проблема:** Ошибки отправки email не логируются и не обрабатываются должным образом.

**Решение:**

- Добавить try-catch в `server/application/auth/email-sender.ts` в функции `sendVerificationEmail`
- Логировать все ошибки с контекстом (email, причина, SMTP настройки)
- При ошибке удалять код из Redis
- Возвращать понятное сообщение пользователю

### 6.3. Валидация SMTP конфигурации

**Проблема:** Нет проверки SMTP конфигурации при старте сервера.

**Решение:**

- Добавить функцию `validateSmtpConfig()` в `server/application/auth/email-sender.ts`
- Вызывать при старте сервера
- Логировать предупреждения о неполной конфигурации
