# ТЗ: Оптимизация стоимости LLM — оставить только previous_response_id, убрать summary и историю

## 0) Контекст

Сейчас чат использует **две** формы памяти одновременно:

1. `summary` прошлых сессий (готовится отдельным LLM‑запросом на `finishSession` и подмешивается в каждый следующий запрос).
2. `previous_response_id` (Responses API), который позволяет модели восстановить контекст без пересылки всей истории.

Дополнительно, в каждый запрос всё равно отправляются последние ~30 сообщений. Итог — **дублирование контекста** и лишние токены на каждом запросе.

## 1) Проблемы (что сейчас тратит деньги)

### 1.1 Два механизма памяти + дублирование истории

- `summary` добавляется в промпт (system/developer блок).
- Параллельно передаются последние сообщения (`slice(-30)`).
- `previous_response_id` включён одновременно.
- Это даёт максимальную стоимость входных токенов без необходимости.

### 1.2 Отдельный запрос на summary

- `finishSession` делает отдельный вызов в OpenAI (`max_output_tokens: 600`).
- Эта операция выполняется на каждую сессию, даже если эффекта немного.

### 1.3 Неуправляемая стоимость

- История и summary передаются «по умолчанию», даже когда можно обойтись одним `previous_response_id`.

## 2) Цель изменения

- Полностью убрать `summary` и любую «ручную» историю из запросов в OpenAI.
- Оставить **единственный механизм памяти**: `previous_response_id`.
- Дать пользователю контроль включения/выключения памяти ИИ через UI.
- Снизить стоимость входных токенов до минимума.

## 3) Решение (основной подход)

**Полностью убрать summary‑память и передачу истории в OpenAI.**  
Оставляем только `previous_response_id`, который пользователь может включать/выключать в UI.

Ключевая фиксация: **summary не участвует в диалоге** — не используется для генерации ответов ИИ и **не передается в OpenAI ни в каком виде**.  
Также **не передаются последние сообщения** (`slice(-30)` и любые аналоги) — запросы должны опираться только на `previous_response_id`.

### 3.1 Что должно остаться включенным

- `previous_response_id` остаётся активным (если включён пользователем).
- `store` остаётся `true` только при использовании `previous_response_id`.

## 4) Детальные изменения (по файлам)

### 4.1 `server/infrastructure/llm/openai.ts`

- **Не формировать** `sessionMemoryText` и не читать `summaryStore`.
- **Не передавать** `messages.slice(-30)` (и любые аналоги истории) в запросы OpenAI.
- В `finishSession()` **не вызывать** генерацию summary.
- `previous_response_id` остаётся единственным источником памяти.

### 4.2 `server/utils/summaryStore.ts`

- Код можно оставить, но **не использовать**.

### 4.3 UI/UX: `app/components/settings/MemorySettings.vue`

- Оставить только переключатель `enablePreviousResponseId`.
- Полностью удалить блок “Память в приложении” (summary) и рекомендацию “включить оба режима”.

## 5) Почему это выгодно

- Убираем отдельный LLM‑запрос `finishSession`.
- Убираем любой ручной контекст в каждом запросе (summary + история).
- Остаётся только `previous_response_id`, который уже оптимизирован OpenAI.

## 6) Риски

- Потеря части «долгой памяти», если `previous_response_id` истёк (срок жизни ограничен и зависит от политики OpenAI).
- Если `previous_response_id` отсутствует или истёк: диалог считается новым, ассистент **не пытается** «вспоминать прошлое», пользователь **не вводится в заблуждение**.
- Качество может снижаться при полном отключении истории — это принимаемый компромисс ради стоимости.

## 7) Метрики успеха

- Падение средних `input_tokens` на запрос в логах.
- Падение общего LLM‑расхода на пользователя.
- Отсутствие деградации NPS/CSAT при сохранении предыдущих `response_id`.

## 8) План внедрения

1. Убрать summary и историю из запросов OpenAI.
2. Обновить UI/UX (оставить только `previous_response_id`).
3. Мониторить токены, стоимость и качество.

## 9) Acceptance Criteria

- В запросы OpenAI **не передаются**: `summary`, `slice(-30)` и любая ручная история.
- Summary **не генерируется** в `finishSession` и **не участвует** в генерации ответов.
- При отсутствии `previous_response_id` диалог трактуется как новый, без «ложной памяти».
- `previous_response_id` работает как раньше и управляется пользователем в UI.

## 10) Рекомендуемое усиление (не косметика)

- **Не использовать `slice(-30)` вообще** — запросы должны быть максимально короткими.
- Если нужно минимальное «подстрахование» без больших затрат, допустимы только **очень короткие** локальные подсказки в UI, но **не в запросе к OpenAI**.
