# ТЗ: server-first сохранение незавершённой чат-сессии и автоматическая user summary

## Статус

Draft перед реализацией.

Документ фиксирует решение для первого боевого этапа:

- **без локального fallback-хранилища**;
- **без хранения полной переписки "навсегда"**;
- **с использованием серверного transient transcript в БД**;
- **с ручной, logout- и ночной автосаммаризацией**.

---

## 1. Что решаем

Нужно устранить текущую проблему, при которой:

- на телефоне при `kill app` или холодном перезапуске теряется текущая живая сессия;
- саммаризация не успевает отправиться, если клиентский store погиб вместе с процессом;
- серверная nightly-логика опирается на слабый источник данных и не должна считаться финальным решением в текущем виде.

Цель этапа:

- сделать так, чтобы содержательная сессия не терялась после закрытия приложения;
- перенести источник данных для user summary с client-only состояния на серверный transient transcript;
- дать клиенту возможность восстановить незавершённую text-session из server transcript после reload / cold start, если сессия ещё не вышла за пределы idle timeout;
- сохранить существующий UX с manual summary и logout summary;
- добавить ночную автоматическую саммаризацию, если пользователь сам её не запустил.

---

## 2. Принятое архитектурное решение

### 2.1. Источник истины

На первом этапе **источником истины для саммаризации становится серверный transient transcript в БД**, но в продуктовой логике он трактуется как **несуммаризованный backlog пользователя**, а не как изолированная одна `therapySession`.

То есть:

- клиент больше не считается единственным местом, где существует полная история текущего диалога;
- сервер хранит **временную** копию текущего backlog ровно до момента успешной саммаризации и cleanup;
- клиент может заново гидрировать чат из этой временной копии при cold start даже после завершения billing-сессии;
- новые billing-сессии продолжают этот backlog новыми snapshot'ами;
- после успешной саммаризации transient transcript удаляется целиком по `userId`.

### 2.2. Что не делаем на этапе 1

На этапе 1 **не внедряется локальное persistent-хранилище чата**.

Причина:

- это отдельный слой сложности;
- сначала нужно стабилизировать server-first lifecycle;
- локальный fallback можно добавить позже как дополнительную защиту, но не смешивать с первым боевым запуском.

### 2.3. Почему это решение выбрано

Это решение выбрано потому, что:

- сервер может дожать summary без повторного открытия приложения пользователем;
- серверный cron не может читать локальное хранилище устройства;
- `kill app` на iOS/Android не даёт надёжной гарантии, что клиентский JS успеет сделать последний запрос;
- transient transcript в БД даёт предсказуемый lifecycle, retry и cleanup.

---

## 3. Общий принцип хранения

### 3.1. Храним не "все чаты навсегда", а только transient draft

В БД хранится не полноценный архив всей истории пользователя, а **временный server-side draft текущего backlog до summary**.

Хранение должно быть:

- серверным;
- временным;
- заякоренным на последней `therapySessionId`, но логически охватывающим все несуммаризованные billing-сессии пользователя;
- пригодным для user summary;
- очищаемым после успешной саммаризации.

### 3.2. Что именно хранится

Для каждой активной `therapySessionId` хранятся:

- `therapySessionId`;
- `userId`;
- сообщения `user` и `assistant`;
- порядок сообщений;
- `startedAt`;
- `lastActivityAt`;
- служебные поля, необходимые для дедупликации и cleanup.

### 3.3. Требование по безопасности

Сообщения должны оставаться **transient и encrypted**, а не превращаться в постоянный пользовательский архив.

---

## 4. Когда и как сохраняется текущий чат

### 4.1. Базовый принцип

Не нужно делать **отдельный клиентский HTTP-запрос на сохранение чата на каждое сообщение**.

Это лишняя сложность и лишняя сеть.

Правильный путь:

- использовать уже существующие серверные точки входа `/api/chat` и `/api/chat/stream`;
- сохранять transcript на сервере **в рамках уже идущего chat request lifecycle**.

### 4.2. Момент записи

Для первого этапа принимается такой lifecycle записи:

1. При первом пользовательском сообщении создаётся `therapySession`.
2. Когда сервер принимает user-message в обработку, он сохраняет user-message в transient transcript.
3. Когда assistant-ответ завершён и финальный текст готов, сервер сохраняет assistant-message в тот же transcript.
4. `lastActivityAt` обновляется на каждом валидном turn.

### 4.3. Чего делать не нужно

Не нужно:

- сохранять каждый SSE chunk;
- перезаписывать весь transcript на каждый токен;
- слать отдельный "save draft" запрос с клиента на каждое изменение store.

### 4.4. Допустимая нагрузка

На один нормальный turn приходится:

- 1 запись user-message;
- 1 запись assistant-message;
- обновление activity/session metadata.

На фоне LLM-запроса такая нагрузка считается оправданной и приемлемой.

---

## 5. Триггеры саммаризации

### 5.1. Ручной запуск

Пользователь нажимает `Завершить сессию`.

Система:

1. проверяет eligibility;
2. запускает создание `session_summaries_user`;
3. после успешной саммаризации очищает transient transcript пользователя целиком;
4. очищает клиентский store.

### 5.2. Logout

Текущую logout-логику **сохраняем**.

При logout:

1. клиент по-прежнему инициирует фоновый запуск саммаризации;
2. logout не должен блокироваться долгим ожиданием summary;
3. если summary завершилась успешно, transient transcript очищается;
4. если summary не удалась, transcript не удаляется и остаётся доступным для retry.

Причина сохранения logout-trigger:

- пользователь часто выходит и потом возвращается под тем же user;
- logout не должен означать потерю полезной завершённой сессии.

### 5.3. Ночная автоматическая саммаризация

Нужна автоматическая обработка случая, когда:

- пользователь общался;
- manual summary не нажал;
- logout не делал;
- чат давно неактивен;
- summary должна быть готова позже автоматически.

Для этапа 1 фиксируется следующая логика:

- nightly-job запускается **ежедневно в 03:15 по `Europe/Moscow`**;
- текущая логика "`stale > 12 часов`" убирается;
- вместо этого используются признаки фактической неактивности сессии.

Сессия считается кандидатом на ночную саммаризацию, если одновременно выполнены все условия:

1. у пользователя есть server transcript backlog без готовой `completed/pending` user summary на последнюю `therapySession`;
2. для сессии ещё нет `session_summaries_user`;
3. transcript текущей сессии существует на сервере;
4. выполнены условия eligibility;
5. `lastActivityAt` старше `CHAT_IDLE_TIMEOUT_MS`;
6. на момент ночного запуска пользователь уже не активен в этой сессии.

### 5.4. Что значит "пользователь не активен"

На первом этапе признаком неактивности считается:

- `lastActivityAt < now - CHAT_IDLE_TIMEOUT_MS`.

То есть если idle timeout чата составляет 15 минут, то сессия, у которой нет активности дольше 15 минут, может считаться завершившейся по бездействию.

### 5.5. Если пользователь пишет ночью

Если пользователь реально общается в момент ночного запуска, то его `lastActivityAt` будет свежим.

В этом случае:

- nightly summary **не запускается**;
- сессия переносится на следующий цикл.

---

## 6. Eligibility

Для user summary сохраняются текущие бизнес-условия:

1. не менее 5 user-сообщений;
2. длительность не менее 4 минут;
3. не менее 3 содержательных user-сообщений;
4. содержательное сообщение = от 80 символов без пробелов.

Проверка eligibility должна выполняться на сервере по серверному transcript и серверным метрикам сессии.

---

## 7. Cleanup и retention

### 7.1. Главный принцип cleanup

Cleanup после успешной саммаризации должен выполняться **по `therapySessionId`**, а не массово по `userId`.

### 7.2. Почему нельзя чистить всё по `userId`

Очистка всех transient-сообщений пользователя по `userId` после одной успешной саммаризации считается опасной.

Причины:

1. Пользователь может начать новую сессию до завершения cleanup предыдущей.
2. У пользователя может быть другой активный клиент или другой сценарий в работе.
3. У пользователя может остаться другая незавершённая/failed сессия, которая ещё требует retry.
4. Массовая очистка по `userId` создаёт race condition: успешно завершили одну summary и случайно стёрли данные другой.

### 7.3. Правильный cleanup после успешной саммаризации

После `session_summaries_user.status = completed` нужно:

1. очистить transient transcript **только** этой `therapySessionId`;
2. очистить transient memory, привязанную к этой `therapySessionId`;
3. оставить остальные сессии и черновики пользователя нетронутыми.

### 7.4. Когда допустима очистка по `userId`

Очистка по `userId` допустима только в отдельных специальных сценариях:

- удаление аккаунта;
- административный purge;
- отдельный retention cleanup старых orphaned transient-данных, не связанных с активной сессией.

### 7.5. Что делать с failed summary

Если саммаризация завершилась ошибкой:

- transcript **не удаляется**;
- данные сессии остаются для retry;
- статус ошибки логируется;
- следующая manual/nightly попытка может использовать тот же серверный transcript.

---

## 8. Как закрывается сессия server-side

### 8.1. Ручной или logout сценарий

При manual/logout summary:

1. сервер берёт transcript по `therapySessionId`;
2. проверяет eligibility;
3. создаёт `session_summaries_user`;
4. при `completed` закрывает сессию и выполняет cleanup по `therapySessionId`.

### 8.2. Ночной сценарий

При nightly auto summary:

1. cron находит кандидатов;
2. определяет, что сессия реально idle;
3. закрывает сессию как завершившуюся по бездействию;
4. создаёт `session_summaries_user`;
5. при успехе очищает transient transcript по `therapySessionId`.

---

## 9. Что меняется в текущей nightly-логике

### 9.1. Что убираем

Из nightly-механизма убирается логика:

- "`stale > 12 часов`";
- попытка строить решение на полупустом источнике данных;
- cleanup, который может конфликтовать с user summary lifecycle.

### 9.2. Что вводим вместо неё

Новый nightly-механизм:

- запускается ежедневно в `03:15 Europe/Moscow`;
- смотрит на серверный transcript;
- проверяет отсутствие активности по `lastActivityAt`;
- не трогает активную ночную сессию;
- создаёт `session_summaries_user` только если сессия реально eligible.

---

## 10. Напоминание пользователю о готовом итоге

На этапе 1 нужно учитывать, что итог может быть подготовлен ночью автоматически.

Минимальное требование:

- пользователь при следующем открытии приложения видит непрочитанный user summary как новый.

Дополнительный сценарий, который можно добавить позже:

- push или другое уведомление о том, что итог готов.

На первом этапе push-напоминание не является обязательной частью этой задачи, если это расширяет scope.

---

## 11. Совместимость и переходный режим

### 11.1. Переходный режим

На время rollout допускается сохранить существующий клиентский fallback, когда manual/logout summary ещё может отправлять `clientMessages`.

Но целевое состояние этапа:

- **основной источник для саммаризации — серверный transcript**;
- client fallback не считается главным механизмом надёжности.

### 11.2. Почему не удаляем client fallback сразу жёстко

Это снижает риск rollout-регрессий на переходном этапе, пока server-first путь не подтверждён на dev и production.

---

## 12. Открытые решения, которые фиксируем сразу

По этому ТЗ принимаются следующие решения:

1. Этап 1 делаем **без локального persistent chat storage**.
2. Основной источник для summary — **серверный transient transcript в БД**.
3. Logout-trigger на summary **сохраняем**.
4. Cleanup после успешной summary делаем **по `therapySessionId`**, а не по `userId`.
5. Очистка по `userId` разрешена только для account deletion или отдельного retention purge.
6. Ночная автосаммаризация остаётся, но логика "`03:15 + stale > 12h`" заменяется на "`03:15 + session idle + server transcript + eligibility`".

---

## 13. Что нужно проверить перед реализацией

1. Что transcript действительно пишется на сервере для text chat во всех целевых сценариях.
2. Что cleanup user summary и cleanup chat memory не конфликтуют между собой.
3. Что failed summary не уничтожает source data.
4. Что manual/logout/nightly используют один и тот же server-side source of truth.
5. Что nightly-job не закрывает реально активную сессию.
6. Что после `completed` cleanup идёт только по целевой `therapySessionId`.

---

## 14. Краткая итоговая формула реализации

Нужный первый этап:

- **server-first**;
- **transient transcript в БД**;
- **manual + logout + nightly triggers**;
- **eligibility на сервере**;
- **cleanup только по `therapySessionId`**;
- **без локального fallback на первом этапе**.
