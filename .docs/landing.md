# ТЗ: Лендинг Mentala

Версия: 2.1  
Дата: 13 февраля 2026  
Статус: draft (детализировано под текущую кодовую базу)

## 1. Цель и контекст

Лендинг на `https://mentala.app` нужен для двух режимов:

1. `Pre-release` (до релиза): сбор заявок в waitlist.
2. `Post-release` (после релиза): перевод трафика в продукт `https://my.mentala.app/auth`.

Лендинг должен отражать реальные возможности текущего продукта, уже присутствующие в коде и документации:

- AI-чат поддержки.
- Темы терапии и привычек.
- Дыхательные практики.
- Медитации.
- SOS-режим быстрой стабилизации.
- Персонализированные уведомления.
- Подписки `Basic / PRO / Premium` и trial.

## 2. Принципы и ограничения (на основе проекта)

### 2.1 Технические ограничения

- Основной продукт уже работает на `Nuxt 4 + TypeScript + Tailwind + shadcn-vue + Radix`.
- Для лендинга используем тот же UI-стек (`Tailwind + shadcn-vue`), без отдельного UI-фреймворка.
- API лендинга реализуется в текущем Nitro backend (`server/api`), по тем же правилам DTO/валидации.
- В `nuxt.config.ts` у основного приложения `ssr: false`, поэтому SEO-часть лендинга не должна опираться на CSR-рендер продукта.

### 2.2 Визуальные ограничения

- В проекте закреплён dark glassmorphism стиль (`glass-deep`, мягкие blur и градиенты).
- Лендинг должен быть визуально совместим с приложением, но более маркетинговый и выразительный.
- Нельзя обещать функциональность, которой нет в текущем продукте или в roadmap документах.

### 2.3 Юридические ограничения

- Обязательный явный medical disclaimer (видимый на странице).
- Ссылки на действующие юридические документы:
  - `/legal/privacy-policy.html`
  - `/legal/terms-of-service.html`

## 3. Архитектура лендинга (to-be)

### 3.1 Размещение в репозитории

Зафиксированная структура для реализации:

```txt
frontend/
├── app/                      # Продукт (my.mentala.app)
├── apps/
│   └── landing/              # Отдельная сборка лендинга (mentala.app)
├── server/
│   └── api/landing/*         # Общие API-ручки для конфига и лидов
└── shared/dto/landing.ts     # Zod DTO для API лендинга
```

Почему так:

- SEO для лендинга не должен зависеть от CSR-конфигурации основного приложения.
- Повторно используется инфраструктура проекта: линтеры, CI, middleware, единый backend.

### 3.2 Домены и интеграция

- Лендинг: `mentala.app`
- Приложение/API: `my.mentala.app`
- Междоменный запрос: `mentala.app -> my.mentala.app/api/landing/*`
- Для CORS в production нужно добавить origin `https://mentala.app` в `PUBLIC_APP_ORIGIN` или `ALLOWED_ORIGINS`.

## 4. Пользовательские сценарии

### 4.1 Сценарий до релиза

1. Пользователь открывает `mentala.app`.
2. Видит ценность и сценарии применения Mentala.
3. Нажимает `Получить ранний доступ`.
4. Заполняет форму (`name`, `email`, `goalKey?` из фиксированного списка).
5. Получает состояние успеха `Спасибо, вы в списке`.

### 4.2 Сценарий после релиза

1. Пользователь открывает `mentala.app`.
2. Основной CTA показывает `Войти и начать`.
3. Переход на `https://my.mentala.app/auth`.
4. Waitlist-модалка скрыта.

6. `SOS`: быстрые техники стабилизации.
7. `Уведомления`: персональные напоминания по темам/привычкам.

### 5.6 Блок «Приватность и безопасность»

## 6. Режимы CTA (релизный флаг)

Лендинг читает конфиг:

- `isReleased = false`: CTA открывает форму waitlist.
- `isReleased = true`: CTA ведёт на `https://my.mentala.app/auth`.

Клиентский TTL кэша конфига: 5 минут.

## 7. API-контракт лендинга

### 7.1 `GET /api/landing/config`

Ответ:

```json
{
  "isReleased": false,
  "ctaUrl": "https://my.mentala.app/auth",
  "updatedAt": "2026-02-13T12:00:00.000Z"
}
```

Требования:

- Публичный endpoint.
- Допускается агрессивное кеширование (`Cache-Control`) на edge/CDN.

### 7.2 `POST /api/landing/lead`

Request:

```json
{
  "name": "Николай",
  "email": "user@example.com",
  "goalKey": "reduce_anxiety",
  "utmSource": "instagram",
  "utmMedium": "cpc",
  "utmCampaign": "launch_2026"
}
```

Response (новая запись):

```json
{
  "ok": true,
  "status": "created"
}
```

Response (дубликат по email):

```json
{
  "ok": true,
  "status": "duplicate"
}
```

Валидация:

- `name`: `1..120`.
- `email`: валидный email.
- `goalKey`: optional enum.
- UTM поля: optional, `0..120`.

Фиксированный список `goalKey` (v1):

- `reduce_anxiety` — снизить тревожность.
- `sleep_better` — улучшить сон.
- `reduce_stress` — снизить стресс/выгорание.
- `quit_smoking` — бросить курить.
- `reduce_alcohol` — сократить алкоголь.
- `reduce_caffeine` — сократить кофеин.
- `build_habits` — развить полезные привычки.
- `try_ai_support` — попробовать AI-поддержку.

Нормализация:

- `email` обрабатывается через существующую серверную функцию `normalizeEmail()` (как в auth/trial потоке).

## 8. Данные и БД (Drizzle, `schema.ts`)

### 8.1 Таблица `landing_config`

- `id` `serial` PK (используем запись `id=1`).
- `is_released` `boolean not null default false`.
- `cta_url` `varchar(255) not null default 'https://my.mentala.app/auth'`.
- `updated_at` `timestamp with timezone not null default now()`.

### 8.2 Таблица `landing_leads`

- `id` `serial` PK.
- `name` `varchar(120) not null`.
- `email` `varchar(255) not null`.
- `email_normalized` `varchar(255) not null`.
- `email_hash` `varchar(64) not null`.
- `goal_key` `varchar(50) null`.
- `utm_source` `varchar(120) null`.
- `utm_medium` `varchar(120) null`.
- `utm_campaign` `varchar(120) null`.
- `referrer` `text null`.
- `created_at` `timestamp with timezone not null default now()`.

Индексы:

- `unique(email_hash)` для идемпотентности.
- индекс по `created_at` для выгрузок.

## 9. Безопасность и антиспам

Обязательные меры уже в первой версии:

- `Rate limit` для `POST /api/landing/lead` (IP + email hash).
- Honeypot-поле формы (скрытое, должно быть пустым).
- CORS только для доверенных origin (включая `https://mentala.app`).
- Логи без утечки чувствительных данных.
- Единый `X-Request-Id` в ответах (уже есть middleware).
- Базовая серверная валидация `Origin/Referer` для публичной формы.

Опционально в phase 2:

- hCaptcha/Cloudflare Turnstile.
- Блокировка по ASN/странам.

## 10. Уведомления о новых лидах

Уведомления отправляются только при `status=created` (не при duplicate).

### 10.1 Email-уведомление команде

- Тема: `Новая заявка Mentala (landing)`.
- Поля: имя, email, цель, UTM, дата.
- Использовать существующий SMTP-контур (`nodemailer`, как в auth email sender).

### 10.2 Telegram-уведомление

- Отправка в фиксированный чат.
- Формат:
  - `Новая заявка Mentala`
  - `Имя: ...`
  - `Email: ...`
  - `Цель: goalKey + расшифровка`
  - `UTM: ...`
  - `Дата: ...`

Переменные окружения:

- `NUXT_TELEGRAM_BOT_TOKEN` (уже используется в runtimeConfig).
- `NUXT_TELEGRAM_LEADS_CHAT_ID` (новая, обобщённая для заявок).

## 11. SEO, доступность, производительность

### 11.1 SEO baseline

- `title`, `description`, `canonical`.
- Open Graph + Twitter Card.
- `robots.txt`, `sitemap.xml`.
- JSON-LD: `Organization`, `WebSite`, `FAQPage`.
- Один `h1`, валидная иерархия заголовков, `alt` у изображений.

### 11.2 A11y baseline

- Контраст не ниже WCAG AA.
- Полная клавиатурная навигация.
- Видимый `focus` для интерактивных элементов.
- `prefers-reduced-motion` поддерживается.

### 11.3 Perf baseline

- LCP < 2.5s, CLS < 0.1 на мобильных.
- WebP/AVIF.
- Lazy-load ниже первого экрана.
- Минимум JS в критическом пути.

### 11.4 Кроссбраузерность и адаптивность (обязательно)

Базовое требование:

- Лендинг должен корректно работать начиная от ширины `320px` и выше, без горизонтального скролла и без «ломающихся» блоков.

Матрица обязательных ширин для проверки UI:

- `320`, `360`, `375`, `390`, `414`, `480`, `768`, `1024`, `1280`, `1440`, `1920`.

Обязательные платформы/браузеры:

- `Chrome` (desktop, последние 2 версии).
- `Safari` (macOS, последние 2 версии).
- `Firefox` (desktop, последние 2 версии).
- `Edge` (desktop, последние 2 версии).
- `Safari iOS` (`iOS 13+`).
- `Chrome Android` (`Android 8+`).

UX-инварианты для всех экранов:

- Все CTA видимы и кликабельны без overlap.
- Header/меню/модалка waitlist корректно перестраиваются на mobile.
- Типографика и отступы читаемы на `320px`.
- Интерактивные элементы имеют удобный tap-target (не меньше ~44px).
- Изображения/медиа не вылезают за контейнер.
- Анимации не ломают layout, `prefers-reduced-motion` соблюдается.
