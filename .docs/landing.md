## 1. Цель и контекст

Лендинг на `https://mentala.app` нужен для двух режимов:

1. `Pre-release` (до релиза): сбор заявок в waitlist.
2. `Post-release` (после релиза): перевод трафика в продукт `https://my.mentala.app/auth`.

Лендинг должен отражать реальные возможности текущего продукта, уже присутствующие в коде и документации:

- AI-чат поддержки.
- Темы терапии и привычек.
- Дыхательные практики.
- Медитации.
- SOS-режим быстрой стабилизации.
- Персонализированные уведомления.
- Подписки `Basic / PRO / Premium` и trial.

## 2. Принципы и ограничения (на основе проекта)

### 2.1 Технические ограничения

- Основной продукт уже работает на `Nuxt 4 + TypeScript + Tailwind + shadcn-vue + Radix`.
- Для лендинга используем тот же UI-стек (`Tailwind + shadcn-vue`), без отдельного UI-фреймворка.
- API лендинга реализуется в текущем Nitro backend (`server/api`), по тем же правилам DTO/валидации.
- В `nuxt.config.ts` у основного приложения `ssr: false`, поэтому SEO-часть лендинга не должна опираться на CSR-рендер продукта.
- Рендеринг `apps/landing` фиксируем как `SSR + SWR (гибрид)`:
  - SSR-HTML для стабильной индексации;
  - SWR-кэш на edge/server для снижения нагрузки.

### 2.2 Визуальные ограничения

- В проекте закреплён dark glassmorphism стиль (`glass-deep`, мягкие blur и градиенты).
- Лендинг должен быть визуально совместим с приложением, но более маркетинговый и выразительный.
- Нельзя обещать функциональность, которой нет в текущем продукте или в roadmap документах.

### 2.3 Юридические ограничения

- Обязательный явный medical disclaimer (видимый на странице).
- Ссылки на действующие юридические документы:
  - `https://my.mentala.app/legal/privacy-policy.html`
  - `https://my.mentala.app/legal/terms-of-service.html`

## 3. Архитектура лендинга (to-be)

### 3.1 Размещение в репозитории

Зафиксированная структура для реализации:

```txt
frontend/
├── app/                      # Продукт (my.mentala.app)
├── apps/
│   └── landing/              # Отдельная сборка лендинга (mentala.app)
├── server/
│   └── api/landing/*         # Общие API-ручки для конфига и лидов
└── shared/dto/landing.ts     # Zod DTO для API лендинга
```

Почему так:

- SEO для лендинга не должен зависеть от CSR-конфигурации основного приложения.
- Для SEO и скорости используется гибрид `SSR + SWR` (без зависимости от режима рендера основного `app/`).
- Повторно используется инфраструктура проекта: линтеры, CI, middleware, единый backend.

### 3.2 Домены и интеграция

- Лендинг: `mentala.app`
- Приложение/API: `my.mentala.app`
- Междоменный запрос: `mentala.app -> my.mentala.app/api/landing/*`
- Для CORS в production используем `ALLOWED_ORIGINS` (comma-separated), включая `https://mentala.app` и `https://www.mentala.app`.
- **Важно:** если на `my.mentala.app` включён Basic Auth (например, через Traefik), preflight OPTIONS до Nuxt не доходит (401), и браузер сообщает об ошибке CORS. Нужно **исключить путь `/api/landing/lead` из Basic Auth** (только этот эндпоинт), чтобы OPTIONS и POST обрабатывались приложением и возвращали заголовки `Access-Control-Allow-Origin` и т.д.

### 3.3 Стратегия рендеринга и кеша (SEO)

- Лендинг в `apps/landing` работает в режиме `SSR + SWR`.
- Для публичных страниц лендинга применяется SWR-кэш с коротким TTL.
- Критичные мета-данные (`title`, `description`, `canonical`, JSON-LD) рендерятся на сервере.
- Для `GET /api/landing/config` фиксируем `Cache-Control: public, max-age=60, stale-while-revalidate=120`.

### 3.4 Избежание Hydration Mismatch (SSR)

Чтобы серверный HTML совпадал с тем, что строит клиент, и не «плыла» вёрстка:

1. **Чистая пересборка после правок**  
   После изменений в лендинге перезапускай dev с очисткой кэша Nuxt:

   - Остановить `landing:dev`, удалить `apps/landing/.nuxt` и при необходимости `node_modules/.cache`, затем снова `pnpm landing:dev`.  
     Так серверный и клиентский бандлы собираются из одного и того же кода.

2. **Не кэшировать HTML в dev**  
   В `apps/landing/nuxt.config.ts` для маршрута `/` в режиме разработки задано `swr: 0`, чтобы каждый запрос получал свежий SSR-ответ, а не закэшированную старую разметку.

3. **Одинаковый контент на сервере и клиенте**  
   Не использовать при первом рендере то, что различается между средой: `window`, `document`, `localStorage`, `Date.now()`, `Math.random()`, или данные с API, зависящие от окружения. Такие блоки лучше рендерить только на клиенте через `<ClientOnly>`.

4. **Корректная разметка**  
   Избегать невалидного вложения (например, `<div>` внутри `<p>`): браузер может нормализовать DOM, и разметка на клиенте будет отличаться от серверной.

5. **Запуск именно лендинга**  
   Лендинг — отдельное приложение: `pnpm landing:dev` (порт 3001). Основное приложение — `pnpm dev` (порт 3000). Убедись, что открываешь нужный порт.

### 3.5 Деплой (статический экспорт)

На продакшне лендинг разворачивается как **статический сайт**: `pnpm landing:generate` создаёт предрендеренный HTML и ассеты в `apps/landing/.output/public`. Деплой — Nginx (или контейнер со статикой), атомарное обновление через releases + symlink. Полное ТЗ по сборке, CI и хостингу — `.docs/landing_static_deploy_tz.md`.

## 4. Пользовательские сценарии

1. Пользователь открывает `mentala.app`.

4. Waitlist-модалка скрыта.

### 5.2.1 Демонстрация продукта через скролл

#### Цель

Показать ключевые возможности Mentala без горизонтальных каруселей и без перегруза. Пользователи на лендингах скроллят, а не свайпают, поэтому демонстрацию интерфейса делаем как вертикальный сторителлинг.

5 скринов экранов по пути app/assets/images/landing/features

- chat.webp
- therapy.webp
- habits.webp
- meditations.webp
- breathing.webp

#### Формат

Sticky phone layout:

- слева (или сверху на мобильном) - текстовый блок: заголовок + 2-3 строки смысла + 3-4 чипа-примеров
- справа (или ниже на мобильном) - один телефонный мокап
- при прокрутке в пределах секции меняется экран внутри телефона (crossfade), синхронно меняется текст

Требования к анимации:

- смена экранов: crossfade 180-240 миллисекунд, easing ease-out
- без резких параллаксов и без агрессивной физики
- учитывать prefers-reduced-motion: при включенной настройке анимации отключаются, остается статическая смена

#### Сценарий секций

##### Блок 1 - Чат

Заголовок: Говорите честно. Без оценки.  
Текст: Ассистент помогает разобраться в тревоге, усталости и сложных мыслях через диалог и практики.  
Экран в телефоне: главный экран чата.  
Примечание: пузырь ассистента должен быть коротким (2-3 строки), без длинного текста.

##### Блок 2 - Терапия по темам

Заголовок: Выберите состояние, которое сейчас важно.  
Текст: Быстрый вход в разговор, дыхание и практики по теме.  
Экран в телефоне: список тем терапии.

##### Блок 3 - Привычки

Заголовок: Формируйте устойчивые изменения.  
Текст: Привычки и напоминания настраиваются под себя, маленькими шагами.  
Экран в телефоне: список привычек (Избавиться).  
Опционально: показать “Избавиться” только как внутренний переключатель в рамках блока, без отдельного шага.

##### Блок 4 - Медитации

Заголовок: Звуки и практики для глубокого восстановления.  
Текст: Каталог медитаций и звуковых текстур для тревоги, сна и восстановления.  
Экран в телефоне: выбрать один визуально сильный экран (каталог или “Космическая текстура”).

##### Блок 5 - Дыхание

Заголовок: Регулируйте состояние за 60 секунд.  
Текст: Короткие практики: 4-4-4-4 для стабилизации, 4-7-8 для сна, 4-6 для снятия тревоги.  
Экран в телефоне: практика дыхания с кругом.  
Формат: короткий видео-луп 6-8 секунд в мокапе. Если видео недоступно, использовать статичный скрин.

#### Какие скрины использовать

Используем (5 основных):

- Чат
- Терапия (список тем)
- Привычки (Избавиться)
- Медитации (один выбранный экран)
- Дыхание (экран с кругом)

Не используем на первом релизе лендинга:

- дубли экрана привычек (оба сразу)
- дубли каталога медитаций
- промежуточные экраны навигации, которые не объясняют ценность

#### Реализация на фронтенде

- Desktop: 2 колонки (текст слева, телефон справа), телефон sticky
- Mobile: стек (телефон сверху, текст ниже), без sticky
- активный шаг определяется IntersectionObserver (порог 0.5) или scroll progress
- смена контента в телефоне: crossfade между изображениями, либо замена video source

#### Производительность

- Изображения: WebP/AVIF, размеры под реальную ширину мокапа (не грузить 4K)
- Видео: MP4/H.264, muted autoplay loop, poster обязателен
- Lazy loading для всех экранов кроме первого

## 6. Режимы CTA (релизный флаг)

Лендинг читает конфиг:

- `isReleased = false`: CTA открывает форму waitlist.
- `isReleased = true`: CTA ведёт на `https://my.mentala.app/auth`.

Политика кеша для `landing/config`:

- Источник истины: `GET /api/landing/config`.
- Серверный кэш: `Cache-Control: public, max-age=60, stale-while-revalidate=120`.
- Клиентский TTL при `SSR + SWR` по умолчанию не требуется.
- Если в клиенте остаётся локальный TTL, он должен быть в диапазоне `60..120` секунд.

## 7. API-контракт лендинга

### 7.1 `GET /api/landing/config`

Ответ:

```json
{
  "isReleased": false,
  "ctaUrl": "https://my.mentala.app/auth",
  "updatedAt": "2026-02-13T12:00:00.000Z"
}
```

Требования:

- Публичный endpoint.
- `Cache-Control`: `public, max-age=60, stale-while-revalidate=120`.
- Этот endpoint — единственный источник истины для release-режима (`isReleased`).

### 7.2 `POST /api/landing/lead`

Request:

```json
{
  "name": "Николай",
  "email": "user@example.com",
  "goalKey": "reduce_anxiety",
  "utmSource": "instagram",
  "utmMedium": "cpc",
  "utmCampaign": "launch_2026"
}
```

Response (новая запись):

```json
{
  "ok": true,
  "status": "created"
}
```

Response (дубликат по email):

```json
{
  "ok": true,
  "status": "duplicate"
}
```

Валидация:

- `name`: `1..120`.
- `email`: валидный email.
- `goalKey`: optional enum.
- UTM поля: optional, `0..120`.

Фиксированный список `goalKey` (v1):

- `reduce_anxiety` — снизить тревожность.
- `sleep_better` — улучшить сон.
- `reduce_stress` — снизить стресс/выгорание.

## 9. Безопасность и антиспам

Обязательные меры уже в первой версии:

- `Rate limit` для `POST /api/landing/lead` (IP + email hash).
- Honeypot-поле формы (скрытое, должно быть пустым).
- CORS только для доверенных origin (включая `https://mentala.app`).
- Логи без утечки чувствительных данных.
- Единый `X-Request-Id` в ответах (уже есть middleware).
- Базовая серверная валидация `Origin/Referer` для публичной формы.

Опционально в phase 2:

- hCaptcha/Cloudflare Turnstile.
- Блокировка по ASN/странам.

## 11. SEO, доступность, производительность

### 11.1 SEO baseline

- `title`, `description`, `canonical`.
- Open Graph + Twitter Card.
- `robots.txt`, `sitemap.xml`.
- JSON-LD: `Organization`, `WebSite`, `FAQPage`.
- Один `h1`, валидная иерархия заголовков, `alt` у изображений.

### 11.2 A11y baseline

- Контраст не ниже WCAG AA.
- Полная клавиатурная навигация.
- Видимый `focus` для интерактивных элементов.
- `prefers-reduced-motion` поддерживается.

### 11.3 Perf baseline

- LCP < 2.5s, CLS < 0.1 на мобильных.
- WebP/AVIF.
- Lazy-load ниже первого экрана.
- Минимум JS в критическом пути.

### 11.4 Кроссбраузерность и адаптивность (обязательно)

Базовое требование:

- Лендинг должен корректно работать начиная от ширины `320px` и выше, без горизонтального скролла и без «ломающихся» блоков.

Матрица обязательных ширин для проверки UI:

- `320`, `360`, `375`, `390`, `414`, `480`, `768`, `1024`, `1280`, `1440`, `1920`.

Обязательные платформы/браузеры:

- `Chrome` (desktop, последние 2 версии).
- `Safari` (macOS, последние 2 версии).
- `Firefox` (desktop, последние 2 версии).
- `Edge` (desktop, последние 2 версии).
- `Safari iOS` (`iOS 13+`).
- `Chrome Android` (`Android 8+`).

UX-инварианты для всех экранов:

- Все CTA видимы и кликабельны без overlap.
- Header/меню/модалка waitlist корректно перестраиваются на mobile.
- Типографика и отступы читаемы на `320px`.
- Интерактивные элементы имеют удобный tap-target (не меньше ~44px).
- Изображения/медиа не вылезают за контейнер.
- Анимации не ломают layout, `prefers-reduced-motion` соблюдается.

## 12. Аналитика (события)

Провайдер первой версии: `Яндекс Метрика`.

Подключение: счётчик подключается только на клиенте, если задана переменная окружения `NUXT_PUBLIC_YANDEX_METRIKA_ID` (числовой ID счётчика из кабинета Метрики). Плагин `plugins/yandex-metrika.client.ts` вставляет официальный код загрузки, композабл `useLandingAnalytics` отправляет цели (`reachGoal`). Без ID скрипт не загружается.

**Для продакшна (деплой через GitHub Actions):** ID подставляется при сборке из GitHub. Репозиторий → **Settings** → **Secrets and variables** → **Actions**. Создать **Repository variable** (Variables → New repository variable) или **Repository secret** (Secrets → New repository secret): имя `NUXT_PUBLIC_YANDEX_METRIKA_ID`, значение — числовой ID счётчика (например `106891177`). После сохранения пересобрать и задеплоить лендинг (пушить в ветку `landing` или перезапустить workflow).

Минимальный набор событий (реализованы):

- `landing_view`
- `landing_cta_click`
- `landing_modal_open`
- `landing_lead_submit_success`
- `landing_lead_submit_duplicate`
- `landing_lead_submit_error`
- `landing_scroll_depth_25/50/75/100`
- `landing_auth_redirect_click` (post-release)

Поля событий:

- `utm_*`, `referrer`, `isReleased`, `timestamp`.

Сделай очень красиво, с плавными анимациями. Используй библиотеки для анимаций, если нужно. Используй библиотеки для слайдеров вертикальных или горизонтальных. Главная цель - сделать эффектно и красиво.
