# Mentala: ТЗ на единый выбор голоса и гендерной персоны ассистента

Статус: draft v1.0  
Дата актуализации: 19 марта 2026

Официальные источники OpenAI, на которые должна опираться реализация:

- Audio Speech API: https://developers.openai.com/api/reference/resources/audio/subresources/speech/methods/create
- Text-to-Speech guide: https://platform.openai.com/docs/guides/text-to-speech
- Realtime guide: https://platform.openai.com/docs/guides/realtime
- Realtime conversations / sessions: https://platform.openai.com/docs/guides/realtime-conversations
- Audio overview: https://platform.openai.com/docs/guides/audio/quickstart

## 1. Цель

Добавить в Mentala единый пользовательский выбор голоса ассистента, который:

- работает одинаково для обычной озвучки текстового чата и для Realtime Voice;
- доступен приложению уже на этапе bootstrap через `GET /api/user/me`;
- влияет не только на `voice` OpenAI, но и на гендерную самопрезентацию ассистента в промптах;
- не создаёт дублирующихся источников истины и не размазывает настройки по нескольким сущностям.

Результат должен быть таким:

1. Пользователь в настройках ассистента выбирает сегмент `Женский` или `Мужской`.
2. Внутри выбранного сегмента пользователь выбирает конкретный голос.
3. Приложение сохраняет единый канонический выбор голоса.
4. Из выбранного голоса вычисляется гендерная персона ассистента.
5. И `Responses`-чат, и `Realtime Voice`, и обычная TTS-озвучка используют один и тот же выбор.

## 2. Зафиксированные продуктовые решения

Ниже решения уже приняты:

1. Настройка должна быть единой для двух режимов:
   - обычный чат с озвучкой ответа;
   - realtime voice.
2. При bootstrap приложения выбранный голос должен приходить в `GET /api/user/me`.
3. Отдельное persisted поле `assistant_gender` в первой версии не вводится.
4. Источником истины для выбора голоса остаётся chat/assistant settings контур, а не профиль пользователя.
5. Гендер ассистента вычисляется из каталога голосов и используется:
   - в UI для сегментации списка;
   - в prompt/instructions для самопрезентации ассистента.
6. В первой версии имя ассистента не становится отдельной пользовательской настройкой:
   - продуктовая идентичность остаётся фиксированной: `Ассистент Mentala` / `Mentala`;
   - при обычном общении ассистент использует в основном первое лицо (`я`), а не постоянное именование себя.
7. В единый selector можно включать только те голоса, которые поддерживаются и в `Realtime`, и в `Audio Speech API`.
8. Категории `Женский` / `Мужской` являются продуктовой классификацией Mentala, а не контрактом OpenAI API.

## 3. Что есть сейчас

Сейчас в проекте используются два разных дефолтных голоса:

- `Realtime` по умолчанию использует `marin`;
- обычная озвучка текстового чата по умолчанию использует `sage`.

Из-за этого пользователь слышит разный тембр в двух режимах, хотя продуктово ожидает одного и того же ассистента.

Дополнительно сейчас гендерная персона ассистента явно не фиксируется единым слоем:

- голос выбирается отдельно;
- prompt-слой не получает явный `assistantGender` как продуктовую переменную;
- поэтому ассистент не обязан последовательно говорить от мужского или женского лица.

## 4. Архитектурный принцип

Нужно разделить:

1. **Источник истины**

   Это один persisted выбор конкретного `assistantVoice`.

2. **Проекция для bootstrap**

   Это `assistantSettings` внутри `GET /api/user/me`.

3. **Производная prompt-переменная**

   Это `assistantGender`, вычисляемый из voice catalog.

Ключевой инвариант:

- приложение хранит **один канонический voice id**;
- все остальные поля (`gender`, `label`, `previewText`, `supportedInRealtime`, `supportedInTts`) являются либо derived, либо catalog-backed данными;
- нельзя хранить одновременно независимые `assistantVoice` и `assistantGender`, если между ними нет жёсткой синхронизации.

## 5. Почему не нужно хранить отдельный `assistantGender` в БД в v1

Если хранить и `assistantVoice`, и отдельный `assistantGender`, возникает риск рассинхрона:

- `assistantGender = female`, а `assistantVoice = onyx`;
- UI показывает один сегмент, а провайдер получает голос другого сегмента;
- prompt и фактический audio output расходятся.

В первой версии это лишняя сложность без пользы.

Правильный вариант:

- хранить только `assistantVoice`;
- `assistantGender` вычислять через единый shared catalog.

Отдельное поле `assistantPersonaGender` можно вводить только в будущем, если продукт захочет **развязать** голос и персону. В этом ТЗ такая развязка не нужна.

## 6. Data model

### 6.1 Источник истины в БД

Использовать существующий контур `chat_settings`.

Добавить в `chat_settings` новое поле:

- `assistant_voice text not null default 'sage'`

Причины:

- это настройка поведения ассистента, а не профиль пользователя;
- она уже логически соседствует с текущими chat/assistant-переключателями (`voice`, `avatar`, memory flags);
- это позволяет не раздувать `users` и не плодить ещё одну таблицу.

### 6.2 Что не добавлять в БД в v1

Не добавлять:

- `assistant_gender`
- `assistant_voice_gender`
- `assistant_display_name`

Если эти значения нужны клиенту, они должны приходить как derived projection.

### 6.3 Shared voice catalog

Нужен единый shared catalog, например в `shared/constants/assistantVoiceCatalog.ts`.

Каждая запись каталога должна содержать:

- `id`
- `label`
- `gender`
- `description`
- `previewText`
- `supportedInRealtime`
- `supportedInTts`
- `sortOrder`

Пример логической структуры:

```ts
type AssistantVoiceCatalogItem = {
  id: string;
  label: string;
  gender: 'female' | 'male';
  description: string;
  previewText: string;
  supportedInRealtime: boolean;
  supportedInTts: boolean;
  sortOrder: number;
};
```

Важно:

- каталог является продуктовым слоем Mentala;
- категоризация `female/male` задаётся нами вручную;
- нельзя рассчитывать на то, что OpenAI сам вернёт `gender`.

### 6.4 Канонический набор голосов для v1

В selector первой версии включать только пересечение режимов `Realtime` и `TTS`.

Каталог должен быть curated и коротким. Не нужно выводить все возможные голоса OpenAI подряд.

Рекомендуемый формат:

- 2–4 голоса в сегменте `Женский`
- 2–4 голоса в сегменте `Мужской`

Итоговый список фиксируется продуктово в каталоге и не хранится в БД.

## 7. API контракт

### 7.1 `GET /api/user/me`

`GET /api/user/me` должен возвращать уже вычисленную bootstrap-проекцию:

```ts
user: {
  ...
  assistantSettings: {
    voice: 'sage',
    voiceLabel: 'Sage',
    voiceGender: 'female',
  }
}
```

Правила:

- `voice` берётся из `chat_settings.assistant_voice`;
- `voiceLabel` и `voiceGender` достраиваются по shared catalog;
- если в БД лежит неизвестный/устаревший `voice`, сервер должен безопасно откатиться на дефолтный каталоговый голос.

Важно:

- `GET /api/user/me` в этом дизайне является **read model**;
- писать голос через `PATCH /api/user/me` не нужно.

### 7.2 `GET /api/settings/chat`

Это основной read API для assistant/chat settings.

Он должен возвращать:

```ts
settings: {
  voice: boolean,
  avatar: boolean,
  enablePreviousResponseId: boolean,
  enableSummary: boolean,
  assistantVoice: 'sage'
}
```

По желанию дополнительно можно вернуть derived projection:

```ts
assistantVoiceMeta: {
  label: 'Sage',
  gender: 'female'
}
```

Но каноническим persisted полем остаётся именно `assistantVoice`.

### 7.3 `PATCH /api/settings/chat`

Через этот endpoint должен сохраняться выбор пользователя.

Patch payload:

```ts
{
  assistantVoice?: string
}
```

Валидация:

- `assistantVoice` обязателен к проверке по каталогу;
- нельзя сохранять голос, которого нет в текущем shared catalog;
- нельзя сохранять голос, который не поддерживается одновременно в `Realtime` и `TTS`, если используется единый selector.

Ответ:

```ts
settings: {
  ...
  assistantVoice: 'sage'
}
```

### 7.4 Single-source правило

После сохранения:

- `chat_settings.assistant_voice` обновляется;
- `GET /api/settings/chat` начинает возвращать новое значение;
- `GET /api/user/me` начинает проецировать тот же voice в `assistantSettings`.

Нельзя делать два независимых write-path:

- отдельно в `/api/user/me`
- отдельно в `/api/settings/chat`

Источник истины должен быть один.

## 8. Frontend UX

### 8.1 Где размещать настройку

Лучшее место: страница `Настройки ассистента` (`/settings/assistant`).

Причина:

- это настройка не профиля пользователя, а поведения ассистента;
- там уже находятся `Стиль общения` и `Обращение`;
- голос и гендерная персона ассистента логически относятся к тому же экрану.

Не размещать настройку:

- на странице профиля пользователя;
- в privacy;
- внутри realtime-панели в чате;
- отдельным несвязанным top-level экраном в settings.

### 8.2 Что показать на `settings/index`

На `settings/index` в блоке `НАСТРОЙКИ АССИСТЕНТА` нужно добавить summary-строку:

- заголовок: `Голос ассистента`
- подзаголовок: например `Женский • Sage`

Нажатие ведёт на `/settings/assistant`.

### 8.3 Что показать на `/settings/assistant`

На странице `Настройки ассистента` нужно добавить новый блок:

1. Сегмент-переключатель:
   - `Женский`
   - `Мужской`

2. Ниже список/сетка голосов выбранного сегмента.

3. Для каждого голоса:
   - название;
   - короткое описание тембра;
   - `preview` кнопка;
   - состояние `selected`.

4. Общая кнопка `Сохранить`.

### 8.4 Важное UX-правило

Переключатель `Женский / Мужской` является в UI **фильтром и продуктовым способом выбора персоны**, но persisted result всё равно должен быть конкретным `assistantVoice`.

Логика:

- пользователь переключил сегмент;
- UI показывает только голоса этого сегмента;
- если текущий выбранный голос не относится к сегменту, UI автоматически подставляет дефолтный голос этого сегмента;
- в сохранение уходит итоговый `assistantVoice`.

### 8.5 Preview

У каждого голоса должна быть preview-проверка.

Preview должен:

- использовать тот же TTS pipeline, что и обычная озвучка;
- не менять текущие настройки автоматически;
- играть короткую, фиксированную product-safe фразу;
- всегда останавливаться при выборе другого preview.

Realtime preview отдельно не нужен.

## 9. Поведение при активной realtime-сессии

Если пользователь меняет настройку голоса во время активной realtime-сессии:

- текущую realtime-сессию не перестраивать на лету;
- показать понятное UX-правило: новый голос применится при следующем запуске realtime;
- обычная TTS-озвучка текстового чата может использовать новый голос сразу после сохранения.

Причина:

- в Realtime смена voice внутри уже звучащей сессии ненадёжна и продуктово не нужна;
- граница применения должна быть простой и предсказуемой.

## 10. Backend / provider integration

### 10.1 Обычный текстовый чат с озвучкой

Текущий TTS pipeline должен использовать `assistantVoice` пользователя как дефолт.

Правило:

- если voice явно не передан в endpoint preview/tts, брать его из `chat_settings.assistant_voice`;
- жёсткий fallback на дефолтный голос допускается только если каталоговый голос устарел или отсутствует.

### 10.2 Realtime Voice

При `POST /api/realtime/session` backend должен:

- читать `assistantVoice` пользователя;
- валидировать его через catalog;
- вставлять его в OpenAI realtime session config.

Голос в realtime фиксируется на момент старта конкретной voice-сессии.

### 10.3 Responses текстовый режим

`Responses API` продолжает отвечать текстом как и раньше.

Но prompt/instructions для него должны получать derived assistant persona variables:

- `assistantVoice`
- `assistantGender`
- `assistantDisplayName`

Важно:

- `Responses API` в рамках этого ТЗ не становится отдельным аудио-каналом;
- audio playback остаётся через TTS слой;
- prompt-persona и voice-output должны быть консистентны.

## 11. Prompt / instruction contract

### 11.1 Общий принцип

Нужно ввести единый prompt-builder слой для assistant persona.

Он должен строить компактный persona block, который подмешивается:

- в `Responses API` developer/system prompt;
- в `Realtime` instructions.

Нельзя дублировать это правило отдельно в двух местах разным текстом.

### 11.2 Какие переменные должны быть доступны prompt-слою

Нужно нормализовать и передавать:

- `assistantVoice`
- `assistantGender`
- `assistantDisplayName`
- `userAddressing`
- `userGender` (если уже используется существующим слоем персонализации)

### 11.3 Что именно должен знать ассистент

Если выбран голос женского сегмента, модель должна понимать:

- она говорит от женской персоны;
- при самореференции использует женские формы:
  - `я сделала`
  - `я подумала`
  - `я заметила`

Если выбран голос мужского сегмента:

- она говорит от мужской персоны;
- при самореференции использует мужские формы:
  - `я сделал`
  - `я подумал`
  - `я заметил`

### 11.4 Ограничения prompt-инструкции

Нельзя превращать это в театральную roleplay-персону.

Инструкция должна быть прагматичной:

- ассистент должен сохранять продуктовый стиль Mentala;
- не должен постоянно подчёркивать свой пол;
- не должен навязчиво напоминать, что он женщина или мужчина;
- не должен выдумывать телесность или биографию;
- не должен менять тон, безопасность, кризисные правила и clinical-границы из-за выбранного голоса.

### 11.5 Рекомендуемая смысловая формулировка prompt-блока

Смысл, который должен быть закреплён:

- Ты — ассистент Mentala.
- Твоя продуктовая голосовая персона: `female` или `male`.
- Если ты говоришь о себе в первом лице, используй соответствующие грамматические формы.
- Не акцентируй это без необходимости.
- Если пользователь не затрагивает тему пола ассистента, не выноси её в центр ответа.

### 11.6 Имя ассистента

В первой версии не добавляется отдельная кастомизация имени.

Правило:

- фиксированная идентичность: `Ассистент Mentala` / `Mentala`;
- если нужен self-reference, использовать прежде всего `я`;
- явное именование себя использовать только по ситуации.

## 12. Слои, которые должны использовать assistant persona

Обязательно:

- обычный чат (`Responses API`);
- realtime voice instructions;
- welcome/opening слой, если он использует self-reference ассистента.

Не обязательно в v1:

- AI-уведомления;
- вспомогательные offline-тексты;
- внешние рекламные/маркетинговые тексты;
- практики и медитации, где речь идёт о заранее записанном или статическом контенте.

То есть scope этого ТЗ:

- chat assistant persona
- realtime assistant persona

без расширения на весь продукт.

## 14. Acceptance criteria

Решение считается готовым, если:

1. На странице настроек ассистента пользователь видит:
   - сегмент `Женский / Мужской`;
   - список голосов внутри сегмента;
   - preview для голоса.
2. После сохранения выбор переживает logout/login и перезапуск приложения.
3. После bootstrap `GET /api/user/me` уже содержит `assistantSettings`.
4. Обычная TTS-озвучка использует выбранный голос.
5. Новая realtime-сессия использует тот же выбранный голос.
6. `Responses`-чат и `Realtime` получают одинаковую derived persona instruction по полу ассистента.
7. При женском голосе ассистент последовательно использует женские формы при self-reference.
8. При мужском голосе ассистент последовательно использует мужские формы при self-reference.
9. Нет второго независимого write-path для тех же данных.
10. Нет дублирования voice/persona mapping в нескольких местах.

## 15. Риски и защитные меры

### Риск 1. Голос и prompt-персона разъедутся

Защита:

- один source of truth `assistantVoice`;
- `assistantGender` всегда derived.

### Риск 2. В разных режимах окажутся разные списки голосов

Защита:

- единый shared catalog;
- в selector выводить только пересечение поддерживаемых голосов.

### Риск 3. Пользователь поменял голос в active realtime-session и ожидает мгновенный эффект

Защита:

- явно зафиксировать правило `применится со следующего запуска realtime`.

### Риск 4. Prompt станет слишком многословным и начнёт тратить лишние токены

Защита:

- persona block должен быть коротким;
- не дублировать одно и то же правило в нескольких prompt-слоях.

## 16. Что не входит в это ТЗ

Не входит в первую итерацию:

- кастомное имя ассистента как пользовательская настройка;
- независимая развязка `voice` и `assistant persona gender`;
- пользовательская загрузка собственных голосов;
- отдельные голоса только для `Realtime` или только для `TTS`;
- автоматическое A/B тестирование голосов;
- отдельный paywall на выбор голосов;
- миграция AI-уведомлений и прочих несвязанных AI-текстов на новую assistant-persona модель.

## 17. Итоговое решение

В v1 нужно сделать так:

1. В БД хранить только `assistantVoice`.
2. В `GET /api/user/me` возвращать derived `assistantSettings`.
3. В UI давать пользователю выбор `Женский / Мужской` + конкретный голос.
4. В prompt/instructions передавать derived `assistantGender`, чтобы ассистент говорил от соответствующего пола.
5. Один и тот же выбор применять одновременно к:
   - обычной озвучке чата;
   - realtime voice;
