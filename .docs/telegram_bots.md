Техническое задание

Telegram-уведомления для Mentala. Первая итерация

1. Цель

Реализовать легковесную систему Telegram-уведомлений для ключевых событий проекта Mentala.

Система нужна для того, чтобы:
• оперативно получать важные технические уведомления;
• отслеживать ключевые бизнес-события;
• видеть важные пользовательские события;
• получать краткую ежедневную сводку;
• не влиять на производительность основного приложения;
• не замедлять пользовательские сценарии.

1. Главный принцип

Отправка Telegram-уведомлений не должна выполняться синхронно в пользовательском запросе.

Запрещено:
• отправлять сообщение в Telegram прямо внутри регистрации пользователя;
• отправлять сообщение прямо внутри обработки оплаты;
• ждать ответ Telegram API перед возвратом ответа пользователю;
• делать дополнительные тяжелые запросы ради формирования текста уведомления.

Разрешено только:
• быстро зафиксировать внутреннее событие;
• передать его в очередь;
• обработать отправку в фоне отдельным воркером.

Итог:
• пользователь не ждет Telegram;
• основное приложение не страдает;
• нагрузка на сервер минимальная и контролируемая.

1. Чаты Telegram в первой итерации

В первой итерации используются 4 логических канала.

3.1. DevOps чат

Назначение:
технические и инфраструктурные события.

Что отправлять:
• мало свободного места на диске;
• Redis недоступен;
• PostgreSQL недоступен;
• не работает отправка push-уведомлений;
• критические серверные ошибки уровня 500;
• другие технические события, явно помеченные как критичные.

3.2. Billing чат

Назначение:
платежи, подписки, финансовые ошибки.

Что отправлять:
• успешный платеж;
• неуспешный платеж;
• возврат;
• успешное создание подписки;
• отмена подписки;
• критическая ошибка биллинга;
• ошибка обработки webhook платежной системы;
• ошибка создания или подтверждения платежа.

3.3. Users чат

Назначение:
ключевые пользовательские события и рост продукта.

Что отправлять:
• регистрация нового пользователя;
• удаление аккаунта;
• достижение круглых порогов по числу регистраций:
• 100
• 500
• 1000
• далее по настраиваемому списку.

Для круглых чисел использовать праздничный формат сообщения с позитивным эмодзи.

3.4. Errors чат

Назначение:
только важные прикладные ошибки, которые требуют внимания.

Что отправлять:
• критическая ошибка на бэкенде;
• критическая ошибка в важной бизнес-логике;
• ошибка, из-за которой ломается ключевой пользовательский сценарий;
• ошибка интеграции с внешним сервисом, если это влияет на работу продукта;
• повторяющаяся ошибка, если она превысила заданный порог.

Не отправлять сюда мелкие предупреждения, разовые несущественные сбои и шум.

⸻

1. Daily summary

Отдельный чат для ежедневных отчетов не создавать.

Ежедневная сводка отправляется в Users чат.

4.1. Время отправки

Каждый день в 10:00 утра по серверному времени проекта или по явно заданной временной зоне проекта.

Нужно зафиксировать одну временную зону в конфигурации и использовать ее везде одинаково.

4.2. За какой период

Сводка формируется за предыдущий календарный день.

Пример:
в 10:00 13 марта отправляется сводка за 12 марта.

4.3. Что включать в daily summary

В одном сообщении отправлять:
• количество новых регистраций за день;
• количество удалений аккаунта за день;
• количество активных пользователей за день;
• количество новых подписок за день;
• количество успешных платежей за день;
• количество неуспешных платежей за день;
• количество возвратов за день;
• общую сумму успешных платежей за день;
• количество критических ошибок за день;
• количество технических критических событий за день;
• количество достижений по регистрационным порогам, если были.

Если часть данных в первой итерации сложно или дорого собирать, обязательный минимум такой:
• новые регистрации;
• активные пользователи;
• новые подписки;
• успешные платежи;
• неуспешные платежи;
• возвраты;
• сумма успешных платежей;
• критические ошибки.

4.4. Формат daily summary

Сообщение должно быть компактным, читаемым, без простыни текста.

Пример структуры:

📊 Сводка за 12.03.2026

Пользователи

- Новые регистрации: 14
- Активные пользователи: 97
- Удаления аккаунта: 1

Подписки и платежи

- Новые подписки: 3
- Успешные платежи: 5
- Неуспешные платежи: 2
- Возвраты: 0
- Сумма успешных платежей: 2 495 RUB

Система

- Критические ошибки приложения: 1
- Технические критические события: 2

1. Архитектурный подход

6.1. Общая схема

Нужно реализовать событийную схему с фоновой доставкой.

Поток работы: 1. В приложении происходит важное событие. 2. Приложение публикует внутреннее событие. 3. Внутреннее событие ставится в очередь. 4. Отдельный воркер обрабатывает очередь. 5. Воркер формирует короткий текст уведомления. 6. Воркер отправляет сообщение в нужный Telegram чат. 7. Результат доставки логируется.

Важно

Основной HTTP запрос не должен ждать Telegram API.

⸻

6.2. Требования к производительности

Система должна быть реализована так, чтобы:
• не увеличивать заметно время ответа API;
• не создавать тяжелых запросов к базе в момент отправки уведомлений;
• не делать каскад дополнительных вычислений;
• не создавать сильную нагрузку на Redis;
• не спамить Telegram одинаковыми сообщениями.

Обязательные ограничения
• отправка только через очередь;
• минимальный payload события;
• форматирование сообщения без тяжелых обогащений;
• дедупликация одинаковых критических событий;
• ограничение retry;
• защита от спама одинаковых ошибок.

1. Требования к payload событий

Payload должен быть самодостаточным и коротким.

Запрещено делать так, чтобы при форматировании сообщения система шла в базу за кучей связанных данных.

То есть событие должно уже содержать нужный минимум.

Пример. Регистрация пользователя

{
type: 'user.registered',
payload: {
userId: 'usr_123',
registeredAt: '2026-03-12T09:12:00.000Z',
authProvider: 'email'
}
}

Пример. Успешный платеж

{
type: 'billing.payment_succeeded',
payload: {
userId: 'usr_123',
paymentId: 'pay_456',
amount: 499,
currency: 'RUB',
planCode: 'premium_monthly',
paidAt: '2026-03-12T09:20:00.000Z'
}
}

Пример. Критическая ошибка

{
type: 'error.app_critical',
payload: {
code: 'INTERNAL_SERVER_ERROR',
message: 'Unhandled exception in subscription activation',
route: '/api/billing/activate',
requestId: 'req_789',
createdAt: '2026-03-12T09:25:00.000Z'
}
}

1. Очередь и воркер

Для отправки уведомлений использовать отдельную очередь.

С учетом текущего стека проекта логично использовать BullMQ и Redis.

Требования
• очередь для Telegram-уведомлений должна быть отдельной;
• обработка должна идти в фоне;
• retry ограничить, например, 3 попытками;
• использовать backoff;
• при ошибке доставки не ломать основное приложение;
• результат доставки логировать.

Пример retry политики
• первая попытка сразу;
• вторая через 30 секунд;
• третья через 2 минуты.

1. Дедупликация и защита от шума

Это обязательно.

11.1. Для DevOps и Errors

Если приходит одинаковое критическое событие несколько раз подряд за короткое окно времени, не нужно отправлять каждое.

Примеры:
• Redis недоступен 50 раз за 3 минуты;
• одна и та же ошибка 500 пришла 100 раз;
• PostgreSQL недоступен сериями.

Нужно:
• отправить первое сообщение сразу;
• затем временно подавлять дубли;
• при необходимости отправить summary, например:
“Событие повторилось 37 раз за 5 минут”.

11.2. Для Users

Не делать дедупликацию регистраций.
Каждая новая регистрация должна приходить отдельно.

Но milestone события отправлять только один раз при достижении нужного порога.

11.3. Для Billing

Каждую транзакцию отправлять отдельно, если это успешный платеж, неуспешный платеж или возврат.

Но повторяющиеся системные billing errors можно агрегировать.

1. Логирование доставок

Нужно хранить лог попыток отправки уведомлений.

Минимально сохранять:
• event id;
• event type;
• целевой канал;
• статус доставки;
• количество попыток;
• текст ошибки, если был сбой;
• created at;
• sent at.

Срок хранения

Для первой итерации достаточно хранить ограниченно.

Пример:
14-30 дней.

Потом старые записи очищать cron-задачей.

Это нужно, чтобы:
• видеть, что реально отправилось;
• понимать, где были сбои;
• не раздувать базу бесконечно.

1. Источники событий

   13.1. DevOps

Часть DevOps уведомлений уже отправляется кодом, который крутится прямо на сервере.

Для первой итерации допустимо сохранить текущий серверный механизм там, где он уже работает стабильно.

Но новые технические события нужно постепенно приводить к единому формату.

То есть:
• существующий алерт по диску можно временно оставить как есть;
• новые DevOps уведомления лучше сразу строить через общую систему событий;
• в будущем DevOps слой можно унифицировать.

13.2. Backend события

• критические ошибки;

1. Что считать критической ошибкой

Чтобы не превратить чат ошибок в свалку, нужно ввести явное правило.

Критическая ошибка - это ошибка, которая:
• ломает ключевой пользовательский сценарий;
• ломает платежный сценарий;
• ломает авторизацию или регистрацию;
• ломает отправку важных уведомлений;
• приводит к массовым 500 ошибкам;
• указывает на недоступность важной интеграции.

Не считать критической:
• локальные предупреждения;
• единичные неважные сбои;
• recoverable ошибки без влияния на пользователя;
• технические сообщения для отладки.

1. Критерии готовности

Функционал считается готовым, если:
• Telegram уведомления уходят в нужные чаты;
• пользователи не ждут отправку Telegram сообщений;
• регистрация, платежи и другие важные сценарии не замедляются;
• критические ошибки приходят в чат ошибок;
• важные биллинговые события приходят в billing чат;
• регистрация и удаление аккаунта приходят в users чат;
• daily summary приходит в 10:00;
• одинаковые критические события не спамят чат;
• ошибки доставки логируются.

1. Моя рекомендация по одному важному нюансу

Daily summary в Users чат - это нормальное решение.

Отдельный чат под отчеты на первой итерации не нужен. Иначе начнется лишнее дробление, а пользы ноль.

Но я бы добавил правило:
• оперативные пользовательские события идут в течение дня;
• daily summary отправляется всегда одним отдельным сообщением утром;
• формат этого сообщения должен быть стабильным, чтобы его легко читать глазами.

То есть идея правильная, оставляем именно так.

# Техническое задание

## Telegram-уведомления для Mentala. Первая итерация

Ниже описана первая итерация Telegram-уведомлений без лишней сложности. Только ключевые события, которые реально нужны на старте.

## 1. Цель

Реализовать легковесную систему Telegram-уведомлений для ключевых событий проекта Mentala.

Система нужна для того, чтобы:

- оперативно получать важные технические уведомления;
- отслеживать ключевые бизнес-события;
- видеть важные пользовательские события;
- получать краткую ежедневную сводку;
- не влиять на производительность основного приложения;
- не замедлять пользовательские сценарии.

## 2. Главный принцип

Отправка Telegram-уведомлений не должна выполняться синхронно в пользовательском запросе.

Запрещено:

- отправлять сообщение в Telegram прямо внутри регистрации пользователя;
- отправлять сообщение прямо внутри обработки оплаты;
- ждать ответ Telegram API перед возвратом ответа пользователю;
- делать дополнительные тяжелые запросы ради формирования текста уведомления.

Разрешено только:

- быстро зафиксировать внутреннее событие;
- передать его в очередь;
- обработать отправку в фоне отдельным воркером.

Итог:

- пользователь не ждет Telegram;
- основное приложение не страдает;
- нагрузка на сервер минимальная и контролируемая.

## 3. Чаты Telegram в первой итерации

В первой итерации используются 4 логических канала.

### 3.1. DevOps чат

Назначение: технические и инфраструктурные события.

Что отправлять:

- мало свободного места на диске;
- Redis недоступен;
- PostgreSQL недоступен;
- не работает отправка push-уведомлений;
- критические серверные ошибки уровня 500;
- другие технические события, явно помеченные как критичные.

### 3.2. Billing чат

Назначение: платежи, подписки, финансовые ошибки.

Что отправлять:

- успешный платеж;
- неуспешный платеж;
- возврат;
- успешное создание подписки;
- отмена подписки;
- критическая ошибка биллинга;
- ошибка обработки webhook платежной системы;
- ошибка создания или подтверждения платежа.

### 3.3. Users чат

Назначение: ключевые пользовательские события и рост продукта.

Что отправлять:

- регистрация нового пользователя;
- удаление аккаунта;
- достижение круглых порогов по числу регистраций: 100, 500, 1000 и далее по настраиваемому списку.

Для круглых чисел использовать праздничный формат сообщения с позитивным эмодзи.

### 3.4. Errors чат

Назначение: только важные прикладные ошибки, которые требуют внимания.

Что отправлять:

- критическая ошибка на бэкенде;
- критическая ошибка в важной бизнес-логике;
- ошибка, из-за которой ломается ключевой пользовательский сценарий;
- ошибка интеграции с внешним сервисом, если это влияет на работу продукта;
- повторяющаяся ошибка, если она превысила заданный порог.

Не отправлять сюда мелкие предупреждения, разовые несущественные сбои и шум.

## 4. Daily summary

Отдельный чат для ежедневных отчетов не создавать.

Ежедневная сводка отправляется в Users чат.

### 4.1. Время отправки

Каждый день в 10:00 утра по серверному времени проекта или по явно заданной временной зоне проекта.

Нужно зафиксировать одну временную зону в конфигурации и использовать ее везде одинаково.

### 4.2. За какой период

Сводка формируется за предыдущий календарный день.

Пример: в 10:00 13 марта отправляется сводка за 12 марта.

### 4.3. Что включать в daily summary

В одном сообщении отправлять:

- количество новых регистраций за день;
- количество удалений аккаунта за день;
- количество активных пользователей за день;
- количество новых подписок за день;
- количество успешных платежей за день;
- количество неуспешных платежей за день;
- количество возвратов за день;
- общую сумму успешных платежей за день;
- количество критических ошибок за день;
- количество технических критических событий за день;
- количество достижений по регистрационным порогам, если были.

Если часть данных в первой итерации сложно или дорого собирать, обязательный минимум такой:

- новые регистрации;
- активные пользователи;
- новые подписки;
- успешные платежи;
- неуспешные платежи;
- возвраты;
- сумма успешных платежей;
- критические ошибки.

### 4.4. Формат daily summary

Сообщение должно быть компактным, читаемым, без простыни текста.

Пример структуры:

```text
📊 Сводка за 12.03.2026

Пользователи
- Новые регистрации: 14
- Активные пользователи: 97
- Удаления аккаунта: 1

Подписки и платежи
- Новые подписки: 3
- Успешные платежи: 5
- Неуспешные платежи: 2
- Возвраты: 0
- Сумма успешных платежей: 2 495 RUB

Система
- Критические ошибки приложения: 1
- Технические критические события: 2
```

## 5. Что не входит в первую итерацию

Не делать на этом этапе:

- Security чат;
- антибот-логику;
- детальную модерацию;
- отдельные отчеты по маркетингу;
- уведомления про завершение onboarding;
- уведомления про создание привычек;
- уведомления про запуск голосового режима;
- уведомления про первый чат;
- уведомления про каждое пользовательское действие;
- сложную аналитическую панель;
- тонкую настройку правил из админки.

Это все переносится на следующую итерацию.

## 6. Архитектурный подход

### 6.1. Общая схема

Нужно реализовать событийную схему с фоновой доставкой.

Поток работы:

1. В приложении происходит важное событие.
2. Приложение публикует внутреннее событие.
3. Внутреннее событие ставится в очередь.
4. Отдельный воркер обрабатывает очередь.
5. Воркер формирует короткий текст уведомления.
6. Воркер отправляет сообщение в нужный Telegram чат.
7. Результат доставки логируется.

Важно: основной HTTP запрос не должен ждать Telegram API.

### 6.2. Требования к производительности

Система должна быть реализована так, чтобы:

- не увеличивать заметно время ответа API;
- не создавать тяжелых запросов к базе в момент отправки уведомлений;
- не делать каскад дополнительных вычислений;
- не создавать сильную нагрузку на Redis;
- не спамить Telegram одинаковыми сообщениями.

Обязательные ограничения:

- отправка только через очередь;
- минимальный payload события;
- форматирование сообщения без тяжелых обогащений;
- дедупликация одинаковых критических событий;
- ограничение retry;
- защита от спама одинаковых ошибок.

### 6.3. Минимальные правила надежности

Обязательно предусмотреть:

- retry с ограниченным количеством попыток;
- backoff между попытками;
- таймаут на запрос к Telegram API;
- логирование неудачных отправок;
- безопасную обработку ошибок воркера без падения основного приложения.

## 8. Требования к payload событий

Payload должен быть самодостаточным и коротким.

Запрещено делать так, чтобы при форматировании сообщения система шла в базу за кучей связанных данных.

То есть событие должно уже содержать нужный минимум.

Пример. Регистрация пользователя:

```ts
{
  type: 'user.registered',
  payload: {
    userId: 'usr_123',
    registeredAt: '2026-03-12T09:12:00.000Z',
    authProvider: 'email',
  },
}
```

Пример. Успешный платеж:

```ts
{
  type: 'billing.payment_succeeded',
  payload: {
    userId: 'usr_123',
    paymentId: 'pay_456',
    amount: 499,
    currency: 'RUB',
    planCode: 'premium_monthly',
    paidAt: '2026-03-12T09:20:00.000Z',
  },
}
```

Пример. Критическая ошибка:

```ts
{
  type: 'error.app_critical',
  payload: {
    code: 'INTERNAL_SERVER_ERROR',
    message: 'Unhandled exception in subscription activation',
    route: '/api/billing/activate',
    requestId: 'req_789',
    createdAt: '2026-03-12T09:25:00.000Z',
  },
}
```

## 10. Очередь и воркер

Для отправки уведомлений использовать отдельную очередь.

С учетом текущего стека проекта логично использовать BullMQ и Redis.

Требования:

- очередь для Telegram-уведомлений должна быть отдельной;
- обработка должна идти в фоне;
- retry ограничить, например, 3 попытками;
- использовать backoff;
- при ошибке доставки не ломать основное приложение;
- результат доставки логировать.

Пример retry политики:

- первая попытка сразу;
- вторая через 30 секунд;
- третья через 2 минуты.

## 11. Дедупликация и защита от шума

Это обязательно.

### 11.1. Для DevOps и Errors

Если приходит одинаковое критическое событие несколько раз подряд за короткое окно времени, не нужно отправлять каждое.

Примеры:

- Redis недоступен 50 раз за 3 минуты;
- одна и та же ошибка 500 пришла 100 раз;
- PostgreSQL недоступен сериями.

Нужно:

- отправить первое сообщение сразу;
- затем временно подавлять дубли;
- при необходимости отправить summary, например: "Событие повторилось 37 раз за 5 минут".

### 11.2. Для Users

Не делать дедупликацию регистраций. Каждая новая регистрация должна приходить отдельно.

Но milestone события отправлять только один раз при достижении нужного порога.

### 11.3. Для Billing

Каждую транзакцию отправлять отдельно, если это успешный платеж, неуспешный платеж или возврат.

Но повторяющиеся системные billing errors можно агрегировать.

## 12. Логирование доставок

Нужно хранить лог попыток отправки уведомлений.

Минимально сохранять:

- event id;
- event type;
- целевой канал;
- статус доставки;
- количество попыток;
- текст ошибки, если был сбой;
- created at;
- sent at.

Срок хранения:

- для первой итерации достаточно 14-30 дней;
- потом старые записи очищать cron-задачей.

Это нужно, чтобы:

- видеть, что реально отправилось;
- понимать, где были сбои;
- не раздувать базу бесконечно.

## 13. Источники событий

### 13.1. DevOps

Часть DevOps уведомлений уже отправляется кодом, который крутится прямо на сервере.

Для первой итерации допустимо сохранить текущий серверный механизм там, где он уже работает стабильно.

Но новые технические события нужно постепенно приводить к единому формату.

То есть:

- существующий алерт по диску можно временно оставить как есть;
- новые DevOps уведомления лучше сразу строить через общую систему событий;
- в будущем DevOps слой можно унифицировать.

### 13.2. Backend события

Основные новые события должны публиковаться из серверной логики приложения:

- регистрация пользователя;
- удаление аккаунта;
- платежные события;

## 16. Что считать критической ошибкой

Чтобы не превратить чат ошибок в свалку, нужно ввести явное правило.

Критическая ошибка - это ошибка, которая:

- ломает ключевой пользовательский сценарий;
- ломает платежный сценарий;
- ломает авторизацию или регистрацию;
- ломает отправку важных уведомлений;
- приводит к массовым 500 ошибкам;
- указывает на недоступность важной интеграции.

Не считать критической:

- локальные предупреждения;
- единичные неважные сбои;
- recoverable ошибки без влияния на пользователя;
- технические сообщения для отладки.

- подключение существующего disk alert.

### Этап 4. Daily summary

Сделать:

- ежедневную задачу;
- сбор агрегатов за предыдущий день;
- отправку сводки в Users чат.

## 21. Критерии готовности

Функционал считается готовым, если:

- Telegram уведомления уходят в нужные чаты;
- пользователи не ждут отправку Telegram сообщений;
- регистрация, платежи и другие важные сценарии не замедляются;
- критические ошибки приходят в чат ошибок;
- важные биллинговые события приходят в billing чат;
- регистрация и удаление аккаунта приходят в users чат;
- daily summary приходит в 10:00;
- одинаковые критические события не спамят чат;
- ошибки доставки логируются.

## 22. Дополнительные требования, которые стоит зафиксировать сразу

### 22.1. Ограничения по данным

В Telegram-уведомлениях запрещено отправлять чувствительные пользовательские данные.

Не отправлять:

- содержимое переписок с AI;
- текст дневниковых записей;
- медицинские и чувствительные пользовательские данные;
- токены, секреты, webhook signature, заголовки авторизации;
- полные платежные реквизиты.

Разрешено отправлять только технический минимум, который нужен для диагностики или бизнес-контроля.

### 22.2. Идемпотентность

Для платежных и webhook событий нужно предусмотреть защиту от повторной отправки одного и того же уведомления, если одно и то же событие обработано повторно.

Минимум:

- использовать уникальный event key или dedup key;
- не отправлять повторно один и тот же billing event при дубле webhook.

### 22.3. Наблюдаемость

Нужно добавить базовые внутренние метрики или логирование по системе уведомлений:

- количество созданных событий;
- количество успешно отправленных уведомлений;
- количество неудачных отправок;
- количество подавленных дублей.

Это нужно хотя бы в логах, чтобы потом не гадать, почему чат внезапно замолчал.

## 23. Рекомендация по daily summary

Daily summary в Users чат - нормальное решение.

Отдельный чат под отчеты на первой итерации не нужен. Иначе начнется лишнее дробление, а пользы ноль.

Но нужно зафиксировать правило:

- оперативные пользовательские события идут в течение дня;
- daily summary отправляется всегда одним отдельным сообщением утром;
- формат этого сообщения должен быть стабильным, чтобы его легко читать глазами.

Идея правильная, оставляем именно так.
