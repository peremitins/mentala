
# MentAI — Архитектурные правила и ограничения (ARCH_RULES)

## Назначение
Этот документ фиксирует **обязательные правила** для реализации фронтенда и бэкенда MentAI, чтобы команда и ИИ‑ассистенты (Cursor, Copilot) следовали единым стандартам.  
Он **дополняет**: `MENTAI_TZ_PRODUCT.md`, `MENTAI_TZ_FRONTEND.md`, `MENTAI_TZ_BACKEND.md` и не дублирует их.

---

## 1) Общие принципы
1. **Безопасность по умолчанию**: приватность (opt‑in хранение истории), минимизация PII, шифрование в транзите/на диске, логирование без чувствительных данных.
2. **Типобезопасность end‑to‑end**: все запросы/ответы описаны в общих Zod‑DTO (`shared/dto/*`). Фронт и бэк валидируют схему.
3. **Fail‑soft UX**: в случае деградации AI/медиа — показываем дружелюбные подсказки/ретраи, интерфейс не «ломается».
4. **Обратимая эволюция**: изоляция доменной логики (Clean/Hex). Любую подсистему (billing и т.п.) можно вынести без переписывания домена.

---

## 2) Сетевые и API‑правила
1. **Команды vs Запросы (CQRS‑лайт)**  
   - Команды (изменяют состояние): `POST/PATCH/DELETE` — валидируются, **идемпотентны** (см. ниже).  
   - Запросы (чтение): `GET` — кэшируются/пагинируются.
2. **Тонкие хендлеры** (Nitro): только парсинг DTO + делегирование в use‑case. Бизнес‑логика — строго в `application/*`.
3. **Идемпотентность** для всех команд создания/оплаты/генерации:  
   - Заголовок `Idempotency-Key` + таблица `idempotency_keys` (уникальная пара: `user_id + key + route`).  
   - Повтор запроса возвращает **тот же** результат.
4. **Пагинация/сортировка**: `?page=1&limit=20&sort=-createdAt`. Ответ `{ items, page, limit, total }`.
5. **Ошибки** — единый формат:  
   ```json
   { "error": { "code": "E_VALIDATION", "message": "Invalid payload", "details": {...} } }
   ```
   Коды: `E_VALIDATION`, `E_AUTH`, `E_FORBIDDEN`, `E_RATE`, `E_NOT_FOUND`, `E_CONFLICT`, `E_UPSTREAM`, `E_UNKNOWN`.
6. **Версионирование**: заголовок `X-API-Version: 1` (при необходимости — путь `/api/v1/*`). Задним числом API не ломаем.
7. **Rate‑limit**: по IP и пользователю, агрессивнее на AI/tts/оплатах. Ответ при превышении: `429` + `Retry-After`.
8. **Наблюдаемость**: корреляционный `X-Request-Id` в ответах; Sentry + структурный лог `pino` (без sensitive payload).

---

## 3) Валидаторы/DTO/Контракты
1. Все ручки обязаны использовать **Zod**‑схемы из `shared/dto/*` (и на вход, и на выход).  
2. На фронте `vue-query`/компосаблы **парсят** ответ через Zod. Ошибка парсинга = баг либо API, либо клиента.  
3. Строковые поля локализуются через ключи i18n; сервер отдаёт **ключи**, а фронт — строки.

---

## 4) Аутентификация и авторизация
1. **JWT**: Access (короткий TTL) + Refresh (ротация на `/auth/refresh`).  
2. **Guards** в хендлерах: проверка скоупов/ролей, принадлежности ресурсов (`owner_id`).  
3. Общие требования безопасности: CORS — только доверенные origin, Helmet‑заголовки, HTTPS‑везде.

---

## 5) Консистентность и модели чтения
1. Для отчётов/графиков допустима **eventually consistent** статистика. Агрегации обновляются асинхронно (очереди BullMQ).  
2. Источником истины остаётся OLTP‑БД (Postgres). Кеши Redis — только ускорение чтения.

---

## 6) Медиа/AI/Очереди
1. TTS/STT/Chat — внешние провайдеры через `ports/*` гейты. Таймауты и ретраи с экспоненциальной паузой.  
2. Очереди: **BullMQ** для тяжёлых задач (TTS, экспорт, расчёт метрик). Идемпотентность — через job‑keys.  
3. Хранилище медиа: S3‑совместимое (R2). Публичные URL подписываются с TTL, приват по умолчанию.

---

## 7) UI/UX‑правила (фронт)
1. **Glassmorphism**: мягкие тени, `backdrop-blur`, полупрозрачные панели; доступность AA не нарушается.  
2. **Headless‑подход**: Radix Vue как поведение/доступность, стили — Tailwind/shadcn.  
3. **Стабильная навигация**: нижняя панель; fullscreen‑режим чата скрывает UI иконкой.  
4. **Сеть/ошибки**: все запросы через `vue-query`; состояния **loading/error/empty** обязательны.

---

## 8) Производительность
1. Бюджеты: **LCP < 2.5s**, **TTI < 3s** (mid‑девайсы).  
2. Lazy‑загрузка тяжёлых модулей (3D/графики/TTS). Code‑split страниц.  
3. Кэширование `GET` (etag/max‑age), сжатие (brotli/gzip).

---

## 9) Репозиторий/CI/CD/Код‑стайл
1. Линт на pre‑commit: `ESLint + Prettier + prettier‑plugin-tailwindcss`.  
2. Коммиты через **cz-git** + **commitlint** (`feat|fix|refactor|docs|chore|test`).  
3. Ветки: `main` (stabile), `develop` (интеграция), фичи `feat/*`, фиксы `fix/*`. PR — обязательный ревью + CI.  
4. Тесты: Vitest (юниты) обязательны для use‑cases и критичных composables.

---

## 10) Идемпотентные команды (детализация)
- Применимо к: создание сессии AI (если создаёт запись), TTS‑джоб, платежи/подписки, экспорт данных.  
- Схема: таблица `idempotency_keys` (`user_id`, `route`, `key`, `response_hash`, `expires_at`).  
- Повтор запроса с тем же ключом возвращает **оригинальный ответ** (или ссылку на job/result).

---

## 11) Redirect/Fire‑and‑Forget (если понадобится)
- Лёгкие эндпоинты (например, клики/реферальные переходы) не должны тормозить редирект.  
- Модель: **302 Redirect** сразу, событие клика уходит асинхронно в очередь.

---

## 12) Логирование и аудит
- Аудит действий: `who, what, when, where (ip/ua)`; **без** содержимого сообщений, если `saveHistory=false`.  
- Логи — структурированные, с `request_id`, безопасны для PII.  
- Ошибки и перформанс — в Sentry.

---

## 13) Процедура изменения контрактов
1. Обновляем Zod‑DTO в `shared/dto/*`, помечаем **minor/major**.  
2. Сначала выкатываем обратносовместимый сервер, затем фронт.  
3. Нельзя убирать поля без grace‑периода и предупреждения.

---

## 14) Definition of Ready / Done (бек/фронт)
- **Ready**: описан сценарий, DTO, коды ошибок, тест‑критерии, i18n ключи.  
- **Done (бэк)**: handler + use‑case + тесты + логирование + Sentry + дока.  
- **Done (фронт)**: экраны/состояния, валидация, локализация, Sentry, unit‑тесты, сторибук‑примеры (если UI).

---

## 15) Безопасность поставщиков (3rd‑party)
- Храним только необходимые токены, доступы — по least‑privilege.  
- Таймауты/ретраи/изоляция ошибок по каждому провайдеру.  
- Регулярный пересмотр ключей и логирование обращений.
